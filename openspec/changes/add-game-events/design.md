# Design

## Context

- 动机见 `proposal.md` 的 Why：规则集现在只有「定义条目」这一种登记方式（`rule.card`，见 `openspec/specs/rule-loading/spec.md` 与 `package-routing`），没有挂载点。
- 现成机制：`server/tools/simple-event.lua`（`moe.sevent`）已经提供了「注册顺序即执行顺序、`on` 返回 unsubscribe、`fire` 里 `xpcall(cb, log.error, ...)` 错误隔离」。**但它是一个单列表，没有事件名**，所以还需要一层"按名分发"。
- 依赖方向约束（既有）：`package/ → server/core`，**内核永不反向依赖规则**；规则门面 `moe.rule` 是 `require` 加载的不可重载模块。
- 生命周期约束：规则集是「清空 + 重新加载」，所以**注册必须跟着每一轮加载走**，不能跨轮残留。

## Goals / Non-Goals

**Goals:**

- 规则集能在加载期按时机名注册回调，注册顺序即执行顺序，注册可撤销。
- 触发方（装配 / 流程 / 无头测试）能按名触发并传上下文；未注册 = 空操作；回调报错隔离。
- 注册随清空重载一并清空；依赖方向不破。

**Non-Goals:**

- **不做**"回调返回值改事件载荷 / 可取消事件"这类机制：要覆盖就改**状态**（写标签、改属性、加标记），顺序天然给出覆盖语义。
- **不做**优先级、一次性、条件注册等花活（需要时再加，`sevent` 的 `once` 暂且不用）。
- 不做时机的**枚举 / 校验 / 文档表**：时机名由规则集自由使用（`'游戏开始'`、`'回合开始'`…），内核与加载器不认识任何具体时机名。
- 不把时机注册写进包元信息（预解析产物仍是依赖 / 互斥 / 条目清单）。

## Decisions

### D1 机制在内核，实例由规则门面持有

- 新增 `server/core/event.lua`：`Core.Event` = 「时机名 → `moe.sevent` 实例」的表，接口 `on(name, cb) -> disposer`、`fire(name, ...)`、`clear()`。
- 实例由 `moe.rule` 持有（`M.events`），`load` 时重置 —— 于是注册的生命周期天然等于一轮加载。
- 之所以不把机制写在规则门面里：将来 Room 等内核侧消费者要订阅游戏时机，若它们去 `require 'rule'` 就形成了内核反向依赖；**注入事件实例**才是正确姿势（内核提供机制 + 由上层持有实例并注入）。规则集文件里只注入 `rule`，因此它们拿不到内核，符合既有注入面约定。

### D2 注册按"加载期"限制，触发不限制

- `rule:on(name, cb)` 与 `rule.card` / `rule.depends` 一致：只在 `moe.rule.context` 存在时可用，否则报错 —— 这样"注册只在加载期发生"这条不变量成立，清空重载也就能可靠地清干净。
- `rule:fire(name, ...)` 谁都能调（装配 / 流程代码与无头测试）；**规则集文件虽然也能看到 `rule:fire`，但约定只由流程与装配代码调用**，内容包不主动触发（写进 `sanguosha-rules` 的规则集侧写法）。

### D3 覆盖靠顺序，而不是改载荷

- 上下文约定为**只读**（改状态靠调接口）。这样"后注册的后执行 ⇒ 它写的状态覆盖先前的"就自然成立，不需要"回调能改事件对象/能取消事件"的复杂机制。
- 例：身份场注册「游戏开始」写身份，国战（若也注册同一时机）后注册、后执行，于是它写的身份/上限生效。

### D4 薄封装而非新写一套

- `Core.Event` 只是按名分发 + 生命周期管理，实际回调链与错误隔离都交给 `moe.sevent`（已有测试与行为稳定，且 `fire` 已经是 `xpcall(cb, log.error, ...)`）。
- 空时机名 = 没建过 `sevent` 实例 ⇒ `fire` 直接返回（空操作），不报错。

## Risks / Trade-offs

- [时机名无约束 ⇒ 拼错名字静默无效] → 注册期不校验（用户明确"不预设"）；排查手段：注册与触发的日志，以及 `Core.Event` 提供"当前有哪些时机名"的查询（实现时给，测试也用得上）。
- [同一轮加载里重复注册同一回调 ⇒ 执行多次] → 属调用方责任；`on` 返回 disposer，重复注册可用它撤销；用例钉住"按注册顺序执行"。
- [回调里做重活拖慢触发] → 约定回调只做"登记状态"，需要玩家决策的部分走将来的挂起/恢复通道（不在本变更）。
- [注册在加载期之外被绕过（例如内核直接往事件实例里塞）] → 内核侧消费者通过注入拿到实例，属受控路径；规则集文件只能走 `rule:on`。

## Migration Plan

- 纯新增：新文件 `server/core/event.lua` + 门面新增两个方法与一个字段。回滚 = 删掉它们（规则侧无内容依赖，`package/` 还没有内容）。
- 兼容性：既有 `rule-loading` / `package-vfs` / `package-routing` 行为不变（本变更不 MODIFY 任何既有能力）。

## Open Questions

- 将来"回调返回是否影响流程"（如技能取消某操作）—— 属**结算栈/时机系统**的范畴，等做「杀」或技能时另开变更。
