# Design

## Context

动画节拍这一层（2026-10-15）的形状是：

- 内核只给原语 —— `Game:animSleep(秒)`（`---@async`），落在 `moe.await.sleep(秒 * moe.animScale)`；
- **节奏点与数字住内容侧**（`@基础/回合.lua` 进阶段前 `0.1`、`@基础/动画.lua` 打出牌 `1`）；
- 倍率是门面字段 **`moe.animScale`**（`server/moe-kill.lua`，默认 `1`；`server/test.lua` 顶层设 `0`）；
- **倍率 0 = 等于没调用**（连一次调度都不让出），所以「内容侧照常按节拍写、测试零等待」两头都对。

当时的结论是「前端不需要任何新消息 ⇒ 不涉及对外契约」，倍率只能启动时写死。本批把它变成运行期可调，于是**必须**补上协议那一段。

## Goals / Non-Goals

- 目标：调试时能在运行期改动画节拍；这个能力**只有调试模式**能用；改了对所有连接一致。
- 非目标：不给每条连接一份自己的倍率（一个 VM 一局，一份全局值就够）；不改内容侧的节奏点与数字；不改前端动画自身的时长；不做「倍率上限」这种防呆（只拒负数与非数字）。
- 非目标：做一个完整的「lobby / single 两种运行模式」体系 —— 本批只把 `debug` 这个概念立起来。

## Decisions

### 1. 调试模式 = `--single` 自动开，`--debug` 可显式开

`server/args.lua` 的 `M.current` 里推导：

```lua
result.DEBUG = result.DEBUG or result.SINGLE
```

理由是 `--single` 现在**就是**开发 / 调试用的启动方式（`main.lua` 拿它守在「lobby 还没做」那行），而将来 lobby 起来之后，开发者也该能在 lobby 模式下打开它 ⇒ 留一个显式开关。显式关掉不做（`--no-debug` 之类没需求）。

### 2. 门面字段 `moe.debug`，与 `moe.animScale` 同一种挂法

内核级、跨局、不参与重载 ⇒ 照 `AGENTS.md` 的硬约束挂在门面表 `moe` 上（`server/moe-kill.lua`），**不挂类表**。写成「有则复用」（`moe.debug = moe.debug or …`）以便热重载时不丢。

### 3. 客户端要知道 debug，走**快照**而不是单开一个查询方法

快照（`Proto.SnapShot`）本来就是「服务器给你的现状」，入座与重连各发一次。把 `debug` 与 `animScale` 塞进去 ⇒ **零额外往返**、重连后也自然拿到当前值。另开一个 `Game.GetDebug` 只是多一次往返，没有收益。

⚠️ 客户端拿到 `debug` **只用于界面**（要不要显示调节入口），**服务端必须自己校验** —— 协议是外部输入，不能信任客户端「我这边显示的是可调所以我发得出去」。

### 4. 请求名字取 `Game.SetAnimScale`，不改用 `Debug.*` 前缀

项目现有方法全在 `Game.` / `Panel.` / `Skill.` / `Ask.` 之下，没有 `Debug.` 前缀。这条方法改的确实是「局级的节拍」⇒ 归 `Game.` 一致。配套的通知同前缀：`Game.AnimScale`。

### 5. 改了就**广播**

`moe.animScale` 是**服务器全局一份**（一个 VM 一局）。一个客户端把它改成 `0.5`，那么**所有人**看到的节奏都变快、而且 `Game.AnimScale` 的当前值对每个连接都该是一致的 —— 不广播的话，其它客户端的界面里会一直显示旧值，调试时很容易懵。

广播范围与 `Room.Update` 那类**不同视角也照发**的通知一致：全体连接各一条。

### 6. 校验放在服务端，形状与既有方法一致

- 参数形状（`scale` 得是数字）由既有的**形状校验**在门口挡下（`Proto.Request.Game.SetAnimScale`），不合形状回 `-32602`，处理器根本不会被调到。
- 处理器里判两件事：**是不是调试模式**（不是 ⇒ `-32600` + 「只有调试模式能调动画倍率」）、**`scale >= 0`**（负数 ⇒ `-32600`）。`0` 是**合法值**（= 不等，正是测试与「快进」要的语义）。
- 校验不过 ⇒ **什么都不改**（包括不广播）。

### 7. 前端只存值，不缩动画

`agent` 存一个 `animScale`（默认 `1`），跟着 `Game.AnimScale` 更新；调试抽屉（`client/src/debug/Drawer.ts`）里在 `agent.debug` 为真时给几个按钮（`0` / `0.5` / `1` / `2` / `4`），点一下发 `Game.SetAnimScale`。

**前端那些动画时长一行不改**（`FLY_MS = 1000` / 出牌 `420` / `MOVE_MS = 260`）。口径是 2026-10-15 就定的「服务器只是慢一点、前端照常播」：倍率调小 ⇒ 服务器等得短 ⇒ 动画被下一批动作打断/取消 —— 这正是「快进」想要的观感；倍率调大 ⇒ 动画播完了服务器还在等 —— 也是「慢放」该有的样子。要真去缩前端的时长，等于让「倍率」同时管两套节拍，反而对不上。

### 8. 倍率作用在 `animSleep` 上，也就是内核那一行不用改

`Game:animSleep` 里已经是 `moe.await.sleep(秒 * moe.animScale)`，`scale <= 0` 时直接返回。本批**内核一行不改** —— 变的只是「谁能改 `moe.animScale`」。

## Risks / Trade-offs

- **调试开关被恶意利用**：靠服务端校验挡住（第 3 条），不靠 UI 隐藏。非调试模式下 `Game.SetAnimScale` 是**明确的错误**（`-32600`），不是静默忽略 —— 这样客户端出问题时看得见原因。
- **广播带来的一点噪音**：改倍率是低频动作（一局几次），比「一人一份」的实现省得多。
- **`debug` 与 `single` 的名字可能被读混**：`--single` 是**运行模式**、`debug` 是**语义**，本次两者恰好绑在一起，但代码里是**两个字段**（`Args.SINGLE` / `Args.DEBUG`），将来 lobby 模式不用回头拆。

## Migration

无。默认值 `animScale = 1`、`debug = false`（非 `--single` 启动时）—— 既有启动方式（`--single`）行为不变，只是多了「可以调倍率」的能力。
