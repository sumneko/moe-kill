# Design

## Context

动机见 `proposal.md`。与做法相关的现状：

- 「用牌」的四步现在写在 `Game:play` 里（找牌所在的牌区 → 取定义 → 校验目标 → 取出牌 → 跑回调 → 触发收尾时机），「伤害」现在写在 `Damage:apply` 里（触发「伤害-前」→ 改体力 → 触发「伤害-后」）。
- 内核已有的继承先例是 `OrderedZone : Zone`（`require 'core.zone'` → `Class 'OrderedZone'` → `Extends('OrderedZone', 'Zone')`）。类系统在 `New` 时会把**父类链与自己的 `__init` 依次调用**，并传同一份参数 ⇒ 子类 `__init` 可以只处理自己那部分，父类 `__init` 拿到的第一个参数同样可用。
- 项目硬约定：**可叠加的操作必须返回撤销函数**；`<close>` 语法可用（`enableCloseFunction`，测试里已在用）。所以"压栈"天然就该返回一个 dispooser，"退栈保证"用 `<close>` 表达。
- 禁止**模块级可变状态**（热重载要求）⇒ 栈必须挂在局的实例上，不能放在模块表里。

## Goals / Non-Goals

**Goals:**

- 「正在结算什么」成为一等的、可查询的状态，并为**插入结算**（技能 / 响应 / 濒死）留下唯一入口。
- 用牌与伤害的**调用方写法完全不变**（`game:play(...)` / `game:damage(...)`）。
- 退栈是**结构性保证**，不靠每个效果自觉。

**Non-Goals:**

- 不加入栈 / 退栈时机（本批沿用 `'卡牌-结算后'`）。
- 不做效果的中断 / 取消 / 替换（"被闪抵消"是下一批的事：那时是效果的结算内部改变结局，不是从栈里抹掉）。
- 不做效果的排队与异步结算（现在全是同步结算；挂起 / 恢复由将来的决策者接口承担）。
- 不让栈跨局共享（栈属于局）。

## Decisions

### D1 `Effect:apply()` 管栈，子类只实现 `settle()`

```lua
function Effect:apply()
    local pop <close> = self.game:pushEffect(self)
    self:settle()
end
```

**为什么**：压栈 / 退栈是**每个效果都一样**的结构性逻辑，写在基类一处，子类只关心"这次结算做什么"；同时天然满足"抛错也退栈"（`<close>` 在 `settle()` 抛错时也会跑）。

**备选**：每个效果自己 `push` / `pop`（重复代码，且漏一处就泄漏栈帧）；用 `xpcall` 包住 `settle()` 再重抛（手写控制流，容易漏）。

### D2 压栈入口返回撤销函数，栈由局持有

`game:pushEffect(effect)` → disposer（精确弹出那一次；不在栈顶时明确失败；重复调用安全）。栈是局的字段（`#effects`），随局存亡。

**为什么**：项目硬约定"可叠加操作返回撤销函数"；栈挂在局上才能满足"模块不许持模块级可变状态"，也不会串局。

**备选**：`game:popEffect()` 无参（无法精确对应一次压栈，乱序退栈静默出错）；模块级栈（违反热重载约定、多局会互相干扰）。

### D3 栈对外只读 + 压栈入口，不给"直接改栈"的能力

`game:getCurrentEffect()` / `game:getEffects()`（快照，栈底 → 栈顶）+ `game:pushEffect(效果)`。将来"插入结算"的内容侧（如无懈可击）就靠 push 拿到的 disposer 自己管理自己的帧。

**为什么**：查询接口让内容侧知道"现在在结算什么"（无懈、技能判定都要），而写入口只有"压一层"这一种，栈的顺序不会被外部乱改。

**备选**：完全不暴露（内容侧没法知道上下文）；暴露 `getEffects()` 返回**活表**（外部可以插队，栈语义失守）。

### D4 用牌的效果类叫 `UseCard`，住 `server/core/use-card.lua`，门面 `moe.useCard`

`UseCard : Effect`（`kind` = `useCard`），字段 `user` / `card` / `targets`；`game:play(...)` = 「造 `UseCard` + `:apply()`」。「用牌」的四步（找牌 / 取定义 / 校验目标 / 取出牌 / 跑回调 / 收尾时机）从 `Game:play` 搬进 `UseCard:settle()` —— 这四步本来就是"这次使用"的结算内容。

**为什么**：与 `Damage` 并列、对称（`OrderedZone` 也是独立文件 + 独立门面）；名字直白（"一次使用牌"）。

**备选**：`CardUse`（用户 2026-09-19 定为 `UseCard`）；把它塞进 `effect.lua`（一个文件两个类，门面只能挂一个）

### D5 牌回调与收尾时机的上下文 = `UseCard` 实例

`ctx.user` / `ctx.card` / `ctx.targets` 字段名不变，所以规则包与既有用例零改动；纯类型 `Game.EventCtx.卡牌` 撤掉（与伤害那批的处理一致：上下文就是内核的某个类时不再另立纯类型）。

**备选**：保留匿名表（与伤害的形状不统一）；包一层 `{ effect = ... }`（多一层）。

### D6 校验仍在取出牌之前，且失败时牌不动

校验（牌在使用者手上 / 有内容定义 / 目标合法）在 `UseCard:settle()` 开头做，全部通过才 `take`。压栈发生在 `settle()` 之前（`apply()` 里），所以校验失败时栈上**短暂**有这一帧 —— 但它由 `<close>` 恢复，外部观测不到（两次时机触发之间没有任何可观测点）。

**备选**：`apply()` 先问效果"能不能开算"再压栈（多一个钩子，收益只是"栈更早干净"，外部不可观测）。

### D7 同一个效果被 `:apply()` 两次不做限制，但栈有深度上限

本批不禁止同一实例反复结算（第二次照常压栈 → 结算 → 退栈，于是会再扣一次血）；要不要防重入（"一个效果只能结算一次"）等真有这种调用场景时再定。

**递归则由深度上限拦住**（用户 2026-09-19 定：「加个 100 层意思一下」）：结算栈最多 100 层，`pushEffect` 在达到上限时直接报错。定在 100 就是"意思一下"：结构化递归（技能 A 触发 B 触发 C）不会碰到，写错的无限递归会立刻撞墙而不是把栈或内存跑爆。常量放栈的所有者上（`Game.MAX_EFFECT_DEPTH = 100`）。

**备选**：不设上限（写错就无限递归）；可配置上限（`setValue`）—— 没有消费者，不值当。

## Risks / Trade-offs

- [栈帧泄漏] → `<close>` 结构性保证 + 用例钉住「结算抛错后 `getEffects()` 与结算前一致」。
- [嵌套结算是顺序敏感的] → 栈语义就是先进后出，用例覆盖「内层结束后回到外层」。
- [效果对象被复用（同一实例压栈两次）] → 允许；disposer 是**按次**的（每次压栈一个），互不干扰，用例覆盖。
- [`Damage` 从"直接改体力"变成"在栈上改体力"⇒ 未来濒死插入会自然落在「伤害-后」之后] → 正是想要的效果；本批不做濒死，但结构已经对了。
- [`UseCard` 与 `Damage` 的上下文都是对象 ⇒ 包作者看到的是内核类型（`UseCard` / `Damage`）而不是纯表] → 类型由 `env-meta.lua` 给出，第三方包照抄注解即可；这也是 `core-effect` 的对外契约。

## Open Questions

- 深度上限（100 层）将来要不要变成可按局配置的规则数值？现在写成常量，真出现"合法地需要更深"的模式（如大规模连锁）再谈。
