## 背景

协议自 2026-10-09（`add-client`）落地：帧格式、`Link` 抽象、`Client` 端点、模块级方法表。之后陆续长出来 —— 卡牌下行（`add-card-sync`）、玩家数据与属性（`add-player-update` / `add-player-attributes`）、流程（`flow-sync`）、面板（`panel-sync`）、技能（`skill-sync`），以及请求级时限（2026-10-13）。

所以规格要**一次覆盖当前这条线的全貌**，而不是复述最早那一版。

## 判断

### D1 规格写「外部必须知道的」，实现细节不进规格

形状以 `server/proto.d.lua` 为准（它同时是 `--gen-proto` 的输入 ⇒ 前端类型与服务端声明天然同源）；规格里**只写**：分帧、四种消息、错误码、方法 / 通知清单、时限与取消的语义。`Proto.Card` / `Proto.Panel` 这类数据形状**不抄** —— 抄一遍必然与声明漂。

### D2 语义进规格，落点不进

规格写「一条请求要能认出是哪条连接在问、问的是谁」「状态快照走 result 不走通知」这类**外部能观察到**的约定；`moe.snapshot.requireUser` 这种落点写在实现里（必要时在 design 提一句）。

### D3 取消与时限分开写

两者常一起用，但不是一回事：**取消**是双向的（谁都可以 `Cancel { cancelToken }` 掉一条可取消的请求），**时限**是服务端对询问的兜底（`timeLimit` + 宽松 1 秒，到点按「取消」收尾并通知客户端别答了）。分开写才不会把「超时」误当成一种取消。

### D4 通知的「攒批 / 即时」也写进规格

「同一次调度攒成一条」与「回合 / 阶段 / 结束这三类即时发」是**客户端能观察到的**行为（前者决定条数、后者决定节奏），属于契约的一部分。

## 风险

- **规格会与实现漂**：唯一的对策是「形状以 `proto.d.lua` 为准」这条指针 + 方法 / 通知清单要随着加（改协议时顺手改规格）。
- 本变更归档后，`openspec/specs/jsonrpc-protocol/spec.md` 成为主规格；后续协议变更**必须**走 delta（这是本项目第一个「活的」对外契约规格）。
