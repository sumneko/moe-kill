## 为什么

JSON-RPC 协议是本项目**唯一长期稳定的对外契约** —— 前端、将来的 AI 客户端与「一个后端对接多种前端」这条主线的所有消费者都按它对接。可它现在只活在 `server/proto.d.lua` 与实现里：**没有一个外部消费者能读的规格**。

按项目口径（`AGENTS.md`「工作流」）：只有真要长期稳定的对外契约才写规格，这类变更**不设** `skip_specs`。协议正属于这一类（有外部消费者、改动昂贵）。

本变更**不实现任何新功能** —— 协议早已跑通（六种询问、19 条通知、一条静态快照全在用）。它把**既成事实**写成规格。

## 变更什么

- 新增能力 **`jsonrpc-protocol`**，8 条需求：分帧与传输 / 四种消息 / 参数形状校验 / 错误码 / 上行方法清单 / 时限与取消 / 下行通知清单 / WebSocket 握手。
- 规格**描述现状**：每条需求都对应已经在跑的代码（在正文里点出落点文件），**不改实现**、不改形状、不加方法。

## 不做什么

- 不写「实现计划」（这里没有实现要做）
- 不把 `proto.d.lua` 的字段表抄一遍：形状的**唯一声明处**是 `server/proto.d.lua`（并由 `--gen-proto` 生成前端类型），规格只写「以它为准」+ 消息四类与错误码这些**外部必须知道**的部分。
- 客户端打包 / 静态文件通道、worker 模式：另开变更。
