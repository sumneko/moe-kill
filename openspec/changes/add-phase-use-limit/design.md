# Design

## Context

现状（见 `proposal.md` 的 Why）：

- **阶段只是两个时机**：`package/@基础/回合.lua` 自己 `game:fire('阶段-开始' / '阶段-结束', { player, phase })`，内核不认识「阶段」；别的包想按阶段办事只能再记一遍"现在是什么阶段"。
- **次数挂在玩家标签上**：`@基础/使用限制.lua` 用 `player:setTag('本阶段用过', …)`，靠 `'阶段-开始'` 清、`'阶段-结束'` 删。
- **限额是一张按牌名查的表**：`PLAY_PHASE_LIMIT = { ['杀'] = 1 }` —— 与"这张牌自己的规则"分家，将来「出牌阶段限一次」的技能无处可写。

可用的既有形状：

- 生命周期走 `Class` + `Delete`/`__close`：`GCNode:__close()` 就是 `Delete(self)`，`Task` / `Timer` 同款；内容侧拿不到 `Delete`，所以要么 `<close>`、要么对象自己开一个方法。
- `game.desk` / `game.random` 是**公开字段**（只认字段、不加 getter）；`Player` / `Zone` 有一层**不透明标签**（`setTag / getTag / removeTag`）。
- 内容定义：`Card '杀'` = 加载期环境函数 → `game:declareCard('杀')` 返回 `CardDef`，链式 `:on('获取目标', …)`；`game:getCard('杀')` 可在别处取回同一条定义。
- 内容侧注入面只有 `game` / `Card` / `Depends`（没有 `moe`、没有 `Delete`）；包之间共享函数靠**直接写全局函数**。

## Goals / Non-Goals

**Goals:**

- 「现在是哪个阶段、属于谁」在内核里是**一等对象**，进/出是一次操作，且能嵌套。
- 「某阶段某名字最多用几次」写在**内容定义**上（卡牌，将来技能同一形状），基础规则里不再有按名字写的表。
- 次数记在阶段实例上，随阶段结束自然消失（且**只在自己的回合里记**）；两种口径（**此牌不计次** / **本阶段该名字不限次**）都能用阶段实例上的接口表达。
- **按次数的阻止是内核的内建条目**（校验不过就不问内容侧），用牌成功时内核自己记账。
- 阶段外不受限（与现状一致）。

**Non-Goals:**

- 不做武将技能系统：本批只把次数接口留成"名字通用"的形状（技能的定义与发动时机等技能系统落地再定）。
- 不做判定 / 装备 / 距离 / 回合时限，不动会话与 JSON-RPC，不写规格（探索期，见 `.openspec.yaml` 的 `skip_specs`）。

## Decisions

### D1 阶段 = 内核实例 + 栈 + `<close>`

- `game:enterPhase(player, name)`（**玩家在前**，用户 2026-09-22 定）建一个 `Phase` 实例：压栈 → `game.phase = 它` → 触发 `'阶段-开始'` → 返回实例。
- 返回的实例当 **`<close>`** 用：`local phase <close> = game:enterPhase(player, '出牌')`。`Phase:__close()` = `Delete(self)`（框架惯例），`Phase:__del()` 里真正离开：触发 `'阶段-结束'` → 出栈 → `game.phase` 回到上一层或空。
- `game.phase` 是**公开字段**（与 `game.desk` / `game.random` 同风格），读当前阶段（不在阶段里就是空）；阶段自己的 `name` / `player` 也是公开字段。
- 用**栈**而不是单槽：将来有「额外的一个出牌阶段」这类嵌套。离开时校验"就是栈顶"，不是栈顶就报错（内容侧按 `<close>` 自然 LIFO，不是栈顶 = 用错了）。
- **事件由内核触发**（不再由流程 fire）：进入/离开是一次操作，触发点必须唯一，否则包可以只压栈不触发、状态与事件不一致。
- 阶段实例带**不透明标签袋**（`setTag / getTag / removeTag`，与 `Player` 同形状）—— 给内容侧放"这个阶段里的账"。
- 备选（否）：① 内核只存字段、事件仍由流程 fire（两个状态源，迟早不一致）；② 阶段实例不带标签（"记在阶段上"就没地方落）；③ 单槽不嵌套（额外阶段必来，提前留形状便宜）。

### D2 阶段时机的上下文 = 阶段实例

`'阶段-开始' / '阶段-结束'` 的 ctx 直接给阶段实例（`ctx.player` / `ctx.name`），与 `'卡牌-结算前'` 直接给效果实例同风格。

**BREAKING**：`ctx.phase`（阶段名字符串）→ `ctx.name`。只影响 `@基础/回合.lua`（`@基础/使用限制.lua` 本批会被删）与规则侧用例，同批改掉。
备选（否）：保留 `{ player, phase }` 表再塞一个实例字段 —— 一个字段两个含义，绕。

### D3 限额写在内核的内容定义上，用专门接口

`CardDef:limit(阶段名, 次数)`（链式、可多次调、按阶段名写）+ `CardDef:getLimit(阶段名)`（**没为这个阶段声明过就返回 `1000`**，用户 2026-09-22 定）。

- **1000 = "实质上没有限制"**（与「无限用 = +1000」同一口径）：这样上限永远是一个整数，基础规则那边不用为"没声明"写特例，「可以多用一次」（+1）对没声明的牌也照样成立。
- 与出牌阶段的终止条件 `MAX_PLAY_COUNT = 1000`（`@基础/回合.lua`）同值，量级上是同一件事。

- **为什么给专门接口**（用户 2026-09-22 定）：阶段已经是内核概念，「某阶段最多用几次」就是它能认得的形状；专门接口比"通用字段袋 + 基础规则自造键名"少一层约定，还能在编辑期收窄类型（不用再往包 `meta.lua` 里补）。
- 阶段名**不透明**：内核只当键用，不校验取值、不认识"出牌"。
- **不做基础规则里的配置表**（用户 2026-09-22 定）：限额跟着定义走 —— 别的包要改就 `game:getCard('杀'):limit('出牌', 2)`（后写的覆盖先写的，与 `:on` 追加回调同一套）。
- 技能将来照抄同一形状；现在不抽公共基类（技能定义还没有）。

### D4 检查与记账都在内核里（按次数的限制整套进内核）

（用户 2026-09-22 定）阶段、限额、账都在内核了，按次数的阻止就直接做成内核的内建条目：

- **检查**：`game:canUse` 的内建条目多一条：**阶段存在且阶段角色就是使用者**时，`已用次数 < 上限` 不成立就直接返回原因，**不再触发 `'卡牌-能否使用'`**（“不通过就不用问规则了”，用户原话）；阶段不属于使用者（别人的回合）或不在任何阶段里（阶段外）⇒ 不判。
- **记账**：`game:useCard`（`UseCard:settle()`）在校验通过之后由**内核**记一次（`phase:addUseCount(名字, 1)`），条件与检查一致（只在自己的回合里记）。顺序：`canUse` → **记账** → 取牌 → `'卡牌-结算前'` → 逐目标结算 → `'卡牌-结算后'`；于是牌 / 技能在结算过程中的任何时机调 `addUseCount(名字, -1)`（“此牌不计入次数”）都来得及，不受注册顺序影响。
- **为什么不让基础规则记**：账与限额都在内核，记账是一句 `addUseCount`，再让内容侧挂 `'卡牌-结算前'` 只是多一层往返，而且“自己的回合”这个条件就写了两遍（容易漂）。
- **`canUse` 仍然只读**：它会被 `askCard` 用来筛选项（一次筛选可能调几十次）⇒ 内建条目里**不能**记账，记账只能在真正用出去的路径上。
- 备选（否）：把次数留在 `'卡牌-能否使用'` 里当内容侧条目（现状）—— 内容侧只能"否决"、不能"先判"，每次用牌都要绕一圈规则层，且与内核已有的账 / 限额分家。
- **`@基础/使用限制.lua` 删除**（用户 2026-09-22 同意）：三件事（按牌名的限额表、`'卡牌-能否使用'` 里否决、`'卡牌-结算前'` 记数）分别被牌定义与内核接手。

### D5 两个调整接口：改已用次数 / 改上限，都挂在阶段实例上

（用户 2026-09-22 定）两个接口都以**（名字, 次数变化）**为参数，都是 **`Phase` 的方法**（以 phase 为对象）：

| 接口 | 作用 | 两种口径怎么用 |
| ---- | ---- | ---- |
| `phase:addUseCount(名字, 次数变化)` | 改本阶段该名字**已用次数** | 「此【杀】不计入次数」= `addUseCount('杀', -1)`（直接传名字，不传 ctx） |
| `phase:addLimit(名字, 次数变化)` | 改本阶段该名字的**上限增减** | 「可以多用一次」= `addLimit('杀', 1)`；「本阶段使用【杀】无次数上限」= `addLimit('杀', 1000)` |

- **不再做“无限”专用接口**：无限也是有上限的，+1000 次就够了（用户 2026-09-22 定）；好处是只剩一种算术（整数增减），不用再引入哨兵值。
- 读接口：`phase:getUseCount(名字)`（默认 0）、`phase:getLimitDelta(名字)`（默认 0）。
- **有效上限 = 内容定义声明的基数 + 阶段上的增减**：`CardDef:getLimit(phase.name)`（没声明就是 1000）+ `phase:getLimitDelta(name)`；没有例外分支（"不限次数"只是 1000 这个数），合成处就在内核那条内建检查里。
- 为什么不用"给这一次使用挂标记"：`canUse` 是**无状态**的同步校验（被 `askCard` 拿来筛选项，没有"这一次"的概念），per-use 标记在检查侧根本看不见；而"退"是主动调用、不依赖事件顺序，与现有机制不打架。

## Risks / Trade-offs

- [阶段时机 ctx 改了（BREAKING），漏改就静默失效（`ctx.phase` 变空）] → 用例钉住两个事件拿到的 `player` 与 `name`；`env-meta.lua` 同步类型（写错编辑期就报）。
- [`<close>` 忘了写 ⇒ 阶段不离开、`game.phase` 一直挂着] → 流程统一 `<close>`；离开时校验栈顶，乱序直接报错；用例覆盖嵌套与作用域结束。
- [在 `__del` / `<close>` 里触发时机：取消路径（`coroutine.close`）下可能打折扣] → 与既有的 `<close>` 守卫（`Task` / `Timer` / 效果族）同一形状；规则侧时机的回调本来"报错被隔离"，最坏是少改一次状态。
- [阶段栈是运行期状态，`resetContent`（重装规则集）不能清它] → 与号源 `nextId` 同样处理：放在 `__init` 里、不写进 `resetContent`；用例覆盖"重装后阶段栈照常"。
- [计数账上是否需要玩家维度] → 不需要（D4）：只在自己的回合里记 ⇒ 账只按名字。
- [删掉 `package/@基础/使用限制.lua`：还有没有别处引用它] → 删前 grep 一遍包名 / 文件路径（清单、用例里的 `packages = { '@基础' }` 都不点名文件）看看。
- [限额语义将来可能扩展（如"0 = 不准用"、"每回合"而非"每阶段"）] → 现在按数字与阶段处理；真有跨阶段口径时在同一个接口上加。

## Migration Plan

无（单进程、探索期、无外部消费者）：改完跑 `server/bin/moe-kill.exe --test` 全绿即可；不改 JSON-RPC，不回改 `openspec/specs/`。

## Open Questions

- 两个接口与两个读接口的名字（`addUseCount` / `getUseCount` / `addLimit` / `getLimitDelta`）—— 改名只动一处定义 + 用例。
- 「上限增减」的作用域按**本阶段**存（限额本来就按阶段查）；将来真有跨阶段的"本回合"口径再加。
- 「限额 0」的含义（不准用 vs 视为未声明）未表态，现在按数字处理（0 = 一次都不行）。
- **技能的使用次数**（“出牌阶段限一次”的技能）：接口已经名字通用（技能自己调 `phase:addUseCount`），但技能系统还没做，本批不接。
