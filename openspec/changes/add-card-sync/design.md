# Design

## Context

- 协议类型已在 `server/proto.d.lua` 就位（`Proto.Zone` / `Proto.CardTemplate` / `Proto.Card` / `Proto.MovingCard` 与四条 `Proto.Notify.Card.*`），实现还没有。
- 可复用的既有件：`Player.Update` 那套「按视角组装 + 置脏 + 一次调度末尾 flush」（`game:markDirty` / `moe.player.sendUpdates` / `User:update`）；`'卡牌-进入区域'` / `'卡牌-离开区域'` 两个时机（对所有区都发，含临时区；对区的主人再发一份那份也在）；`Zone.name` / `Zone.owner` / `Zone:isVisibleTo`。
- 现状：`Card.id` 是「建牌时由 `game:nextId()` 发的永久号」，产品代码里只有 `Card:__tostring` 在用它（`game:nextId()` 的另一位用户是 `player.id`）。
- 临时区是「每个效果自己一块」，既没有名字、也不登记、没有归属 ⇒ 协议上全部等价。

## Goals / Non-Goals

**Goals:**

- 客户端拿到一份「盘面」：每个牌区里有哪些牌、牌面是什么，以及牌从哪到哪的动画线索。
- 变化一律表达成「不可变实例的增删」+ 一类原地更新，客户端不必做差分推理，也不会因为重播动画或重建实例而打乱它自己排好的手牌顺序。
- 复用既有时机、可见性与批量下发机制，不新开通道。

**Non-Goals:**

- 牌级朝向（「这张牌正面朝上」作为牌自身的状态）—— 沿用区级 + 搬动级两层可见性；牌级那批另开。
- 快照 / 重连（`Proto.SnapShot` 里加 `cards`）—— 本批用创建通知灌全量，重连那批再做。
- 询问（`askCard` 等）的下行往返 —— 那是下一条协议。

## Decisions

### D1 视图与 id 住在传输层，每个连接各一套（内核不加协议字段）

协议用的 id **不进内核**：`server/transport/card-sync.lua` 按**每个连接**维护一份「这个客户端当前看见的卡牌视图」（`cards: table<id, Proto.Card>`，含背面牌），id 由**这个连接自己的号源**分配。

- 理由（用户 2026-10-10）：① 这个 id 是「协议看到的牌」，不该变成内核 `Card` 的属性；② 每个连接各一套之后，「背面牌」的 id 就成了**只有那个客户端认识的匿名代号**（见 D9）。
- 代价：状态随连接数成倍（每份视图 ≈ 该客户端看得见的牌数）；断线时随连接释放。
- 备选（否）：id 进内核 `Card`（破「内核不认识协议」）；全局一套 id（背面牌会在连接之间可配对）。
- **内核那个 `Card.id` 留着**（用户 2026-10-10 定）：它由 `game:nextId()` 在建牌时发、产品代码里只有 `Card:__tostring` 在读，**与协议无关** —— 本变更不碰它，就当牌的调试号用（也免得改一批调用点）。
- **顺带清理（用户 2026-10-10 定）**：内核那个既没人消费、协议又用不上的 `Card.id` **删掉** —— `moe.card.create` / `Card:__init` 不再收号，`game:createCard` / `createVirtual` 不再传 `game:nextId()`，`Card:__tostring` 换成不依赖号的写法（重名牌多，建议带牌名或完整名），受影响的既有用例跟着改。`game:nextId()` 本身留着（`player.id` 还在用它）。

### D2 变化判定：拿「这个连接的视图」当基准逐字段比

每次组装时对每张相关牌算出新的 `Proto.Card`，与**这个连接视图里已有的那份**（同一个 id）逐字段比：

| 比较结果 | 动作 |
| --- | --- |
| 完全一致 | 什么都不发 |
| 有变化、协议 zone 相同 | `Card.Update`（id 不变） |
| 有变化、协议 zone 不同 | `Card.Remove` + `Card.Create`（新 id，见 D9） |

- 理由：视图本来就是「这个客户端手上有什么」的账本，拿它当基准最自然 —— **不需要**另存一份「上次快照」，而且「要不要发」天然按视角算（别人的暗牌在自己这份里本来就没有牌面，暗牌翻不翻对他不算变化）。
- 早先那版打算用「服务器侧状态」当基准（图省一份每连接的账），被否：省下的那点内存换来「视角突变时不发通知」的坑，而视角化的账本来就要有。
- 备选（否）：只要被置脏就发 —— 会产生大量无意义通知（手牌反复进出尤其明显）。

### D9 背面牌的 id 是匿名代号：从不可见区移除时随机挑一个

对某个连接而言，**看不见内容的区**里的每张牌都只有 id（没有牌面），客户端只知道「这个区里有几张」，分不清哪张是哪张。因此：

- **进入不可见区** ⇒ 给一个新 id（内容为空）；对客户端来说就是「这个区又多了一张」；
- **从不可见区移除** ⇒ **从「这个客户端看到的该区那些没有牌面的牌」里随机挑一个 id** 当作被移除的那张（客户端本来就分不清，挑哪个都对）；
- **进入可见区 / 从可见区移除** ⇒ 用真实那一张的 id。

- 理由：否则「移除 + 创建」是**对称**的，客户端能把「刚消失的匿名牌」与「刚出现的明牌」配起来 ⇒ 学到一个它不该知道的事实（这张明牌原来在某人手里）。随机挑把这条推断打断。
- 随机源用**连接自己的**（不影响玩法复现；回放也不要求两次的 id 相同）。

### D3 协议 zone =「玩家 + 区名」，临时区一律等价

`Proto.Zone` 由 `zone.owner?.id` 与 `zone.name` 构成；两者都缺（临时区）时表示成同一个空对象。

- 理由：「换没换区」是给客户端看的判据，客户端看不见的东西（具体是哪一块临时区）不该参与判断 —— 否则两块临时区之间挪牌会白换一次 id、白播一次动画。
- 实现：比较就是比这两个字段（两个空对象互相相等），不需要额外标记。

### D4 `Card.Move` 走「离开时记住、进入时配对」，当场发

`'卡牌-离开区域'` 时记下「这张牌从哪个区出来」（一张牌一次只在一个区里，一个字段就够）；`'卡牌-进入区域'` 时取出它与目标区比较，协议 zone 不同就**当场**发 `Card.Move`（带 `from` / `to` 与每张牌**搬之前**的展示 id）。

- 理由：`Remove` 只带 id（不知道去哪）、`Create` 只带新牌（不知道从哪来），动画需要 from/to；而"一次搬牌"在内核里就是连续的「离开 + 进入」，用这两个时点配对最省，不必在内核 `Zone` 里开协议口子。
- 代价：它不受 flush 合并管；但一次搬牌的 `Move` 与随后的 `Remove` / `Create` 天然相邻，客户端按 `Move.cards[].id` 关联即可。

### D5 可见性在后端消费，只下发「看得见 / 看不见」

牌面是否下发 = 区级可见性（`zone:isVisibleTo(player)`）叠加这一次搬动的可见性；任一不可见就不给 `template`（客户端渲染成背面）。

- 理由：客户端不需要知道可见性规则，只需要知道"给我看的这张牌是什么"；可见性本身是规则层概念，原样下发反而把前端的秘密映射复杂化。
- 沿用 `Player.Update` 的组装方式：遍历局里所有有 `user` 的玩家，各组装一份。

### D6 出口：给 `User` 加一条卡牌方法

`User` 上除 `update(data)`（玩家数据）之外再加一条卡牌数据的出口（`updateCard(data)` 之类），`ClientUser` 覆写成四类 `notify`。

- 理由：延续「一类数据一条协议、一条出口」的既有形状；内核只把组装好的表交出去，不认识协议。
- 备选（否）：泛化成 `User:sync(kind, data)` —— 现在只有两类数据，泛化过早。

### D7 批量：三类通知置脏 + 一次调度末尾 flush，`Move` 例外

- `Card.Create` / `Card.Update` / `Card.Remove` 攒着，flush 时按「移除在前、创建在后」各发一条（空的条不发）。
- `Card.Move` 当场发。
- 与 `player.custom` 的 `markDirty` + `moe.await.wake(flush)` 同一套：**第一次标脏只登记一次 flush**。

### D8 落点：住在 `server/transport/`（内核不认识协议）

新增 `server/transport/card-sync.lua`：订阅两个区域时机、维护脏卡表与「上一次同步的那份」、flush 时组装并按收件人下发；门面 `moe.cardSync`（与 `moe.clients` 并列，在 `server/transport/init.lua` 里装载）。

- 理由：架构硬约束是「内核 MUST NOT 依赖协议 / 网络」—— 把内核状态翻成协议形状、再按连接发出去，这层只能在传输侧；内核只提供时机、区名、归属与可见性。
- 备选（否）：放 `server/core/`（破约束）；放 `server/session/`（那是待退役的外壳）。
- 「上一次同步的那份」挂在牌实例上（一个私有字段，随牌走），不另建表。

### D10 牌面分两层：`template` = 牌自己那份面，`modifier` = 转化叠出来的那一份

`Proto.CardTemplate` 的字段都是可选的：`template` 给**牌自己那份**（永不变）、`modifier` 给**所有「转化」叠出来的那一份**（没挂转化就不带这个字段）。客户端把两份叠起来才是当前牌面。

- **合并只在内核做一份**：`card.ownFace` / `card.modifier` / `card.face`（最终值）三条读法都住在 `Card` 上，协议层只是抄结果 ⇒ 客户端不必再实现「后挂的覆盖先挂的」。
- **代价**：「挂了转化」这类变化只体现在 `modifier` 上（`template` 基本不变）；`Card.Update` 的判定照旧逐字段比这两块。
- **`Card.Move`**（`Proto.MovingCard`）只带 `template` —— 它与该连接已有的快照合起来用，客户端本地就有 `modifier`。

## Risks / Trade-offs

- **[每个连接一份视图 ⇒ 状态随连接数成倍]** 每份视图的大小是「该客户端看得见的牌数」（标准包百余张）。→ 断线随连接释放；真有几百连接再加共享或裁剪策略。
- **[随机挑 id ⇒ 同一局两次运行的报文不同]** 这是有意的（id 只是给客户端用的代号），不影响玩法与回放的正确性 ⇒ 用例断言里**不要**写死背面牌的 id。
- **[全量灌入的体量]** 开局要把全场牌（含抽牌堆，标准包百余张）发一遍 —— 一次性开销，换来"之后只发变化"。抽牌堆整堆只发背面（不带牌面），实际体量待观察。
- **[临时区等价 ⇒ 客户端分不清两块临时区]** 这是有意的（客户端本来也不该看到"是哪块临时区"）；将来做"桌面中央"表现时，临时区一律渲染到同一个位置即可。
