# Design

## Context

- 结算栈（`game:getCurrentEffect()` / `getEffects()`）与退栈撤销函数已就位，`Effect:apply()` 目前是「压栈 → `settle()` → `<close>` 退栈」。
- 效果实例持有 `game` 与 `kind`；子类（`UseCard` / `Damage`）持有各自的业务字段。

## Decisions

### D1 父效果取自结算栈，而不是取自调用者

`Effect:apply()` 里，在 `pushEffect(self)` **之前**读 `game:getCurrentEffect()` 赋给 `self.parent`。

- **为什么在 `apply()` 里**：`settle()` 里各处造效果（一张牌结算出多个伤害）不用各写一遍；将来 `判定` / `技能` 也一样自动有父。
- **为什么必须在压栈之前**：压栈之后读到的就是自己。
- **为什么不在 `create` 时赋值**：效果对象可能先造好、稍后才结算（延时类、批量结算），创建那一刻的栈顶未必是它真正的父。

### D2 父 ≠ 伤害来源

- `parent`（结算嵌套）回答"我是在哪次结算里发生的"；
- `Damage.from`（伤害来源）回答"这一下算谁的"。

有延时类的情形能说明两者为什么必须分开：闪电的伤害是在**判定结算**里发生的（父是那一次判定/延时结算），而"来源"另有其说。把两者合并会让"来源"随结算结构变化，是错的。

### D3 类型面

`---@field parent? Effect`（可选 = 「不存在」）。**字段而不是 getter** —— 与刚定的口径一致（一个概念不要两套 API）。根效果的 `parent` 就是「不存在」，不报错。

## Risks / Trade-offs

- [链是单向的，想看"这次用牌造了哪些伤害"要遍历] → 记录为已知取舍：子列表没有消费方，等真有需要再加。
- [有人误用 `parent` 当"归因"] → 类型与文档里各写一句，指向 `Damage.from`。
- [`apply()` 被重复调用时 `parent` 会被重算] → 效果是一次性的（结算完即退栈）；不为此加防御，重复 `apply` 本就是误用。

## Open Questions

- 深度上限（100 层）命中时报错，要不要顺便把**链**（每一层的 `kind`）带进错误信息，便于定位？等真有此类排查需求时再定。
