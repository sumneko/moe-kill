# Design

## Context

- 现状（动机见 proposal.md）：`Effect:apply()` 建一个协程、只 `resume` 一次，且只认一种让出理由 `'cancelled'`（取消）。
- **每个效果有自己的协程**，这是取消的实现基础（取消一个效果 = 丢弃它的栈帧、外层继续）。本批不改这条。
- 现成的基础设施（复用，不重写）：`server/tools/await.lua`（`await.call` / `await.sleep` / `await.yield`，照搬 4.0.0）、`server/tools/event-loop.lua`（`start(options, errorHandler)`，options = `waiter` / `deadline` / `waker`）、`server/tools/timer.lua`（`wait` / `update` / `getNextDeadline`）、`moe.eventLoopOptions()`；`server/test.lua` 里用例体本来就跑在 `moe.await.call` 起的协程里、事件循环由它启动 ⇒ **最外层已经可让出**。
- 4.0.0 的参照做法：一个请求 = 一个协程；挂起时循环继续跑；**测试给事件循环一个假 sleeper**（`ls.timer.update(1000); thread.sleep(1)`）推进虚拟时间 ⇒ 等待类用例不必真等。
- 用户口径（2026-09-20）：「能单独实现和测试抽象的 Effect 系统吗（包括等待响应）？关于 ask 我还有些东西要思考」⇒ 本批只做抽象层，`Ask` 一行不动。

## Goals / Non-Goals

**Goals:**

- 一次结算能**真的挂起**：等外部输入期间把控制权交回最外层，输入到达后从原处继续，结算栈与状态保持。
- **效果就是可等待的任务**：完成信号（完成 / 取消 / 失败）+ `result` / `err`；`apply`（驱动）与 `wait`（等它结完）职责分开（D4）。
- 挂起期间**拒绝起新结算**。
- 测试侧能把「挂起 → 稍后收到结果 → 继续」与「挂起 → 取消」整条链跑完，且等待用例**不必真等**。

**Non-Goals:**

- **`Ask` 的挂起语义**（答案从哪来、时限、回答者形状、超时）：用户还在想，本批不做 —— `ask.lua` 一行不动，`Ask` 照旧当场取答案。
- **生产侧的最外层**（会话怎么把请求报给前端、怎么收答复）：本批不做。
- 不引入 `ls.task` / `ls.progress` 式任务与进度体系（上一批已否 `ls.task`，见 `add-jink-response` 的 D6）。
- 不改取消的既有语义（运行态让出 + 由驱动点 close；挂起态直接关闭），只补"挂起态取消要连带收掉子结算"。
- 不改内容包写法（【杀】照旧调 `game:ask`）。

## Decisions

### D1 挂起 = 把调用方一并挂起（用户定）

`Effect:apply()` 改造成**可挂起**：结算要等外部输入时，它把**调用它的执行体**一起挂起（沿调用链一路让出到最外层），输入到达后从挂起处继续，`apply()` 到那时才返回。`game:play` / `game:damage` / `UseCard:settle` / `CardEffect:settle` 随之都是可挂起入口（标 `---@async`）。

- **否掉**：`apply()` 返回 `'done' | 'suspended'` 状态码 —— 那会把"等"这件事推给每一层调用方（`game:play` → 会话 → 协议 → 前端），任何一层忘了传就静默错序。

### D2 让出协议：驱动点独占 resume，理由分派

保留「这次结算的驱动点独占 `coroutine.resume`」这条不变量。让出带**理由**：

| 理由 | 载荷 | 谁发出 | 谁处理 |
| --- | --- | --- | --- |
| `'cancelled'` | 无（只可能由该效果自己让出） | 该效果（`remove()` 走 `__del` 的让出） | 它**自己的** `apply()`：关掉执行体、这次生效结束 |
| `'wait'` | 要等什么（叶子效果自己定；内核不解释） | 叶子效果的 `Effect:suspend(请求)` | 原样上抛到最外层，由**驱动者**服务 |

取消**不需要转发**：`'cancelled'` 只可能由该效果自己让出，所以每个 `apply()` 只处理"载荷就是我自己"的那一个，别的原样上抛。未知理由 MUST 当场报错（免得有人偷 yield 却没人接）。

### D3 让出**原样上抛**，恢复打在最外层

`apply()` 的驱动循环做成**透明转发**：子执行体让出什么（理由 + 载荷）就由 `apply()` 原样交给调用方，并把调用方恢复时给的值原样送进子执行体。

- 于是内层的等待会**一路冒到最外层**；**恢复必须打在最外层的那个执行体上**，值再逐层下传回等待点 —— 这就是"调用点看起来像同步函数"的全部秘密。
- **为什么不用 `moe.await.yield` / `await.sleep` 做等待**：它们把"恢复"绑在**当前**协程上（`coroutine.running()`）。在嵌套的效果协程里用，恢复会打在内层协程上 —— 内层跑完就结束了，外层仍停在转发那一行，整条链再也回不来（**搁浅**）。所以等待只能在**最外层**（驱动者）做。**这条写进 `code-style.md`。**

### D4 效果即任务：完成信号 + `apply` / `wait` 分开（用户 2026-09-20 定）

效果有**完成信号**，两个入口职责分开：

| 入口 | 职责 |
| --- | --- |
| `:apply()` | 驱动这次结算（需要等外部输入时把调用链一起让出），返回效果自己 |
| `:wait()` | **等它结完**并返回**效果自己**；已经结完就立刻返回（幂等，不重跑） |

- 完成状态：`settle()` 跑完 = 完成（可以有结果）；`remove()` / 超时 = 完成但没有结果；出错 = 失败。结果与失败记在效果的 `result` / `err` 字段上。
- **用牌 / 造成伤害这类入口自动「驱动 + 等」并返回效果实例**（`game:damage(...):wait()` 写法等价于直接调入口）—— 用户原话「调用 damage 的那方必须要等」；这也是结算栈的要求：栈是一条先进的链，同一时刻 MUST NOT 有两个在飞的结算。
- **取消与超时不算失败**：以「没有结果」完成（`result` 与 `err` 都为空、不抛）；**内核错误照旧抛**（同时记进 `err`）—— 与「错误的传播」那条规格一致。
- **叶子效果的挂起点**：需要外部输入的那个效果用 `Effect:suspend(请求)` 让出（载荷内容内核不解释），外部把结果送回来。于是「要一个决策」= 造一个效果（将来的 `Ask`）再等它 —— `wait` 本身不需要载荷。
- **否掉**（用户原始方案的初版、也是我一开始写的）：把「等外部输入」做成一个带不透明请求对象的通用原语（`wait(请求)`）—— 那不是**效果**这一层的概念；等待的对象应当就是**一次结算**（它自己的完成）。

### D5 驱动者：本批只做测试侧

「驱动者」= 最外层的执行者，负责建流程协程、驱动它、服务它的让出（伪代码）：

```lua
---@async
function driver.run(fn, service)
    local co = coroutine.create(fn)
    local args = {}
    while true do
        local result = table.pack(coroutine.resume(co, table.unpack(args, 1, args.n)))
        if not result[1] then error(debug.traceback(co, result[2]), 0) end
        if coroutine.status(co) == 'dead' then return table.unpack(result, 2, result.n) end
        args = { service(result[2], result[3]) }   -- 按理由 + 载荷服务，返回下次 resume 要送的值
    end
end
```

- **服务函数跑在驱动者所在的协程里**（也就是最外层），所以它**可以自由等待**：测试里"1 秒后才给结果"就是服务函数里 `moe.await.sleep(1)` 或等一个定时器 —— 有假等待器就瞬间过去。
- 本批只实现**测试侧的驱动者**（测试辅助），生产侧的（会话）不做（Non-Goals）。
- 服务函数返回什么，就原样成为叶子里 `self:suspend(...)` 的返回值；返回 `nil` 就是"没有结果"，由调用方自己按 `nil` 处理（内核不额外造语义）。

### D6 挂起期间禁止起新结算

局上记住**当前挂起的那一个位置**，`game:play` / `game:damage` / `game:ask` 在挂起期间 MUST 明确失败。

- 理由：挂起时这次效果仍在栈顶，新结算会嵌在它下面；而且"游戏正挂着一件事"将来是会话要读的状态，明确失败比静默错序好。
- **否掉**：排队等结果后再跑（要引入队列与顺序语义）。

### D7 挂起态取消要连带收掉它下面挂着的子结算

取消一个**挂起中**的效果时，它下面可能还挂着子结算（子执行体停在自己的让出点，而它的驱动点正停在父执行体的转发那一行）。只关父执行体会让子执行体变成孤儿。

- 做法：沿**结算栈**自顶向下（从栈顶到该效果）依次关闭；栈本来就告诉我们"谁嵌在谁里面"。
- 用例要钉住：取消一个"正在等结果、且自己底下还挂着一次结算"的效果 ⇒ 结算栈回到这次结算之前的样子、不留孤儿。

### D8 事件循环接入点（测试侧）：**不**注入假等待器

- 内核**不主动驱动**事件循环：挂起只是把让出交上去，由最外层服务。
- 原计划照 4.0.0 给测试注入**假等待器**（推进虚拟时间），**实施时否掉**：① `add-async-io` 那批已经**特意删掉**测试里的虚拟时间兑底（见 `openspec/changes/archive/2026-09-19-add-async-io/design.md`：那是为了掩盖忙等而"提前"触发定时器），② `server/test/async/idle.lua` 用 `moe.timer.clock()`（虚拟时钟）断言真实延迟，注入假等待器会动到它。
- 结论：**挂起与时间无关**（它是控制流）—— 测试里模拟"稍后"只需让出一次循环 tick（`moe.await.sleep(0)`）或毫秒级真实等待，等待类用例本来就不必真等。将来真做超时（`Ask` 那层）时再按需定。
- **否掉**：内核里直接登记到 `eventLoop`（内核不该知道事件循环，测试也不好换）。

### D9 与既有代码的兼容

- `ask.lua` **不动**：`Ask` 照旧当场取答案，`--test core.response` / `rule.slash` 全绿。
- 【杀】等内容包不动：它们没调用 `wait`，`apply()` 不真挂起时行为与改动前一致。
- 唯一对内的影响：可挂起的入口标 `---@async`；`.luarc.json` 已把 `await` 组设为 `None`（全项目关掉 `await-in-sync`），所以**不会有诊断提醒**，靠文档与用例守着。

## Risks / Trade-offs

- [让出穿过不可让出的 C 边界]（`include`、`table.sort` 比较器、C 上的 metamethod）→ 真踩到会以 `attempt to yield across a C-call boundary` 立刻暴露，不会静默；写进代码风格约定。
- [某一层忘了转发 ⇒ 搁浅] → 转发只在 `apply()` 一处实现（同一条循环），不在各子类；用例覆盖"挂起时控制权确实交到调用方"与"值能穿过多层下传"。
- [在嵌套深度用 `await.*` 会搁浅] → `code-style.md` 写明：`await.*` 只给最外层（驱动者 / 服务函数）用。
- [挂起态取消留下孤儿子结算] → D7 的"沿结算栈往下关" + 专门用例。
- [迟到输入]（结算已结束 / 已取消之后服务函数才把值送回来）→ 服务函数是同步返回值的形状（等待在它内部完成），所以不存在"迟到"；将来真接外部输入时（会话批次）要再定。
- [漏标 `---@async` 没有诊断提醒] → 文档 + 用例覆盖。
- [有人绕过驱动点直接 resume 执行体] → 错误传播与取消会一起失效；写进代码风格约定（这条已存在）。

## Migration Plan

三步（见 tasks.md）：① 内核（转发循环 + `wait` + 挂起登记与禁止新结算 + 挂起态取消的子链处理）；② 测试侧驱动者与假等待器；③ 用例与文档。旧行为在"不挂起"路径下完全不变（`Ask` 与内容包零改动），不需要数据迁移；改动集中在 `effect.lua` / `game.lua` + 测试设施，回滚面小。

## Open Questions

- **OQ1（用户在想）**：`Ask` 的挂起语义 —— 答案从哪来、时限与超时怎么定、回答者形状、答复的入口。本批只把机制准备好，等这套定了再另开变更长上去。
- **OQ2（属于会话接线批次）**：生产侧驱动者长什么样（怎么把请求报给前端、怎么把结果送回来）。
- **OQ3（可延后）**：除 `'cancelled'` / `'wait'` 之外的让出理由要不要，本批不预留。
