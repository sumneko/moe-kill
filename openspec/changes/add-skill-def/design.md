# Design

## 两个正交维度（底本依据）

底本说得比传闻清楚：

> 技能按照**是否有发动时机**这个要素可分为**状态类技能（没有发动时机这个要素）**和**触发类技能（有发动时机这个要素）**。 —— `Chapter1/Section2.md`

> 触发类技能于发动时机若能发动**是否必须发动，与此技能是否带有"锁定技"标签无关，关键是要找是否有"可"这个字**。 —— `Chapter1/Section2.md`（专题一按语，共四条）

> "锁定技"……时至今日，"锁定技"跟什么时候发动没关系（这个由发动的时机决定）……**它其实已经成为了一个标签，专供封印不带此标签的技能用**。 —— `Chapter2/Section5.md`

所以两个维度分开：

| 维度 | 字段 | 干什么 |
| --- | --- | --- |
| 发动方式 | `SkillDef:getKind()`（字段私有 `kindName`） | `'主动'` / `'被动'` / `'自动'` —— **只影响「这个技能能不能被主动点」**（用户口径：按钮能不能点；被动技能能点也没问题） |
| 标签 | `SkillDef` 的标签集合 | `'锁定技'` / `'限定技'` / `'觉醒技'` / `'主公技'` —— 纯数据，各自被对应机制读（锁定技 = 不被克制；限定技 = 一局一次；觉醒技 = 附带另两个；主公技 = 只给主公、但「获得」也算拥有） |

**「自动」的含义**：有时机、但不问「要不要发动」，直接做（= 描述里没有「可」字的触发类技能）。**官方「状态类技能」本批不单开第四类** —— 等做生效机制时若需要再加取值（`kind` 只是数据，加值不动内核）；**类型漏写一律当「主动」**（用户定）。

## 标签为什么是集合

四个标签在底本里是同类东西（`Chapter2/Section5.md` 整节就是「标签」的集合），将来还会加（国战标签、UI 标签）⇒ 用一个集合 + `hasTag(名字)`，加标签不用动内核。**没有为「主公技」单开布尔字段**：读法就是 `skill:hasTag('主公技')`。

- `: tags { '锁定技', '主公技' }` 可多次调、**取并集**（与 `HeroDef:skills` 的一次性赋值不同 —— 标签天然可累加）。
- **「觉醒技」派生**：`hasTag('锁定技')` 与 `hasTag('限定技')` 对只声明了「觉醒技」的技能也返回真（底本：「带有此标签的技能**视为附带**」）。派生放在读法里，`getTags()` 仍忠实返回声明过的那几个。

## 字段与方法不同名

链式声明方法叫 `: kind '被动'`，字段就不能也叫 `kind` —— 否则 `self.kind = kind` 会把字段推成 `function|'主动'|…`（第一次跑就报错）。照 `HeroDef`（字段 `kingdomName` + 方法 `kingdom` + 读法 `getKingdom()`）的先例：**字段私有 `kindName` + 链式方法 `kind` + 读法 `getKind()`**。同一原则用在标签上：字段 `tagSet`、方法 `tags()`、读法 `hasTag()` / `getTags()`。

## 默认值为什么由内核给

「不写就是主动」是一个**固定默认值**（不涉及规则数值，不像 `默认体力` 那样可被别的包覆盖）⇒ 放在 `SkillDef:__init` 里最省事，读的地方（将来的协议层）永远拿得到 `skill:getKind()`。

代价：内核里出现了 `'主动'` 这个中文取值。可接受 —— 它是**默认值**，不是内核的判断分支（内核不根据 `kind` 做任何取舍，`hasTag` 同理）。

## 与既有定义类的分工

- `CardDef`：牌面 + 钩子（`: on(...)`）。
- `BuffDef`：`'获得'` / `'失去'` 两个钩子。
- `HeroDef`：武将牌面（技能名只是数据）。
- **`SkillDef`（本批）**：名字 / 发动方式 / 标签 —— **本批不含任何钩子**。生效机制（订阅时机、主动发动的入口、`addSkill` 挂载、主公技过滤）是后面几批。

## 本批不做

- **不做生效机制**：没有 `: on(...)`、没有 `player:addSkill`、没有「主动技怎么被发动」的入口。
- **不写标准包的技能**：`package/标准/武将/*.lua` 一行不动 —— 技能文本没有底本（入库规则集只到 Chapter2），要另找来源并经用户过目；本批用探针包测定义本身。
