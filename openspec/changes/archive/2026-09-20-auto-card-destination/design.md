# Design

## Context

- 挪牌目前是 `game:moveCard(card, zone)` 里**逐张** `Zone:move` 的同步函数（区名可给一串 = 依次经过）；失败直接 `error`。
- 询问目前是 `game:askCard(to, question)`：`AskCard:settle()` 触发 `'卡牌-询问'`，应答方 `ask:answer(牌)`，结果读 `.result`；**没有任何参数说明"这次要牌是干什么用的"**。
- 基础规则（`package/@基础/牌堆.lua`）已经在管「打出的牌」的去向（订阅 `'卡牌-打出后'` 放进 `弃牌`），而【闪】的响应又要内容包自己 `game:moveCard(card, { '处理', '弃牌' })` ⇒ **同一张牌被挪两次**。
- `openspec/specs/core-response/spec.md` 还停在旧模型（外部注入的"回答者"、"拿不出答案 ⇒ 明确失败"），与现状相反。
- 效果基础设施已就位：`Effect`（协程 + 任务 + `.result` / `.err`、「即将生效」可取消）、`Damage` / `UseCard` / `AskCard` 三个子类可供照抄。

## Goals / Non-Goals

- **目标**：让"这张牌之后去哪儿"由**规则层按缘由**决定，内容包只表达"我要什么牌、为什么"；挪牌成为一等效果（一次结算挪一批、可挂时机、可取消）。
- **非目标（design 层面）**：处理区的**停留点**（见 D6）；「移动前 / 后」类专有时机；`reason` 的取值枚举与校验；把 `core-effect` 的过期段落一并同步（见 D7）。

## Decisions

### D1 挪牌提成效果，一次结算挪一批

新增 `server/core/move-card.lua`：`MoveCard : Effect`（`kind` = `moveCard`），字段 `cards: Card[]` 与 `zones: string[]`（区名保持**名字**，不预先解析成区对象 —— 与调用方看到的一致）。`settle()` 里：先解析全部区名（有一个不属于这一局就报错）→ 再校验每张牌都有归属 → 才沿路径逐站移动。**整批校验在改状态之前**，与前一批定的原子性口径一致。

否掉的方案：继续用同步函数 + 调用方自己 batch（那就没有结算、挂不了时机、取消不了，也没法自然地"一次挪一批"）；把 `Zone:move` 也改成效果（`Zone` 是最底层容器，效果是"游戏动作"这一层的概念，塞进去会把内核切成两半）。

### D2 `game:moveCard` 降格为便利入口

`game:moveCard(card, zone)` = 造 `MoveCard` + `:apply():await()`，返回效果实例（与 `game:damage` / `game:useCard` / `game:askCard` 完全一致），并标 `---@async`。**BREAKING（对内）**：失败不再抛出，改记在 `.err`（调用方读效果）。门面新增 `moe.moveCard`（`MoveCard.API`）。

### D3 `reason` 是第 2 个参数，且内核不解释

`game:askCard(被问者, reason, 要什么牌)`（用户 2026-09-20 定）。`AskCard` 带 `reason` 字段；内核**只转交**，MUST NOT 解释取值（与时机名同一口径：名字由内容侧约定，内核不认识）。于是"打出一张闪"与"交出一张牌"的区别由**规则层**解释，内核不需要新增语义。

### D4 用「卡牌-答复」时机把答复交给规则层

询问结束后局触发 **`'卡牌-答复'`**（与 `'卡牌-询问'` 对称；分类是「卡牌」），上下文 = 这次询问实例（`to` / `reason` / 结果）。规则层据此决定"这次答复意味着做了什么"。

否掉的方案：内核里判 `reason == '打出'` 就自动响应（把一条内容约定写死进内核；将来 `'使用'` / `'弃置'` 等缘由都会堆进来）；把 `reason` 塞进 `'卡牌-打出后'` 的上下文（打出这个动作本身跟缘由无关，且"没有打出"的答复也会触发）。

### D5 「打出」用询问实例上的 `:respond()`，去向只留一处

基础规则在 `'卡牌-答复'` 里：`reason == '打出'` 且给出了牌 ⇒ 调 **`ctx:respond()`**（用户 2026-09-20 定：不是 `game:respond(to, card)`）—— 它就是"把这次答复当作一次打出"：取出那张牌 + 触发 `'卡牌-打出后'`；**去向**留在 `'卡牌-打出后'` 的订阅里（`game:moveCard(ctx.card, { '处理', '弃牌' })`）。这样"谁来决定去向"只有一处答案（基础规则），内容包与应答方都不写 `moveCard`。

`game:respond(角色, 牌)` 仍是那个与「使用」并列的动作本身（`AskCard:respond()` 转调它）；`AskCard:respond()` 只是把它收成"这次询问的答复"这一形状 —— 调用方不必自己把被问者与结果拆开再拼回去。**没给出牌时它是空操作**（返回 `false`）："没答上"是正常情况（没人应答也会触发答复时机），不该把它当失败 —— 与「没答上不算失败」同一条口径。

### D6 处理区这一次"一次走完"，不留停留

打出的牌在**一次挪牌效果**里走完「`处理` → `弃牌`」。现在没有任何"看得见处理区"的消费者，留一个中间停留点只会变成没人观察的中间状态；真出现这类牌或技能时，再引入"某次结算结束时进弃牌"的时机（那时才需要决定"这次结算"是谁的结算）。**待定项保留**：处理区的停留粒度。

### D7 顺带同步 `core-response`，但**不动** `core-effect`

`core-response` 与本次改动直接相关（`askCard` 签名、答复后时机），顺手把过期的两条（「询问」「回答者」）按新模型重写。

`core-effect` 也过期（正文还写着 `game:pushEffect` 结算栈与"错误照常向外传播"，与现状的"只增记牌器 + 失败记 `.err`"不符），但那与本次无关，改动面也大 —— **另开一次同步**，不在本变更里混做。

## Risks / Trade-offs

- [内容包忘了读 `.err` ⇒ 挪牌失败被无声忽略] → 失败仍会进统一错误报告（测试记账 / 服务模式记日志），不是完全静默；用例钉住失败路径。
- [基础规则在 `'卡牌-答复'` 里调 `ctx:respond()`，而应答方给的牌不在自己手上] → `respond` 明确报错，错误被时机机制隔离并记日志（属调用方失误，不吞掉）；用例覆盖。
- [`reason` 没有枚举 ⇒ 拼错就"不接管"] → 与时机名同一口径（不预设、不校验）；基础规则只认「打出」，其余缘由一律不动牌。
- [挪牌从"抛错"变"记 `.err`"，调用方可能没改] → 全量用例（`test/core/game.lua`、`test/rule/slash.lua`）会当场红，属可发现的破坏。

## Migration Plan

- 调用点：`package/标准/卡牌/杀.lua`（删 `moveCard`、询问加 `'打出'`）、`package/@基础/牌堆.lua`（订阅答复时机、打出后走「处理 → 弃牌」）。
- 测试：`server/test/core/game.lua`（挪牌失败改用 `lt.assertFailed`）、`server/test/core/ask-card.lua` 与 `server/test/rule/{slash,support}.lua`（询问加缘由）。
- 回滚：`git revert` 这几笔即可（纯内存态，没有要迁移的数据）。

## Open Questions

- 处理区的**停留点**：什么时候从 `处理` 进 `弃牌`（该牌自己的响应结束 / 那一次生效结束）—— 有消费者时再定。
- `reason` 的取值要不要枚举要不要枚举进 `env-meta.lua`（拼错在编辑期就报）—— 用户 2026-09-20 定：**先不写**，等缘由多起来再定。
- 「移动前 / 后」这类专有时机 —— 有技能需要时再加。
