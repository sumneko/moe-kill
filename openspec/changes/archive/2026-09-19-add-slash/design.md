# Design

## Context

动机见 `proposal.md`。与本设计相关的现状：

- 内核对「牌」只有薄模型：牌实例只带唯一标识与不透明标签（`game:createCard(名字)` 把牌名写进标签），牌区只管进出与顺序，内核**不知道**牌在哪个牌区、也不知道任何区域名。
- 牌的内容定义（`Moe.CardDef`）已经支持链式登记回调（`Card '名字' :on(事件, 回调)`）与快照读取，但**还没有任何机制会去调用它们**。
- 时机系统只对「局」开放（`game:on` / `game:fire`），时机名不预设；事件的上下文按约定"只装该时机的参数"，环境对象不进上下文（内容侧的闭包直接捕获加载期的 `game`）。
- 属性是唯一被设计成"可被效果修正"的数值载体（`define` 只能在加载期，写入即分发通知）。

## Goals / Non-Goals

**Goals:**

- 让「一张牌用出去 → 产生后果」这条链路第一次跑通，且**规则全部在内容侧**，内核只给流程与时机。
- 把「伤害」做成一等机制（而不是散落在牌里的赋值），使将来所有效果共用同一条体力变更路径与同一组时机。
- 保持内核「不预设区域名 / 不含具体规则」的口径不被本批破坏。

**Non-Goals:**

- 回合与阶段、出牌次数限制（因此本批可无限次使用「杀」）。
- 「打出」与响应（闪）、结算栈、无懈可击。
- 濒死 / 死亡 / 奖惩 / 胜负。
- 装备（武器改范围、±1 马改距离、防具）。
- 判定、摸牌 / 弃牌流程、技能系统。

## Decisions

### D1 使用入口落点与形状：`game:play(使用者, 牌, 目标们)`

机制自己定位"牌从哪来"：遍历使用者名下的牌区找这张牌，取出后结算。调用方只描述意图，不必知道区域名。

**为什么**：内核必须保持零区域名（见 `core-game` 的口径）；而"取牌 → 校验 → 结算 → 去向"是纯机制，放在内核才能被所有牌复用。

**备选与否掉的理由**：

- 调用方显式给出来源牌区 —— 更显式，但把「手牌」这类内容概念塞进通用接口，且第一阶段就要求调用方知道牌在哪。
- 由规则包自己实现使用流程 —— 内核没有"使用"这个概念，后续的响应、技能、协议层都无处挂；且每张牌都要重写一遍取牌与去向。
- 让测试自己组合内核接口（`take` + 直接调回调）—— 能跑但没有可复用的机制，也没有可测的"使用"语义。

**已知代价**：牌不在该玩家手上时，报错只能说"不在该玩家名下任何牌区里"，指不出具体区。

### D2 目标合法性由牌声明（内容侧事件名 `'目标合法'`）

机制在每个目标上调用该牌的 `'目标合法'` 回调，返回 `false` 视为不合法（其它返回值视为通过），不合法则使用失败、牌留在原处。

**为什么**：合法性是"这张牌的规则"——「杀」看距离与攻击范围，将来的「顺手牵羊」看距离 1、「桃」看体力未满。内核不该知道其中任何一种。

**备选**：内核内置"距离 ≤ 攻击范围"（内核含具体规则，越界）；由协议 / 前端过滤目标（把规则权威交给了前端，与"后端权威、前端无状态"冲突，且无头测试会绕过）。

### D3 结算执行与牌的去向

机制按声明顺序执行牌定义的 `'使用'` 回调，然后触发收尾时机 `'卡牌-结算后'`（上下文 `{ user, card, targets }`）。牌的去向由内容侧订阅者决定 —— 基础规则把它放进 `弃牌堆`。

**为什么**：内核不知道"弃牌堆"叫什么；把"用掉的牌去哪"集中写在基础规则一处，避免每张牌各写一遍、也避免漏写。

**备选**：内核直接把牌搬进"弃牌堆"（预设区域名）；每张牌的 `'使用'` 回调自己收尾（重复且容易漏）。

**语义界定**：本批 `'卡牌-结算后'` = "这张牌的使用结算完毕"。下一批引入「闪」的响应后语义不变（被抵消也属于结算完毕），因此兼容。

### D4 伤害入口的形状：`game:damage(来源, 目标, 点数)`

`game:fire('伤害-前', ctx)` → 目标的 `体力` 减点数 → `game:fire('伤害-后', ctx)`，`ctx = { from, to, amount }`。

**为什么**：伤害是**两个角色之间的关系**（来源与目标），挂在局上中性；写成 `player:damage(来源, 点数)` 会让来源是参数、目标是 self，关系不对称。伤害时机在本批就把名字与形状固定下来，将来的属性伤害 / 伤害值修改 / 伤害防止都从这两个时机接入，机制本身不用改。

**备选**：把伤害写进属性系统（属性库只做数值与通知，不该有"伤害"这种游戏语义）。

**本批不含**：属性伤害、伤害值修改、伤害防止、濒死插入。

### D5 攻击范围用属性，定义与初值放 `package/@基础/攻击范围.lua`

`define('攻击范围', { min = 0, max = 999999, simple = true })` 写在文件顶层（必须在属性库编译前，即加载期），开局在「游戏-开始」里给每个玩家写 1。

**为什么**：属性可被后续效果 `add` 修正（武器、武将、技能）而**调用形状不变**。写成玩家上的普通字段的话，将来装备需要另造一套修正路径。

**备选**：直接写 `player.攻击范围 = 1` 字段（不可修正、且绕过属性机制）。

### D6 手牌与弃牌堆：本批只建区、不做摸牌

基础规则在「游戏-开始」建局上的 `弃牌堆`，并给每个玩家建 `手牌`；本批**不做摸牌**，牌由调用方（测试）从抽牌堆 `move` 进手牌。

**为什么**：使用入口需要"牌在手上"这个前提，但不做阶段就不该顺手把摸牌 / 发牌流程做完 —— 那属于上层的回合流程。

**备选**：连摸牌一起做（提前引入"摸牌"这个流程概念，做回合流程时又要改口径）。

### D7 命名与类型面

- 时机名（`game:on` / `game:fire`，沿用 `分类-动作`）：`'卡牌-结算后'`、`'伤害-前'`、`'伤害-后'`。
- 内容侧事件名（`Card:on`）：`'目标合法'`、`'使用'`。
- 类型面：`server/core/loader/env-meta.lua` 补这三个时机的上下文类型（`Moe.Game.EventCtx.*`）与 `game:on` / `game:fire` 的按名收窄重载；`Card:on` 保持通用 `(事件名: string, 回调: function)`，不按牌名分支。

### D8 测试策略

- 内核侧：`server/test/core/play.lua` / `server/test/core/damage.lua` 用独立建的局 + 探针内容包（`moe.loader.install` 加载探针目录），不依赖 `@基础` / `标准`。
- 规则侧：`server/test/rule/slash.lua` 用既有的 `support.start` 建局（含 `@基础` / `身份场` / `标准`），从 `抽牌堆` 摸一张「杀」进手牌、调 `game:play`，断言目标体力与 `弃牌堆`。

## Risks / Trade-offs

- [机制用"遍历使用者牌区找牌"定位来源区，玩家牌区变多时是线性扫描] → 每个玩家的牌区数量很少（手牌 / 装备 / 判定），不做索引优化。
- [伤害不处理体力归零，会出现负体力角色并继续参与] → 本批 Non-goal 且有用例钉住"允许为负、无死亡"；濒死 / 死亡在下一批接管时替换伤害的收尾路径。
- [收尾时机若内容侧没订阅，牌会悬空（不属于任何牌区）] → 明确约定：牌的最终去向由内容侧负责；本批 `@基础` 已订阅，测试钉住"用了的牌进弃牌堆"。
- [`攻击范围` 的默认值写在基础规则，将来武将 / 装备也想写它，会出现"谁覆盖谁"的问题] → 本批只有默认值；将来的装备 / 武将走 `add` 修正或写值时机，语义不冲突（默认值只是基数）。
- [没有阶段与次数限制 ⇒ 「杀」可以无限用] → 用户明确本批不做；边界写在 `proposal.md` 的 Non-goals，等做回合流程时补。
- [使用入口的接口形状（目标列表）将来要支持"多目标"与"响应"时可能不够] → 目标本来就是列表，多目标天然支持；响应属另一条路径（打出），不会挤进这个入口。

## Migration Plan

无破坏性变更：本批是纯新增（新接口、新属性、新区域名、一张新牌），不改动任何现有接口语义，不需要迁移。回退方式 = 不加载新增内容（`标准` 包不写「杀」时链路依然可用，只是没有牌会用到它）。

## Open Questions

- 要不要引入「处理区 / 结算区」（判定牌的停留点、被抵消的牌的中间停留点）—— 本批不做，等做判定或响应时再定。
- 使用前是否需要钩子（将来的无懈可击、技能改写目标）—— 留到引入响应时定；本批只保证"结算完毕"这个时机。
