# skill-auto-confirm

## D1 为什么按钮状态不声明、要推导

用户 2026-10-01：**按钮总是显示的**（它就是技能本身 —— 名字 + 悬浮描述），所以「有没有按钮」这种声明不存在；剩下要表达的只有「**现在能不能点**」，而它等价于「有没有主动发动的入口」⇒ 从 `SkillDef` 上有没有那个钩子推导即可。

本批不引入那个钩子（主动技整批还没做），所以**推导结果恒为「点不下去」**，与现状一致、没有损失。

## D2 开关是几态、默认哪一态

- **两态**（开 = 自动同意 / 关 = 每次问）。不做第三态「永不发动」：真不想发就每次都答「不发动」，多一态要多一套 UI 与协议语义。
- **不写 `auto(…)` = 关（每次问）**：安全默认，不擅自替玩家做决定。技能作者认为「大多数情况下都会发动」才写 `: auto(true)`（【奸雄】就是）。

## D3 `auto` 落在实例上、默认值落在定义上

- 定义层 `SkillDef:auto(值)` 是**链式声明**（与 `tags` / `on` 同款），值存在 `SkillDef.autoFire`（叫 `autoFire` 而不是 `auto`：类表上要放同名方法，实例字段一旦赋值就会遮蔽方法 ⇒ 名字必须分开，与 `kind` / `kindName` 同一处理）。
- `autoFire` 是 `---@field package`（同文件可见）：只有 `Skill:__init` 读它一次，**不对外开读法** —— 前端 / 测试读**实例**的 `auto` 就够（它已经从默认初始化过）。
- 实例上的 `Skill.auto` 是**公开可写字段**：切开关是玩家动作，不需要走方法。

## D4 `confirm()` 收口「问不问」

```lua
function S:confirm()
    if self.auto then
        return true
    end
    return self.game:askChoice(self.owner, self.name, { '发动' }).choice == '发动'
end
```

- 技能自己决定**在哪儿问**（有的技能要在多个点问，有的点不该问）⇒ `confirm()` 只提供「问一次」这一件事，不替技能决定调用位置。
- 询问的 `reason` 用**技能名**（`askChoice(owner, self.name, …)`）—— 与【奸雄】原先手写的 `'奸雄'` 一致。
- **强制发动的技能不调它**（锁定技那类自己直接做）—— 于是「锁定技」标签与「强制发动」保持正交。

## D5 否掉的方案

- **保留 `kind` 三值、另加 `auto`**：两个维度会打架（`kind '自动'` 与 `auto` 说的是同一件事），且按钮那半仍是会撒谎的声明。
- **`button(布尔)`**（有 / 没有按钮）：按钮总在，这个概念不存在。
- **`auto` 挂在 `Player` 上（一个总开关）**：现实里是按技能单独设的（哪个技能想自动、哪个想每次问）。
