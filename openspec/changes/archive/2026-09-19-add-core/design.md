# Design

## Context

用户确定的顺序与分界线：**先做内核（core）并单元测试，规则集与 session 都排在后面**；「目前的实现应该和游戏流程规则完全无关」。

追加口径（用户拍板）：

- **牌区是通用容器**，内核不写死是什么区域（手牌 / 装备 / 判定在 core 眼中没有区别）；具体功能差异（如可见性）做成**区域参数**并通过接口修改；支持**动态添加 / 删除 / 禁用**。
- **牌堆与区域合并成同一套抽象**（一个基类 + 参数 + 少数能力），手牌区 / 装备区 / 判定区 / 抽牌堆 / 弃牌堆 / 处理区都是它的实例。
- **接入 `sumneko/utility` 的 `attribute` 库**做通用属性；属性名与公式由调用方（将来的规则集）定义，内核不预设。
- 玩家叫 `Player`；房间不设人数上限。
- **规则集目录**：项目根 `game/`（中文包名，如 `game/基础规则/`、`game/卡牌包/标准/`），与 `server/` 平级；本批只记录约定，不创建目录、不实现规则。
- **对象模型（`Player` / `Desk` / `Room`）暂缓**（用户 2026-09-19 定）：不按任务清单顺序硬推，**做业务时按需再补**；本批先补“牌的移动”（`core-move`）。

现状：`server/core/` 只有一个空表（`---@class Core`）；已归档的 `headless-server`（`server/session/`）不动也不被依赖。

## Goals / Non-Goals

**Goals:**

- 内核对象可用**纯同步接口**驱动：测试建房间、调接口、断言对象状态，不需要会话、协议或协程。
- 内核与规则彻底分离：没有具体区域名、没有具体属性名、没有"张数 / 顺序 / 时机"默认值。
- 牌区、属性、随机源三者都可注入、可组合、可单测。

**Non-Goals:**

- 开局装配（身份 / 起手牌数 / 发牌 / 先手）、回合阶段推进、牌的效果与结算、技能、规则集内容。
- 决策者接口：内核没有流程，本批没有消费者，留到规则批次。
- 会话外壳、协议、网络、前端；身份信息隔离（属对外可见性，留协议层）。
- 牌的定义（名称 / 花色 / 点数 / 效果）——属配置，后续批次。

## Decisions

### D1 落点与门面

- `script/` → `server/`（后端代码根，与将来的 `client/` 对称）；`engine/` → `core/`（`---@class Engine` → `---@class Core`），门面 `moe.core`。
- 会话外壳目录随之从 `server/server/` 改名为 `server/session/`（避免同名嵌套），门面仍是 `moe.server`。
- **规则集放项目根 `game/`**，与 `server/` 平级：`game/` 是"内容/包"，`server/` 是"后端代码根"（引导、内核、会话、工具）。依赖方向只能是 `game/ → server/core`，内核永不反向依赖 `game`。
  - **本批不创建该目录**（用户 2026-09-19 定）：约定先写在这里与技能文档，目录本体、`package.path`（`game/?.lua`、`game/?/init.lua`）与加载方式等后续批次测到规则集时再落地。
- 入口与产物也归 `server/`（用户 2026-09-19 定）：`server/main.lua`、`server/test.lua`、`server/test/`、`server/bin/`（构建产物）、`server/log/`、`server/tmp/`。**`server/master.lua` 的 `ROOT_PATH` = `<根>/server`**（日志、临时产物、测试入口都在 `server/` 下自洽）；`bin/` 是 `lm:copy` 指定的分发目录（luamake 自己的中间产物在 `build/bin`），所以可以自由选定位置。前端将来 `client/` 有自己的入口，不必与后端入口同构。

### D2 内核与规则的分界线（本批最重要的约束）

判断标准：**出现"具体区域名 / 具体属性名 / 张数 / 顺序 / 时机"这类规则内容，就越界了**。

- 内核提供：通用容器与访问器（牌区放入取出、属性读写、座位距离求值）。
- 规则集将来提供：`发一手牌`、`开局`、`进入下一阶段`、`结算某张牌`、`主公体力上限 +1` 这类**组合动作与默认值**。
- 测试场景由测试**自己组合内核接口**搭出来（连续取牌 + 放入牌区即"发牌"），这同时验证内核没有夹带规则。

### D3 牌区：一个基类 + 参数 + 能力标记

- 基类 `Zone`：放入 / 取出 / 查看 / 计数 / 列举 / 清空；对空区取牌等非法操作**明确失败**。
- **区域参数**：不透明键值（如可见性、归属），内核只保存与读取，不解释含义。
- **动态增删禁用**：玩家持有一组牌区，可添加 / 删除 / 禁用 / 启用；被禁用的牌区不出现在默认列举中，对其操作明确失败。
- **有序能力用子类表达**（用户定）：基类 `Zone` 不带取顶/洗牌；子类（如 `OrderedZone`）声明"有序"能力；**具体子类实例由 game 层创建**（内核不预设任何具体牌区，连"抽牌堆"都不建）。
- 手牌区 / 装备区 / 判定区 / 抽牌堆 / 弃牌堆 / 处理区**都是它的实例**，名字与用途由调用方决定。

补充口径（用户 2026-09-19 定，轮次③ 实施）：

- **顺序口径**：有序牌区的列表顺序 = **从顶到底**（下标 1 是顶）；`put` 追加到底部，`takeTop` 取下标 1，`shuffle` 重排整条列表 —— 故“洗牌后依次取顶”得到的正是洗牌结果的顺序。
- **能力检测与失败方式**：基类保留同名方法 `takeTop` / `shuffle`，调用即报“不具备有序能力”；能力本身仍由子类判定（`Core.OrderedZone`）—— 比调用不存在的方法（`attempt to call a nil value`）能说清原因。
- **运行时不做类型判定**（用户 2026-09-19 定；先按 `kind` 试了家族判定，随后修正）："是牌还是牌区"这类**同一家族内部**的区分由**类型注解**保证，不写运行时断言（不用 `Type` / `isInstanceOf`）。`kind` **只用于区分子类**：基类在自己的 `__init` 里给默认值（`Core.Zone` → `'zone'`），子类覆盖成自己的名字（`Core.OrderedZone` → `'orderedZone'`；规则层子类可设 `'手牌'` 之类），调用方按需读它判断。字段类型声明写开放的 `string`，内核不维护 kinds 清单。
- **禁用边界**：禁用只挡“牌的进出”（`put` / `take` / `clear` / `shuffle`）；读取（`count` / `list` / `peek`）与参数读写不受限；“不出现在默认列举中”由持有牌区的集合（轮次⑤ 的 `Player`）负责过滤。
- **落地位置**：`Core.Zone` 在 `server/core/zone.lua`，`Core.OrderedZone` 在 `server/core/ordered-zone.lua`（后者 `Extends` 前者）。

### D4 属性：接入 `attribute` 库，内核不预设属性名

- 照搬 `sumneko/utility` 的 `attribute.lua` 到 `server/tools/attribute.lua`（照搬区，**不要随便改**），并在 `moe-kill-dev` 技能的 `tools/` 清单里登记来源与版本（该文件在 LuaLS 4.0.0 里没有，属通用能力库上游）。
- 内核只做**接入**：属性系统**挂在房间上** —— 由调用方通过 `room:setPlayerAttributeSystem(system)` 设置，之后房间创建玩家时用该系统创建属性实例（用户定：不在玩家构造参数上传递）。
- 因此"体力 / 体力上限"**不在内核里**：它们是规则集声明的属性名。
- 备选与取舍：自己写一套属性系统——否决，`attribute` 已提供上下限、公式、惰性重算与变更事件，且是本项目工具的既定来源。

轮次④ 落地口径：

- 接入层 `server/core/attribute.lua`：`Core.AttributeSystem`（`create` / `define(name, spec)` / `createInstance`，`spec = { simple?, min?, max? }`，`simple` 默认 `true` 走简易属性路径）与实例包装 `Core.Attributes`（`get` / `getMin` / `getMax` / `set` / `add` / `onChange`）。
- **写入后就地分发通知**（用户 2026-09-19 定）：库把变更攒在 dirty 集合里，包装层在每次 `set` / `add` 之后立即调 `system:updateEvent()`，所以订阅者在写入的同一调用栈里就收到回调，调用方不需要（也不用）自己 flush；回调里再改属性同样会被分发（库的 `updateEvent` 先快照再清空，支持嵌套）。
- 订阅：`attrs:onChange(name, callback)`（对应库的 `Instance:event`），返回**取消订阅函数**。
- **未写入过的属性读数为 0**，下限只在写入时钳制 —— 规则层建立玩家时要自己初始化（如把“攻击距离”显式设为 1）。
- **本轮不暴露**：公式 / 复杂属性（`setFormula` / `setBaseSymbol` / 字符串型 `min`-`max` 引用）与“查询自上次检查以来的变化”（库的 `getTouched`，返回的是变化**前**的取值）—— 等规则层真需要百分比修正 / 批量差分时再一起过语义，避免现在猜错库里的生成语义。

### D5 桌子：座位与行动顺序，距离是求值
- **代码里叫 `Desk`**（`Core.Desk` / `server/core/desk.lua` / `moe.core.desk`）：`Table` 会与 Lua 的全局 `table` 混，`Desk` 与中文“桌子”也对得上（用户 2026-09-19 定）。- 座位序号 = 入座顺序；行动顺序遍历跳过"不参与行动"的玩家（规则层把"阵亡"映射为该标记）。
- 座位距离 = `min(顺时针, 逆时针)`，最小 1；修正值由调用方设置，修正后仍最小 1；距离是**求值函数**不是缓存字段（装备/技能变化必须立即反映）。

### D6 随机源：自带可实例化实现

不使用全局 `math.random` 状态（多房间互相干扰、也不便复现）。内核自带按 seed 构造的随机源，由有序牌区的洗牌消费它；房间持有自己的实例。

实现口径（用户 2026-09-19 定）与取舍：

- 算法照 `lmathlib.c` 的 **xoshiro256\*\***；种子经 **splitmix64** 扩散成 4 个 64 位状态字 —— 相邻种子状态充分分离，且 4 个字不可能同时为 0（mix64 是双射）。
- **不采用「`math.random` + 每次调用前重设种子」**：`math.randomseed(n1, n2)` 只吃两个整数，而状态是 4×64 位且播种要丢弃 16 轮 —— 状态无法还原（实例独立性无从谈起），单次播种成本还高于取一个数；相近种子会产出相关状态。
- **开销实测可忽略**（`server/bin/moe-kill.exe`，Lua 5.5；100 万次取值 / 1 万次洗牌）：取值自实现 108 ms、`math.random` 25 ms；**洗一次 108 张牌堆 13.2 微秒**（`math.random` 3.7 微秒）。一局游戏洗几次牌，量级为几十微秒，故不为此牺牲确定性。
- 收益：实例独立（多房间 / 多测试不互相消耗）、随机源可注入（测试注入固定种子即可断言确定顺序）、算法与 Lua 版本解耦、状态可序列化（将来回放）。
- 接口：`create(seed)` / `nextInt(min, max)`（闭区间、无偏拒绝采样）/ `pick(list)` / `shuffle(list)`（就地 Fisher–Yates）；**不提供重设种子**，避免退化成共享全局状态。

### D7 命名与目录

- 代码标识符用英文（`Core` / `Room` / `Player` / `Desk` / `Zone` / `Card` / `Random`）；规则集目录用中文（`game/基础规则/`）。
- 内核在 `moe.core` 下扁平挂载（`moe.core.room` / `player` / `desk` / `zone` / `orderedZone` / `card` / `random` / `attribute`）。

### D8 牌的移动：原子、薄模型、位置即下标

用户 2026-09-19 定的口径（方案选择见下）：

- 操作落在**源牌区**上：`from:move(card, to, position?)` —— 返回被移动的那张牌（与 `put` / `take` 一致）。
- **原子**：源区必须持有该牌、两端都必须启用、目标位置必须合法 —— 三项都在改状态**之前**校验；任一不通过即报错，两边的计数与顺序都不变。
- **位置是整数下标**：`1` = 顶（插到最前）、`-1` = 底（追加），省略视同底部；其余整数按「从顶部数」或「从底部数」解释（`-k` 即倒数第 k 位）；越界明确失败。位置只影响排列顺序，所以**无序牌区同样接受**位置参数。
- **薄模型（方案 1）**：内核**不记录**"某张牌在哪个牌区"，也不做归属校验 —— `put` / `take` 语义保持不变；将来若真需要"牌不会分身"的不变量，再加厚成方案 2（`Card` 记归属、`put` 受约束）。
- **同区移动 = 重排**（先移除、再按位置插回），顺带覆盖"移到顶部 / 底部"这类整理动作。
- **不产生事件与记录**（用户 2026-09-19 定：事件与记牌器晚点再做）—— 移动只改变牌区状态。

## Risks / Trade-offs

- **[内核被规则污染]** → D2 的可执行判断标准 + 测试里"自己组合接口发牌"的用例。
- **[统一容器后概念过多]** → 牌区只有"参数 + 一个有序能力"两处变量，其余行为共用；不引入继承树深层结构。
- **[照搬 `attribute` 与上游分叉]** → 保持原样照搬，不改；如需改动先问用户，并在 `tools/` 清单登记。
- **[`game/` 中文路径]** → 已实测项目支持 UTF-8 路径（构建产物路径含中文亦可运行）；`require` 走 `package.path`，不依赖文件名 ASCII。
- **[牌实例过于简陋，将来要改]** → 只承诺"唯一标识 + 标签"，牌定义批次再扩展（加字段，不改语义）。

## 交付方式

**增量交付**（用户 2026-09-19 要求）：**一个功能点做完就与用户对齐一次**，不要一口气把整批做完。实际轮次：① 改名 core + 照搬 attribute → ② `core-random` → ③ `core-zones` → ④ `core-attributes` → ⑤ `core-move`（牌的移动，用户临时插入并置前）→ 之后 `core-objects` 按需补 → 收尾文档与验收。每轮都跑测试、清问题面板后再汇报。

## Migration Plan

改名 + 纯新增：`script/` → `server/`（含 `server/session/`、`server/test/`）、`server/engine/` → `server/core/`、根 `main.lua`/`test.lua`/`test/`/`bin/` → `server/` 下、新增 `server/core/*`、`server/tools/attribute.lua`、`server/test/core/`、`moe.engine` → `moe.core`。回滚即还原目录名与门面那一行，并删除新增文件。

## 附录：已移出本变更的推迟项（2026-09-19 整理收尾）

归档只同步**已实现**的行为进主规格，因此把「写了需求但本轮没实现」的部分从本变更摘出，内容记在这里以备届时重建：

### A. 对象模型（能力名 `core-objects`）

本批只交付内核的**容器与数值**（牌 / 牌区 + 移动 / 属性 / 随机源）；以下一律推迟到做业务时按需补：

- **玩家**：持有属性实例（`Core.Attributes`）、"是否参与行动"标记、调用方赋予的不透明标签、一组可增删禁用的牌区；"添加"类操作（标签 / 牌区）按接口约定返回 disposer。
- **桌子（代码名 `Desk`）**：入座、座位序号、按行动顺序遍历（跳过不参与行动者）、相邻座位、座位距离求值（两侧取小、最小 1、修正参与且修正后仍最小 1，**非缓存**）。
- **房间**：加入玩家、持有桌面与牌区集合、查询当前局面；`room:setPlayerAttributeSystem(system)`（创建玩家时用该系统造属性实例）；不设人数上限；两个房间互不影响。

### B. 随对象模型一起推迟的条目

- 原 `core-zones` 里"**给玩家**添加 / 删除牌区、被禁用牌区不出现在默认列举中"这半（本变更已收窄为"牌区自身的禁用 / 启用"）。
- `tasks.md` 的 4.4b（玩家侧牌区集合）、7.5（对象用例）。

### C. 其它推迟项

- 公式 / 复杂属性（`setFormula` / `setBaseSymbol` / 字符串型 `min`-`max` 引用）与"查询自上次检查以来的变化"（库的 `getTouched`，返回的是变化**前**的取值）—— 等有消费者再定。
- 牌归属（"一张牌只能在一个牌区"）：本轮选薄模型，将来真需要时再加厚。
- 移动产生事件 / 记牌器：本轮不做。

原 `core-objects` 规格草案（4 条需求：玩家组成 / 座位与行动顺序 / 座位距离 / 房间装配与隔离）见 git 历史：本变更归档前的 `specs/core-objects/spec.md`。
