# Design

## Context

- 用户已定的口径（2026-09-19）：**不做按名单卸载**（「直接清空重新加载就行了」）；**不走 `require`**，而是「传入一个列表，依次 load 进来」，清单来源先不管、测试写死；规则集侧提供 `rule.card '杀' :onTargets(f) :onUse(f)` 形状的定义入口，以及 `rule.depends { '杀', '闪', '基础规则' }` 形状的依赖声明（文件 ⇒ 直接加载，目录 ⇒ 加载目录下所有文件）。
- **热重载与规则集重载是两条不同通道**（已写入 `architecture.md` 第 8 节与 `sanguosha-rules` 第 9 节）：前者是开发期修 bug 用（`moe.reload`，基于 `include` + `package.loaded`），后者是游戏业务功能（运行期换/重装规则集）。因此本设计**不复用** `moe.reload` 的登记与回调机制。
- 开发节奏为「自底向上、按功能点推进」：本批只交付**加载机制**，卡牌/技能的具体回调名与签名留到做「杀」时定。
- 中文标识符部分**已落地并验证**（提交 `a10c732`）：运行时 = 构建期给 `lctype.h` 打补丁；分析器 = `.luarc.json` 的 `runtime.unicodeName`。

## Goals / Non-Goals

**Goals:**

- `moe.rule.load(清单)` 把规则集文件读进来执行，文件之间可声明依赖，规则集通过定义入口登记内容。
- 加载器与「热重载」在实现上互不牵连（不登记进 `moe.reload`、不进 `package.loaded`）。
- 中文标识符能力可重复构建、不脏第三方源码树、失败即报错。

**Non-Goals:**

- 按名单卸载、mod 式热安装/停用（未来说要支持时另开变更；届时需要自建加载器与卸载语义）。
- 清单的来源与组织方式（先不管，测试写死）。
- 卡牌/技能的具体回调集合与签名（做「杀」时定）。
- 规则表的内容结构（先只有「牌」一类，按功能点增量长）。

## Decisions

### D1 门面与落点

- 门面 `moe.rule`，代码放 `server/rule/`（与 `core/`、`session/` 平级）。命名空间 `rule` 同时作为**规则集侧**的书写入口（`rule.card` / `rule.depends`），它由加载器在加载前**注入到被加载文件的执行环境**里（见 D4），因此规则集文件不需要 `require` 任何东西。
- 规则表与加载器都**不是**可重载模块（不参与 `moe.reload`）。

### D2 加载方式：直接读文件执行，不用 `require`

- 每个文件：读入源码 → `load(chunk, '@' + 路径)` → 执行。用 `@路径` 作 chunkname，使报错与堆栈里显示真实文件路径（中文路径同样可用）。
- 之所以不走 `require`：① 规则集本来就是**数据/内容**，需要整包清空重装，靠模块缓存反而碍事；② 与热重载彻底解耦；③ 将来支持 mod 式装卸时，卸载语义落在自己的加载器里而不是 Lua 的模块系统里。
- 目录 ⇒ 枚举其中所有文件（递归按需；本批只做一层目录展开，遇到子目录再递归）。

### D3 依赖声明在执行时同步加载

`rule.depends { ... }` 在执行到那一行时**立刻**把依赖加载完，再继续本文件剩余的代码。因此约定：**依赖声明写在文件顶部**。这样不必去预扫描源码文本（预扫描要面对字符串/注释里的假匹配），实现简单且语义直观。

- 依赖项解析：先按「文件」解释（相对 `game/` 根，扩展名可省略），不存在则按「目录」解释并展开；两者都不存在 ⇒ 报错。
- 去重与防环用一个「本轮已加载/正在加载」的集合：进入某文件时先登记，重复引用直接返回（这也满足了「同一文件只执行一次」与「循环依赖不死循环」）。

### D4 规则集侧的执行环境

加载时以 `setfenv`/`_ENV` 注入方式让被加载文件看到 `rule`（以及少量约定名），使规则集文件顶部不需要 `require 'rule'`。注入的实现细节留到实现时定（Lua 5.5 用 `load` 的 env 参数即可），但**注入面要尽量小**：只给 `rule`，避免规则集依赖项目内部的其它全局。

### D5 清空重载

`moe.rule.load(清单?)` 的语义：**清空规则表** → 清空本轮加载集合 → 按清单（省略时用上次记下的清单）依次加载。不做增量、不做卸载；重复加载同一份清单会**重新执行**所有文件。

### D6 中文标识符的构建接法（已实现）

- bee.lua 的补丁机制会**把官方 Lua 源码整树复制**到构建目录再 `git apply`，且把整树文件都声明为 outputs ⇒ 不能再往同一目录加第二个补丁步（ninja 会报 outputs 冲突）。因此本项目的做法是：**自己复制到 `build/moe-patched/lua55` 并按序打补丁**（optchain + 中文标识符），再用自有 `source_moe_lua` 编译。
- 代价与风险：`source_moe_lua` 需要**镜像** bee 的 `source_lua` 字段（includes 含 `3rd/lua-patch`、平台 defines、MSVC 的 `BEE_FAST_SETJMP` 与 `/std:c11`）；**bee 上游改动 `source_lua` 时要跟着改**。这一点必须在 `infrastructure.md` 里写清。
- 补丁本体只动 `lctype.h` 的字符分类宏，不改语法、不引入运行时开关。另一个可用路线是把它贡献给 bee.lua 上游（用户已选本路线 A，B/C 留作备选）。

## Risks / Trade-offs

- [与 bee 上游的 `source_lua` 分叉：上游改了字段我们要手动跟] → 在 `infrastructure.md` 的 Lua 补丁链一节写明「要对照 bee 的 `source_lua`」；补丁链本身集中在 `make.lua` 顶部一段。
- [补丁与上游 Lua 源码的上下文漂移（升级 Lua 版本时 `git apply` 会失败）] → 构建期失败即报错（不静默降级），并且补丁文件很小、定位明确。
- [`.patch` 文件的行尾：本机 `core.autocrlf=true` 会把它写成 CRLF，`git apply` 直接报 `corrupt patch`] → 应用脚本在打补丁前把内容规范化为 LF（不依赖各人的 git 配置）；这条要写进文档，避免以后有人「顺手修一下 CRLF」。
- [注入执行环境（D4）让规则集能看见项目全局] → 注入面只给 `rule`；其余一律不给。
- [中文标识符会让人写出「看起来像字符串」的代码（中文名 vs 中文字符串）] → 属风格问题，写进 `game/` 的编写约定即可，不做语言层限制。

## Migration Plan

- 纯新增：`server/rule/`、`make/lua-patch/`、`.luarc.json` 的一个开关。回滚 = 删除这些新增、把 `make.lua` 的 Lua 编译接回 bee 的 `source_lua`（即恢复 `lm.optchain = true`）。
- 兼容性：`moe.reload` 与 `core` 行为不变；`server/` 下现有代码不含非 ASCII 标识符，不受影响。

## Open Questions

- 清单的来源与约定（谁提供、放哪里、要不要支持多套规则集）——等有第二个规则集或业务入口时再定。
- mod 式热安装/停用的语义——用户表示「到时候先研究一下」，不在本批。
