# Design

## D1 为什么反悔「不做增强标准库」

`2026-09-19-package-surface` 的理由是**迷惑性**：`table.filter` 看起来像 Lua 自带的，将来把包挪到别的引擎会踩坑。

两条都还在，但权衡变了：

- **迷惑性这条其实被「来源」吸收了**：包要跑起来就离不开我们的装载器与环境（注入的 `game` / `Card` / `Depends`、白名单、共享环境、「整轮共用一份」），**挪到别的引擎本来就跑不了** —— 单独为 `table.filter` 保留一份可移植性没有意义。而「哪些标准库成员是本项目加的」这件事有**唯一权威清单**：`package/@tools/table.lua`（一行注释都不用写，文件本身就是答案）。
- **纠名字的成本是每轮都在付的**：三轮里换了 `util` → `Table` → `table`，每次都要解释「它为什么叫这个、和标准库什么关系」。定成 `table` 之后这层解释消失了 —— **名字自己表达了设计**。
- **`Table` 那个名字的迷惑性更强**：与 `table` 只差大小写，读的人要么以为是笔误，要么以为真有这么个标准库。

结论：**用浅拷贝把副作用隔离掉，比继续纠名字划算**。

## D2 副本而不是代理（用户原提案是代理）

用户原话是「makeEnv 时要对所有标准库加个代理」。实测**不需要**：

- 所有扩充都是**往表上挂新函数**（`table.filter = …`），**一层拷贝就够**（`pairs` 拷一遍所有成员）。深层表（`table.insert` 等）是函数值，拷贝后仍是同一个函数 —— 本来就该共享。
- 代理（`__index` + `__newindex`）反而更贵也更难懂：读一次要过元方法，`__newindex` 得把「内核已有的」和「内容新加的」分开处理。
- 拷贝的**额外好处**：内容侧甚至可以**覆盖** `table.concat` 这类既有成员而不影响内核，还不用管 `rawset` 与 `__newindex` 的交互。

**代价**：每轮装载多拷 4 张小表（`table` / `string` / `math` / `utf8`）—— 与「每文件跑两遍编译执行」相比可以忽略。

**判定标准**：拷贝范围是「白名单里凡是表值的项」，**不手写名单** ⇒ 白名单加东西时零维护。

## D3 语义与边界

- **每轮装载一份**（`makeEnv` 每次 install 调一次）⇒ 重装换新副本，「上一轮加的函数」自然消失 —— 与共享环境、规则表、规则数值同一生命周期。
- **`table` 不在「每文件刷回」的保护名单里**（那只保护内核注入的 `game` / `Card` / `Depends`）⇒ 哪个包把它整个换掉，**由那个包负全责**（用户 2026-09-21 定，不额外加保护）。与内容侧其它全局同口径。
- **没装 `@tools` 的局仍然有 `table`**（它来自白名单，不来自包），只是少了三个助手 —— 比上一批「没有 `Table` 这个全局」的代价轻。
- **要加的仍只有纯函数**（内核 `moe.util` 里的 `saveFile` / `defer` 拿不到）。

## D4 类型：泛型标在实体函数上，所以不需要 `meta.lua`

上一批为工具集单开了 `@tools/meta.lua`（`---@class 工具.工具集` + `---@type`）。现在类型**直接写在赋值处**：

```lua
---@generic T
---@param list T[]
---@param predicate fun(value: T): boolean
---@return T[]
function table.filter(list, predicate) … end
```

**LuaLS 接受给标准库补字段**，泛型**带着走、跳文件也认** —— 实测（2026-09-21）在 `package/标准/卡牌/杀.lua` 里 hover `table.filter` 得到：

```
function table.filter(list: <T>[], predicate: fun(value: <T>):boolean) -> <T>[]
```

前提是**泛型只能标在实体函数上**（`---@field f fun<T>(…)` 会被压平成 `any`，见 `architecture.md` §9.6）—— 所以这条路只有「函数直接挂在 `table` 上」才走得通，也正好是本次的选择。于是 `@tools/meta.lua` 没有存在理由，由用户删除。

**`integer` 而非 `number`**：回调的 `index` 用 `integer`（用户 2026-09-21 定，同内核口径）。

## D5 用例怎么锁住「副本」

两条：

1. **工具集可用**（改写原有）：内容侧直接 `table.filter` / `table.map` / `table.contains`，用真 `@tools` 包（来源 = 探针目录 + `./package/*`）。
2. **副本隔离**（新增）：

```lua
table.乱来 = function () return "内容侧的" end
```

内容侧读得到；内核侧断言 `rawget(table, '乱来') == nil`。

用 `rawget` 是刻意的：这条要在**内核那张表**上判，写 `table.乱来` 会先被 LuaLS 按标准库类型报 `undefined-field`（实测过），且语义上我们想验的就是「原表没有这个键」。

**不做**的用例：不测 `string` / `math` / `utf8`（同一段代码，重复）；不测「内容侧覆盖既有成员」（同一机制，没有额外分支）。

## D6 随之消失的一条检查（要报给用户）

上一批有一条用例「工具集里只有纯函数」：断言 `Table.loadFile` / `Table.saveFile` / `Table.defer` 都是 `nil`（内核 `moe.util` 有这些副作用能力，工具集不许漏出来）。

它**跟着 `Table` 这个名字一起失效了**：现在三个助手挂在标准库副本上，而副本里本来就是标准库那套成员 —— 断言 `rawget(table, 'loadFile') == nil` 只是「Lua 标准库没有 `loadFile`」，什么都没验。

「`@tools/table.lua` 里只放纯函数」于是退回成**评审时的约定**（写进 `architecture.md` 与 `sanguosha-rules`），不再是可执行检查。要恢复的话得换个形状（比如内核侧留一份标准库键集快照、断言内容侧键差集正好是三个名字），但那会随每次加助手变脆 —— **本批不做**。

**结论（2026-09-21 当天定）**：不恢复这条用例，改成写文档 —— 而且理由比「约定」更强：**这条纪律已经由沙箱自动保证了**。助手写在内容侧的环境里，`io` / `os` / `moe` 全都够不着 ⇒ 带副作用的助手**根本写不出来**（旧 `util` 的隐患在它还是内核注入时才存在）。文档已按这个口径写（`architecture.md` 9.6、`sanguosha-rules` §9.1）。
