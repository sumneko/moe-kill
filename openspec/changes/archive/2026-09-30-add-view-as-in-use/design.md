# Design

## 两个族为什么形状不同

| | 打出族（`AskPlayCard`） | 使用族（`AskUseCard`，本变更） |
| --- | --- | --- |
| 场景 | 回应（要【闪】/【杀】） | 主动（出牌阶段挑一张牌用） |
| 玩家的选择 | 用 / 不用 | 用**哪一张** |
| 声明怎么参与 | 交给应答方之前**依次试**（`beforeAsk`） | 作为**一个选项**出现在 `options` 里 |
| 目标 | 不需要 | 在**同一份答复**里给（`{ viewAs, targets }`） |
| 为什么 | 没有「候选」可言，试到成立就当答复落定 | 有 `options` 这个现成载体，与正常用牌同形；也不必让内核再问一次「打给谁」 |

`add-view-as` 的 design 里那句「窗口制（不是『让玩家挑一个』）」**只对打出族成立**，本变更把这条差异写进两处 design。

## 合法性全部由内核算（内容侧零新增）

使用侧的声明需要「能不能用、能打谁、几个」三样，三样内核都拿得到：

- **素材够不够** ⇒ `ViewAs:canGatherMaterials()`（声明自己的条件，同步判）；
- **这次用得出去吗、能打谁** ⇒ 拿一张**光板虚拟牌**跑 `game:canUse(user, 牌, condition.target, useOptions)` —— 虚拟牌随时能造、不进牌区、用完 `Delete`，零副作用；
- **几个目标** ⇒ `canUse` 顺手给出的 `plan`（`Game.UsableTargets`）。

于是内容侧**一个字都不用改**（丈八只是多传了一个「关联」）。这也回答了「至少对于丈八来说内容侧信息足够」：合法性来自 `canUse` 与牌的 `'获取目标'`，声明只负责「视为哪张牌」+「素材」。

**已知边界**：选项的 `plan` 是拿**光板牌**算的（真牌要等素材到手才造）。将来若某张牌的 `'获取目标'` 读牌面，选项给的目标可能与实际能打的略有出入 —— 由 `useCard` 的**二次校验**兜住（这正是既有的两层职责：选项生成时算区间、答复时重算）。

## 一次「声明答复」的流程

```
选项生成（同步）：素材够？→ 光板牌跑 canUse → 追加 { viewAs, plan }
玩家答复：{ viewAs = 那份声明, targets = { … } }
  ① checkAnswer：给了 viewAs ⇒ 找对应的声明选项（找不到 = 「答复不在可选项里」）、跳过张数检查（牌由内核造）、目标按 plan 校验
  ② beforeResolve（@async）：跑声明的 '发动'（省略 = 成立）→ 内核按声明条件 askCard 收素材 → 造真牌
       拿不到牌（不成立 / 素材没给够 / 收素材的询问没人答）⇒ 作废：task:reject(原因)，.err 记原因、不算失败、不发起使用
  ③ 结果里的 cards 就是那张造出来的虚拟牌 ⇒ 后面与实体牌一模一样（use() → useCard 二次校验 → 牌进处理区时子牌跟着走）
```

**为什么把「造牌」放在 `checkAnswer` 之后**：`checkAnswer` 是同步的，而收素材要问玩家（异步）。于是基类多一个 `@async` 钩子 `beforeResolve(value)`（基类原样返回），`AskUseCard` 在那里把声明换成真牌 —— 与 `makeOption` / `checkOption` 同一套「子类覆写钩子」的风格。

**为什么不用「覆写 `collectAnswer` 再调父类实现」**：class 库没有父类引用机制（子类覆写走虚拟调用是既有风格），多一个空钩子比引入父类调用便宜。

**没给条件的询问**（`condition == nil` = 不做任何限制）：`collectOptions` 直接返回 `nil`，声明也就不进候选 —— 现有调用点（出牌阶段 / 濒死）都给了条件，先不为此改「不做限制」的语义。

## 「素材给不出」= 客户端答错 ⇒ 作废

用户 2026-09-30 定：按既有规范处理（`.err` 记原因、`.card` 空、不算失败），**不重问、不退回**。与「答复不在可选项里」同一个分支，调用方只看 `.card` 就够。

## 关联（`source`）

客户端要「先点一下关联的武器 / 技能，再选牌和目标」⇒ 选项里得能看出它来自谁。给 `ViewAs` 加公开字段 **`source?`**（`addViewAs(牌名, 关联?, 条件?)` —— **关联排在条件前面**，它几乎总是要给；仍是可选参数），内核只存不解释（与 `Buff.payload` 同待遇）；约定**装备传那张牌的实例**（丈八、八卦阵传的就是它们自己那张牌）、技能传技能实例 —— 客户端据此点亮 / 选中来源，再选牌与目标。不解释的代价是协议层只能展示、不能据此做判断 —— 够用。
