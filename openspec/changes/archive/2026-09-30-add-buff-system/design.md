# Design

## 1）形状（2026-09-29 定；用户给的定义思路）

**Buff 就是一个单独的类、附着在 `Player` 上、`extends GCHost`，再给「获得 / 失去」两个时机。**

```lua
-- 内容侧：声明一只 buff（写法与 `Card '杀'` 同形）
Buff '青釭'
    : on('获得', function (buff) end)
    : on('失去', function (buff) end)      -- 需要时才有

-- 获得 / 失去
player:addBuff('青釭', 载荷?) -> Buff      -- 同名可并存（各自一个实例）；第二个参数是给内容侧自己约定的一份来由
buff:remove()                             -- 失去：幂等（内部就是 `Delete(self)`）

-- 实例上现成的三样
buff.owner                                -- 挂在谁身上（内容侧读法）
buff.payload                              -- 挂上时给的载荷（内核只存不解释）
buff:bindGC(x)                            -- 资源 / 订阅：随失去自动撤销（`GCHost` 自带）

-- 查询
player:getBuffs() -> Buff[]                -- 快照（给查询与全量同步）
player:hasBuff(名字) -> boolean
```

**为什么这样就够 —— 三件事都落在已有机制上**：

- **「资源与订阅记在 buff 上」不用另造 API**（design §3 那条要求）：`GCHost:bindGC` 本来就把「挂上去的东西」的释放绑在自己的寿命上，而本工程「可叠加操作一律返回撤销函数」的约定（`Zone:disable()` / `game:on(...)` / `Phase:addLimit(...)`）正好都能直接喂给它 ⇒ 内容侧只写「获得时挂了什么」，**不用**写反向的「失去时撤什么」。
- **「失去」就是 `Delete`**：`buff:remove()` 只是给内容侧一个入口（`package/` 拿不到 `Delete`）。`Buff:__del` 里发 `'失去'`（此时实例还在宿主身上、字段还在 ⇒ 处理器读得到 `buff.owner`），随后从宿主摘掉、基类 `GCHost:__del` 再放掉 `bindGC` 的东西 ⇒ 次序天然是「先发失去、再摘掉、再撤资源」。
- **同名并存**：一个实例一份 `bindGC` 账，重叠窗口各持一层（`Zone:disable` 的计数自己配平，见 §5）。
- **载荷（2026-09-30 补，用户定「用第二个参数传进来」）**：`addBuff(名字, 载荷?)`。有些状态得知道「自己是为什么挂上的」才能自己收掉（青釭剑要知道「哪次使用」）⇒ 内核只把它放着、在 `'获得'` 之前就位（`buff.payload`，类型 `any?`），内容侧自己约定含义。**没选「读当前正在结算的效果」那种环境值**：那个是栈式（嵌套 + `await` 之后就变了）、还得给内核另立一份对外语义承诺，不如「调用方显式给」。

**声明与查询沿用 `Card` 那一套**：`Buff '名字'` → `game:declareBuff(名字)`（只在加载期、按包存、同包重名报错，`resetContent` 一并清），`player:addBuff(名字)` 按名字查定义（`game:getBuff`）；注入全局 `Buff`（真环境 + 预解析 stub 环境两处）与 `env-meta.lua` 的类型声明照 `Card` 抄。

## 2）为什么挂载点先只做 `Player`

第一个需求（青釭剑）挂在目标玩家身上；`Card` / `Zone` 的 buff 没有消费者（YAGNI）。宿主的存储是 `player.buffs`（引用在宿主身上 ⇒ 宿主没则 buff 自然没）。

## 3）为什么资源与订阅记在 buff 上，而不是创建时的环境

官方裁定（§1 司马懿条）：窗口以「这次【杀】使用开始」为准 —— 中途**剑被拿走 / 使用者失去这个技能**，还没结算的目标**照样无效**。⇒ 窗口不能由「剑的被动订阅」或剑自己持有，必须独立于来源 —— **本形状用 `bindGC` 落实这条**：资源与订阅挂在一个独立的 `Buff` 实例上（而不是创建时的 disposer 栈），剑没了窗口也不动。

## 4）生命周期写法（内容侧，内核不预设）

青釭剑的用法（细节见 `add-qinggang-sword`）：

- **卡牌侧只写「压」与「兜底」**：在**使用者头上**订 `'卡牌-结算前'`（2026-09-30 补的第二个发出点），对全目标 `useCard:bindGC(target:addBuff('防具无效', useCard))` —— 状态挂给那次使用（`GCHost:bindGC` 收 table），那次使用收场（含半路取消 / 目标根本没轮到生效）效果被删 ⇒ 状态跟着被删；
- **状态侧写「松」**：在 `:on('获得', …)` 里订 **`buff.owner:on('效果-收尾')`**（当事人头上那一份），`effect.useCard == 载荷里的那次使用` ⇒ `buff:remove()`（官方：「此时青釭剑对司马懿的效果结束」）—— 不必再比 `effect.target == buff.owner`。

⇒ 内核不提供「时长」参数，也不规定何时删：**buff 自己看表**（`remove()` 时订阅随 `bindGC` 一起注销，不留尾巴）。

**依赖**：`'效果-收尾'` 原来只在「结完时自己建过临时区」的效果上发（2026-09-24 收紧）—— 按目标收尾要它无条件发。**那道闸门已于 2026-09-29 提前单独去掉**（每次结算结完都发；见 `architecture.md` §10）⇒ 这里照写即可，但**过滤条件要写全**（`effect.useCard == 这次使用` 且 `effect.target` 是我管的目标），且**别在收尾里起新结算** —— 收尾可重入，不筛会自激到爆栈。

## 5）不做的（YAGNI）

- `layers`：同名实例并存就够（窗口重叠时两个实例各持一层子区禁用，计数由 `Zone:disable` 自己配平）。
- 挂到卡 / 区上；`source` 字段（先不存；协议要展示来源时再加）。
