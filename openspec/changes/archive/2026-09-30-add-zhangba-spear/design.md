# Design

## 素材为什么由「条件」表达（而不是内容侧交牌）

2026-09-30 讨论时先摆过一版：`'发动'` 返回 `{ card = 自己造的虚拟牌, targets = … }`。用户否掉了 —— 内核**管不住**这些值（`createVirtualCard` 是公开机制入口、`subcards` 内核不解释，targets 在打出侧根本不看），既然管不住，就**不该让内容侧填**。三样东西的归属其实是：

| 东西 | 归属 | 谁给 |
| --- | --- | --- |
| 牌名 | 声明的身份 | 内容侧（内核照它造牌） |
| 素材 | **玩家的牌** | 玩家（内核按条件问） |
| 目标 | **玩家的选择** | 玩家（本变更不涉及，打出族不用目标） |

于是「声明 = 需求描述」：`addViewAs('杀', { zone = '手牌', min = 2, max = 2 })` —— 内核照条件收集，内容侧的表态（要不要发动、判定）仍留在 `'发动'` 里。副产品：**「素材不够就不试、也不问玩家」自动成立**（内核能同步判），这正是原方案里要靠「可选性钩子」才能解决的那一条。

## 一次尝试的四步

```
① 同步可行性：按条件收候选，够 min 张才继续（不够 ⇒ 跳过这份声明）
② '发动' 表态：钩子省略 = 默认成立
③ 收素材：内核按条件 askCard 问玩家；没给 / 给不够 ⇒ 这次不成立（继续试下一份声明）
④ 造牌：createVirtualCard(声明的牌名, 收到的素材)
```

**为什么表态在收素材之前**：反过来的话，判定失败（八卦阵那种）时素材已经到手，得把牌放回原区 —— 脏。现在「素材收到 = 一定成」，「收到一半不给」直接当不成立。

**为什么 `'发动'` 可以省略**：带条件的声明里，「给不给素材」就是玩家的表态（官方也是「你可以将两张手牌当【杀】」—— 递牌即表态）；再要求写一个 `return true` 的空钩子是纯样板。不带条件、又不写钩子的声明会「无条件自动成立」，那是**作者错误**级别的事情（谁会声明一份白替的牌），不由内核防。

## 牌面筛选进 `AskCard.Condition`

筛选项按既有口径长：数组 = 满足其一、单值归一化成列表、不填 = 无要求。

| 字段 | 归一化后 | 判据 |
| --- | --- | --- |
| `suit?` | `suits` | `card.suit` |
| `point?` | `points` | `card.point` |
| `color?` | `colors` | `card.color`（派生：红桃 / 方块 = 红、黑桃 / 梅花 = 黑；没有花色就没有颜色） |

筛选收口成**一个共用判断**（`names` / `suits` / `points` / `colors` 一起判），并给「按条件收集候选牌」单开一个入口 —— `collectOptions` 只是「收集候选 + 逐张 `makeOption`」，而**素材可行性检查只需要候选数量**，不能去跑 `canUse`（那是 `AskUseCard` 的重活）。

## 子牌处置：搬虚拟牌 = 搬它的实体子牌

虚拟牌不进任何牌区（收到就注销）已经定了；那它的 `subcards` 谁管？候选两条：

- **甲：内核跟着搬**（本变更）——`Zone:accept` 收到虚拟牌 ⇒ 注销它、改收它的 `subcards`。**搬牌只有 `accept` 一个入口**（2026-09-28 定的），所以这一改就把所有路径覆盖了：用牌搬进处理区、打出的牌交进处理区、收尾送弃牌堆，**一处特判都不用写**（`AskPlayCard:onAnswered` 里那句 `not card.virtual` 反而可以删掉）。
- 乙：内容侧自己在 `'发动'` 里搬。省内核改动，但要自己拿捏时机（收了素材却没发动就白搬），且绕开「打出的牌进处理区」这条统一语义。

口子只有一处、语义一句话说清 ⇒ 选甲。子牌为空的虚拟牌（如【八卦阵】的【闪】）行为不变：注销、什么都不进。

## 不做（本批）

- **使用侧**（出牌阶段主动把两张手牌当【杀】用）：窗口制要多问一次「打给谁」，候选制才是终局形状（玩家自己挑、并在同一份答复里给目标）—— 留到**候选侧**那批一次做对。
- **虚拟牌的花色点数**：按既有口径（一张 ⇒ 抄它、多张 ⇒ 无），丈八的【杀】**没有花色点数**、因而没有颜色 ⇒ 不吃【仁王盾】（黑杀无效）。这是既有口径的自然结果。
- **优先级**（武将技能 ＞ 装备技能）：仍是声明创建顺序。
