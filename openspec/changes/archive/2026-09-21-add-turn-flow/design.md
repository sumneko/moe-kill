# Design

## Context

现有机制（都要用上，不要重造）：

- **效果 = 一次结算 = 一个协程**：`Effect:apply()` 建 `task` 并 `execute` 执行体，`:await()` 等它结完；入口（`game:useCard` / `damage` / `askCard` / `moveCard`）**自动「驱动 + 等」**并返回效果实例（`./add-effect-suspend` 已归档）。
- **内容侧的钩子跑在效果的协程里**，所以钩子里可以 `await`：`package/标准/卡牌/杀.lua` 的 `'生效'` 里直接写 `game:askCard(target, '打出', { name = '闪' })` 就是这么跑的（`CardEffect:settle()` 在协程内调钩子）。
- **会话外壳的决策通道**：`session:requestInput(kind, payload, timeout)` / `submit(...)` / `cancelRequest(reason)`，形状 `{ kind, payload? }`；`handler:run(session)` 是异步入口。外壳只当容器，**不认识牌与阶段**。
- **内容包拿不到 `moe`**：注入面只有 `game` / `Card` / `Depends` / `util` ⇒ **内容包自己没有起协程的能力**，它只能在"某个已经在跑的协程里"执行。
- **订阅时机分两种**（实测口径）：内容包在加载期用 `game:on`；内核侧 / 流程侧要订阅只能用 `game.events:on`（`game:on` 非加载期直接报错，而 `game.events` 是内容、每次重装会被清空）。
- 行动顺序：`desk:getNext(角色)` 按座位递增、跳过不参与行动的角色（阵亡即退出）；主公坐 1 号位 ⇒ 首回合天然是主公。

## Goals / Non-Goals

- **目标**：一局能**从头跑到尾**（无头）：回合轮转 + 六个阶段 + 摸牌 + 出牌阶段的决策 + 弃牌；阶段与回合都是可挂技能的时机。
- **非目标**（另开变更）：判定区与判定结算、装备与距离修正、濒死与胜负、无懈可击、武将技能、【杀】的次数限制、协议 / 前端。

## Decisions

### D1 回合流程住在哪一层 —— 三个方案（**待你拍**）

先说结论：**内容包自己起不了协程**（拿不到 `moe.task`），所以"谁启动这一局的流程"必须落在能起协程的一方 = 装配侧（无头测试 / 将来的房间 / 会话 handler）。剩下的问题是**流程本身写在哪**。

**方案 A（推荐）：内核给一个「流程槽」，内容包登记，装配侧启动**

- 内核加两个通用方法（不含任何游戏流程）：
  - `game:registerFlow(fn)` —— **加载期**由内容登记"这一局的流程"（`fn` 是普通函数，内核用 `moe.task.create{...}:execute(fn)` 跑它，返回任务 / 流程句柄）；
  - `game:runFlow()` —— **装配侧**启动（`---@async`，可 `await`，返回流程句柄）。
- 内容：`package/@基础/回合.lua` 在加载期 `game:registerFlow(function () ... 阶段循环 ... end)`。
- 装配侧：测试 / 房间 / 会话 handler 一句 `game:runFlow()`。
- 好处：流程是**内容**（换包 / 换模式即换流程，符合"规则集内容"的定位）；启动点通用且内核零内容；流程跑在自己的协程里 ⇒ 里面能正常 `await` 询问与用牌。
- 代价：内核多一个"槽 + 启动"机制（env-meta 要声明 `registerFlow`，规格要写清"内核只是机制"）。

**方案 B：流程住在装配侧模块**（如 `server/flow/turn.lua`）

- 阶段顺序、决策点都写在 `server/` 里，用 `moe.*` / `moe.task`；内容侧只能订阅时机参与。
- 好处：不用给内核加机制，启动天然是装配方的事。
- 代价：**阶段顺序与"这个阶段要问玩家什么"是规则内容，却写死在 `server/`** ⇒ 扩展包（军争 / 别的模式）改回合流程要改引擎代码；流程还得知道内容名字（`手牌` / `体力`）⇒ 只能靠规则数值绕，别扭。

**方案 C：内容包在 `'游戏-开始'` 时机里发起** —— ✗ 时机回调是同步的（`fire` 用 `xpcall` 调），不能起协程；要让它可以就得把 `fire` 改成允许让出，污染所有时机。

### D2 出牌 / 弃牌怎么问玩家：内核补一个**通用决策询问**

- 新增 `Ask : Effect`（`kind` = `ask`）：字段 `to` / `reason`（不透明字符串）/ `question`（`any`，问什么由发起方解释）/ `answer`（`any`，答什么由发起方解释）；`ask:answer(值)` 定下结果（**先给出的算数**，重复应答只记 info）。
- 时机：**`'决策-询问'`**（问出去，应答方在这里拿到询问实例）与 **`'决策-答复'`**（有答复才触发，一个就够 —— 它不像「卡牌-答复」那样要分两步处置牌）。
- 入口：`game:ask(被问者, 缘由, 问什么)`（`---@async`，自动驱动 + 等，返回询问实例）。
- 出牌阶段的答复形状（内容侧自己解释）：`{ card = 牌, targets = { 角色… } }` = 用这张牌；`answer()` / `nil` = 结束出牌阶段。弃牌阶段的答复：`{ cards = { 要弃的牌… } }`。
- **不合并 `AskCard`**：`AskCard` 的语义是"要一张牌"，并且绑着「答复后怎么处置那张牌」（基础规则据此送进 `弃牌`）；通用询问**不碰任何状态**。两者并列，`AskCard` 保持不动。

### D3 摸牌是内容侧动作

`摸牌(玩家, 张数)`：从 `抽牌` 依次取顶、用 `game:moveCard` 挪进该玩家的 `手牌`（一次结算挪一批 ⇒ 可取消、进结算栈）。写在回合流程文件里（`package/@基础/回合.lua` 的局部函数）或单独一个 `package/@基础/摸牌.lua`（**待你定**：拆开的好处是【无中生有】能直接依赖它，坏处是多一个文件）。

### D4 回合角色怎么记

流程内部用局部变量持有"当前角色"；对外的可见性靠**时机上下文**（`'阶段-开始'` / `'回合-开始'` 的 `ctx` 里给出这次是哪个阶段、谁是回合角色）。本批**不**在局上写"当前回合角色"这类全局状态 —— 等真有技能需要"是不是我的回合"时再定（口径未定，先不加）。

### D5 出牌阶段的循环形状

```
问当前角色（'出牌'）：
  答复 = { card, targets } ⇒ 校验（是不是他手上的牌 / 目标是否合法，由 game:useCard 兜）⇒ 用牌 ⇒ 再问
  答复 = 空              ⇒ 出牌阶段结束
```
次数限制（【杀】限一次）**不在本批**：它要么需要「使用前」的钩子、要么需要"这个阶段已用过几次"的记账，两种都值得单独定口径。

## Risks / Trade-offs

- [方案 A 给内核加了"流程槽"，显得多余] → 反过来说它是唯一能让"流程属内容、启动属装配"两全的形状；如果你更倾向流程属装配侧，那就是方案 B，代价写在上面。
- [通用询问与「要一张牌」两个原语并存 ⇒ 概念变多] → 两者的语义边界清楚（是否与牌绑定、是否动状态）；真要合并，等第三个消费者出现时再看不迟。
- [弃牌阶段让本批变大（选牌决策 + 多张挪牌）] → 可拆：本批只做"阶段与时机 + 摸牌 + 出牌驱动"，弃牌下一批（**待你定**）。
- [抽牌堆抽空没有口径 ⇒ 摸牌会失败] → 按标准版是"把 `弃牌` 洗混当新抽牌堆"；这属规则口径，**待你确认**（不确认就先在抽空时明确报错，把口径留白）。

## Migration Plan

- 纯新增：内核加 `Ask`（+ 方案 A 的流程槽）、内容加回合流程文件；既有牌 / 技能 / 用例不受影响（不改任何现有签名）。
- 回滚：`git revert` 即可（纯内存态）。
- 验收：新增 `server/test/rule/turn.lua` 覆盖"首回合主公 → 阶段依次走完 → 摸到 2 张 → 出牌（用一张杀）→ 弃牌 → 轮到下一个存活角色"；全量 `--test` 0 失败 + 问题面板 0。

## Open Questions（动手前要你拍）

2. **抽牌堆抽空**：按标准版「`弃牌` 洗混成新抽牌堆」，还是本批先"明确报错、口径留白"？
3. **本批边界**：弃牌阶段一起做，还是先做「阶段 + 时机 + 摸牌 + 出牌驱动」？
4. **摸牌动作**：并进 `package/@基础/回合.lua`，还是单独 `package/@基础/摸牌.lua`？
