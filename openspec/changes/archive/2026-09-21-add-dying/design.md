# Design

## Context

动手前已核实的事实（来源见括注）：

- `Damage : Effect` 是**目前唯一**改体力的机制（`server/core/damage.lua`：`to:addAttr('体力', -amount)` 前后各触发一次时机）；`Player:setAlive(false)` 会触发 `'玩家-死亡'`，但 `package/` 里没人调它。
- `Attributes:onChange(name, cb)` 是**写入后就地同步分发**（`set` / `add` 内部立即 `system:updateEvent()`），返回 disposer。
- `Effect:apply()` 把结算跑在**自己任务的协程里**（`task:execute` → `moe.await.call`），所以结算体与时机回调里可以直接 `await`；失败记 `.err`、不抛给调用方。
- `Desk:getNext(player)` 按座位号递增取下一个**参与行动**的角色（跳过空位与阵亡者）。
- `moe.util.defer(cb)` 返回可 `<close>` 的对象（`__close` 里调它）。

**官方口径（本次查证）**：

- **【桃】两条用法都是「使用」**：biligame 写「对自己使用，回复 1 点体力。任意角色进入濒死阶段，**你可以对其使用**，令其回复 1 点体力」；萌娘百科的《规则集描述》把它拆成两种**使用方法**（① 出牌阶段回复已受伤的你；② 令处于濒死状态的角色回复）。⇒ 濒死求桃也走**使用**这条路。
- **濒死晚于「受到伤害后」**：郭嘉遗计 / 曹操奸雄都是「当你受到伤害后」触发，通行解释是先把伤害结算完（含这些技能）再处理濒死 —— 所以郭嘉能先摸牌（可能摸到桃）再进濒死。网上没能拿到规则集原文（biligame / 萌娘百科都只有卡牌与武将页），这条按社区通行口径实现，**已向用户说明**。

**用户已定**：濒死做成 Effect、形状由 core 提供；监听与脱离濒死由**规则**提供；回复入口叫 `game:heal`；求桃按行动顺序问一圈；【桃】出牌阶段的用法一起做；濒死插入点 = **等当前效果结算收尾**。

## Goals / Non-Goals

**Goals:**

- 一局能真的死人：体力 ≤0 → 濒死结算（求桃）→ 没救回来就阵亡 ⇒ 回合流程的「只剩一个存活角色」终于可能成立。
- 濒死**插在正确的位置**：受伤后技能先跑，濒死紧随其后；多目标时逐个目标各处理一次。
- 内容侧零新概念：规则包只用到 `attrs:onChange`、`game:enterDying`、`game:askCard`、`game:useCard`、`game:heal`。
- 契约由用例钉住（本变更不写规格）。

**Non-Goals:**

- 死亡奖惩与胜负判定（下一批）。
- 武将技能（遗计 / 奸雄）——本批只保证它们**有位置可挂**（在濒死之前跑完）。
- 「濒死中再次掉血」的特殊处理：自然嵌套即可，不做去重 / 排队。
- 「离开濒死」的独立时机（用户定：本批不要，规则侧读体力即可）。

## Decisions

### D1：濒死的形状在 core，语义在规则

- core 只提供 `Dying : Effect`（持局 + 濒死者 + 生命值属性名）与起它的入口；**谁该进濒死、怎么救**全在规则包。
- 于是内核不认识「体力」这个名字（属性名随调用传入），也不需要知道求桃的顺序与范围。

**Alternatives**：把「监听体力跨越」也做进内核（用户已否：内核只提供 Dying）；让濒死继承 `Damage` 之类的既有效果（濒死不是伤害，会把两种语义混在一起）。

### D2：`game:enterDying(player, attribute)` 只记账，结算收尾时才真正开始

- 用户要的时序：`'伤害-后'`（郭嘉遗计、曹操奸雄挂在这儿）**先**、濒死**后**。
- 实现：`enterDying` 把 `player → attribute` 记进局上的待办表（同一玩家后来居上覆盖）；**每次效果结算收尾**时统一处理：活着且体力 ≤0 的起 `Dying`（`apply()` + `await()`），体力回正的 / 已阵亡的丢掉。
- 收尾点选 `Effect:apply()` 里**结算体返回之后**（用 `moe.util.defer` 保证**抛错路径**也处理）—— 内层效果收尾也处理，这正好给出「多目标逐目标处理濒死」的行为。
- 若调用时**根本不在任何效果里**（工具 / 测试直接 `addAttr`），当场开始 —— 否则那种用法会静默什么都不发生。

**Alternatives**：在属性变化回调里当场起（时序错，见 Context）；只在**根**效果收尾处理（多目标时会把第一个目标的濒死拖到整张牌结算完之后，与官方不符）。

### D3：求桃 = `askCard`（缘由 `'使用'`）+ `game:useCard`

```lua
local card = game:askCard(被问者, '使用', { name = '桃' }).result
if card then
    game:useCard(被问者, card, { 濒死者 })
end
```

- 【桃】是**使用**（Rule 见 Context）⇒ 由 `useCard` 跑它自己的『获取目标』与『生效』，**回血逻辑只写在 `桃.lua` 一处**。
- 缘由写 `'使用'` ⇒ 基础规则的 `打出.lua`（只认 `'打出'`）不动这张牌，牌**仍在该玩家手上**，正好交给 `useCard` 走「结算前 → 处理 → 结算后 → 弃牌」的既有通道。
- 同一张牌既被"问出来"又被"用出去"，中间不需要任何手工挪牌。

**Alternatives**：规则侧自己处置（拿到牌直接回血 + 自己 `moveCard`）—— 会与出牌阶段那条路写两份逻辑；用 `game:ask`（决策询问）而不是 `askCard` —— 那就没有「要一张牌」的语义，答复方也不知道该给什么。

### D4：回复也做成效果（`Heal`）

- `Heal : Effect`（`kind` = `heal`，字段 `to` / `amount`）+ 便利入口 `game:heal(player, amount)`，与 `Damage` 对称：进效果链、有父效果、可取消、失败读 `.err`。
- 写体力走 `addAttr`（上界由属性的 `max` 钳制，所以回血不会超过体力上限）。

**待你定（Open Question）**：要不要顺手加一对 `'回复-前'` / `'回复-后'` 时机（与伤害对称；本批没有消费者，不加也不影响任何行为）。

### D5：判死写在 `Dying:settle()` 的末尾

```lua
function M:settle()
    self.game:fire('濒死', self)              -- 规则侧在这里求桃
    if self.player:getAttr(self.attribute) < 1 then
        self.player:setAlive(false)           -- 真死：触发既有的 '玩家-死亡'
    end
end
```

- 阈值 `1` 按用户口径（「没能回到 ≥1 就会真死」）写在濒死效果里；`'濒死'` 时机里规则侧怎么救（几张桃、谁给）内核不管。
- 阵亡只置状态 + 触发时机，**不做奖惩与胜负**（下一批）。

### D6：`'濒死'` 时机的上下文就是这个 `Dying` 实例

与伤害 / 用牌 / 挪牌一致：上下文 = 效果实例（`ctx.player` / `ctx.attribute` / `ctx.game`），不进额外的载荷对象。

## Risks / Trade-offs

- [待办在「效果之外」被标记，可能没人处理] → D2 的兜底：不在效果里时当场开始。
- [取消路径下结算体被 `coroutine.close` 掉，`__close` 里的处理可能起不了效果（不能让出）] → 处理前先确认「待办里确实有活着且体力 ≤0 的人」；真到那一步（取消 + 恰好欠着濒死）只记一条 `warn` 并**保留待办**，等下一次结算收尾补上，不静默丢。
- [濒死嵌套（濒死中再次掉血）] → 本批不做特殊处理：体力再次 ≤0 会再起一次濒死结算；`Effect.deep` 的 100 层上限是现成的护栏。
- [规则包在「游戏-开始」时才订阅体力变化] → 此后的玩家（本阶段没有中途加入）不在监听范围内；将来做中途加入时改为按玩家绑定订阅。
- [「濒死晚于受伤后」只有社区口径、没有规则集原文] → 已在 propose/design 与技能文档里注明来源与不确定性；若你之后拿到官方原文说要换时序，改动点只有 D2 的收尾位置一处。

## Migration Plan

纯新增 + 一处既有流程的收尾钩子，没有数据或接口迁移。回滚 = 还原这几个文件（`game:enterDying` 没人调时是彻底的空转，`Heal` 与 `Dying` 不注册就没有存在感）。
