# Design

## Context

- 底本（`.agents/skills/sanguosha-rules/references/武将牌/标准包.md` 102–105 行）：【谦逊】「锁定技，你不能被选择为【顺手牵羊】与【乐不思蜀】的目标。」；【连营】「当你失去手牌后，若你没有手牌，你可以摸一张牌。」
- 合法目标的现状：`game:canUse` → `collectLegalTargets` 逐候选过内容侧 `CardDef:targets { filter }`（**发起方视角**的判据），筛不出任何候选 ⇒ 「现在没有合法目标」。
- 「能不能生效」的现状：`Effect:apply` 里结算前依次问三段（全局 / 来源 / 目标），**回调返回非 nil 即阻止**，返回值就是原因。
- 区域事件的现状（孙尚香批）：`'卡牌-离开区域'` / `'卡牌-进入区域'` 每个区发两份 —— 先给**牌自己**、再给**区的主人**（同名；公共区没有主人 ⇒ 只一份），载荷 `(card, zone, visible?)`。
- 手牌区现状：无序区，`count()` 可读；批量搬动时 `Zone:accept` **先把这批牌全部摘完再逐张发事件**（既有硬不变量）。

## Goals / Non-Goals

**Goals:**

- 陆逊整将落地。
- 补上「**候选者自己**能否被指定」这一个询问点 —— 【谦逊】唯一需要的机制，也正好是缺口表里那一栏（空城将来照用）。

**Non-Goals:**

- **不做 `'卡牌-移动后'`（批量移动完成）时机**：用户 2026-10-09 定「其实用离开区域也是可以的，第一次触发后摸了一张牌后，第二次触发手里已经有牌了不会重复触发」。
- 不改 `CardDef:targets { filter }` 的语义与落点（发起方视角的判据保持不动）。
- 不动「三段式能否生效」（它管的是**指定之后**生效与否）。
- 不做牌级可见性（周瑜批已定，留给协议层那批）。

## Decisions

### D1. 新时机放**候选者头上**、名字用疑问式「能否」

- 形状：`player:fire('卡牌-目标-能否指定', plan)`，`plan` = `CardDef.TargetPlan`（`{ user, card, targets?, useOptions? }`）—— 与 `filter` 收到的是同一个 plan，技能能据此判「谁要用什么牌指定我」。
- **为什么在候选者头上**：官方写的是「**你**不能被选择为…的目标」—— 这是**他**的属性；写在全局或使用者头上就得让每个技能自己去比 `plan.user`，还容易误伤别人的技能。
- **为什么用疑问式**：项目约定「疑问式名字 = 期望返回值的事件」（`'卡牌-能否使用'` / `'效果-能否生效'`），返回非 nil 即否决、返回值就是原因。
- 备选（否掉）：内容侧在 `'卡牌-使用选项'` 里过滤候选 —— 那条是**使用者**视角的收集式时机（`game:collect`，不能 `await`），拿不到「逐候选问候选者」的语义，也没法表达「原因」。

### D2. 与「三段式能否生效」的分工：筛候选 vs 不生效

| | 时机 | 官方措辞 |
| --- | --- | --- |
| **筛候选**（本批） | 候选者头上的 `'卡牌-目标-能否指定'` | 「**不能**被选择为…的目标」（【谦逊】） |
| **不生效** | `'效果-能否生效'` / `'效果-来源-能否生效'` / `'效果-目标-能否生效'` | 「**无效** / 抵消」（【仁王盾】） |

- 判据写在文档里（`sanguosha-rules` §9.29 与 `architecture.md` 的 `canUse` 行）：写「不能被选择为目标」的走前者（指定都指定不上），写「无效」的走后者（指定得上但不结算）。
- 副作用：候选被剔除 ⇒ 上限的「与合法目标数取小」自然跟着变（`collectLegalTargets` 返回的 `legal` 已经不含他），无需另做。

### D3. 【连营】用「搭便车」的现有事件，不加新时机

- 判据链：`zone == owner:getZone('手牌')`（只看**离开的区**，目的地不看 ⇒ 被拿走 / 给出 / 使用 / 打出 / 弃置都算失去）→ `owner:getZone('手牌'):count() > 0` 就返回 → `tryCast` 里 `draw(1)`。
- **一次失去 N 张只摸一张**（用户 2026-10-09 的推演，用例钉住）：批量搬空手牌时内核**先摘完再逐张发事件** ⇒ 第一张触发摸 1 张后手牌就不再为空 ⇒ 后面几张被 `count() > 0` 挡掉。
- **底本佐证**：官方【枭姬】的判例是「失去 X 张装备 ⇒ 至多 X 次」—— 逐张发事件**就是对的语义**，所以「批量移动完成」这种时机不需要（`'卡牌-移动后'` 明确不做）。
- `auto(true)`：摸一张是纯收益（照【奸雄】【闭月】），默认不问；关掉自动同意就会问（答否不摸）。

### D4. 用例侧：反向验证抓出的「假绿」教训

- 第一版「谦逊挡【顺手牵羊】」用例里，**陆逊手里没牌** ⇒ 而【顺手牵羊】的 `filter` 本来就要求「目标区域里有牌」⇒ 他**压根不在候选**，于是拆掉内核那处 gate 用例**照样绿**（假绿）。
- 修法：先把「本来就满足的条件」补齐（两边手里都放一张牌），断言才有意义。
- 这也是**反向验证**的价值所在：拆 gate ⇒ 红 3 条（顺手牵羊 / 乐不思蜀 / `core.can-use`）；拆【连营】的「手牌还有就不摸」⇒ 红 2 条（手里还有 / 一次失去两张）—— 两处都精确命中。
