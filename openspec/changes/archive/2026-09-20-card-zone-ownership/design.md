# Design

## Context

见 `proposal.md` —— Why。实现侧要面对的现状：

- `Core.Move` 那一批定的是「薄模型」：`Zone:put` / `Zone:take` 只增删自己那份 `cards` 列表，**牌不知道自己在哪里**（见 `openspec/specs/core-move/spec.md` 的旧需求）。
- 因此「把这张牌挪走」只能靠调用方先把所有牌区翻一遍找它（`game:useCard` 里的 `findHeldZone` 就是这么干的）。
- `game:moveCard(cards, 牌区名)` 已经有一个写死的窄接口（`error('挪牌还没实现')`），内容侧（`package/标准/卡牌/杀.lua`）已经在用它把打出的闪送进弃牌堆。
- 三个相关文件的可见性约束：`---@field private` / `---@field package` 在本工程实测都退化成「同一文件」⇒ 牌区**不能在 `zone.lua` 里直接写 `card.zone`**，只能让牌自己提供一个写入方法（先例：`game:pushEffect` / `game:enterWaiting`）。

## Goals / Non-Goals

- 目标：牌能随口答出「我现在在哪个牌区」；挪牌入口落地；把「同一张牌同时在两个牌区里」从「允许」变成「明确失败」。
- 非目标（design 层面的边界）：不给挪牌加时机 / 记录；不引入「按位置（下标）查询」；不做「跨局」「跨玩家归属」的概念 —— 归属只表达**牌区**。

## Decisions

### D1 归属记在牌自己身上，而不是维护一张索引表

**选了**：`Card` 带一个字段记所在牌区，牌区在进出时维护它。

否掉的方案：

- **继续遍历找牌**（现状）：每次挪牌都要翻遍所有牌区，将来的「匹配系统」也要重复这件事；而且它默许同一张牌出现在两个区里。
- **局上维护「牌 → 区」的索引表**：多一份状态就多一份失效责任（谁在什么时候删这条记录？），还得分担「谁的牌区被清了」这类事件；而牌本身就是最自然的归属载体。

### D2 只记「哪个牌区」，不记下标

下标会被**任何一次插入**改掉 —— `Zone:move` 允许插到任意位置、`put` 追加、`take` 又整体前移。要维护它就得在每次插入后刷新一遍全表，收益却只是省一次 `zone:list()` 里的查找。要位置时现找即可；将来匹配系统真需要「按位置查询」，再在那个功能点上单独定。

### D3 `put` 拒收已有归属的牌，而不是「自动从原区摘出来」

**选了**：明确失败（错误文本直接提示「要换区请用 move」）。

否掉的方案：**隐式移动**（`put` 发现牌在别的区里就顺手把它摘出来）。那等于把一次「进出」偷偷塞进另一个操作里：调用方看不出牌是从哪儿挪来的，牌区的顺序副作用也无法预期，与工程「明确失败、不替调用方猜」的口径相悖。换区这件事已经有专门的入口（`Zone:move` / `game:moveCard`）。

### D4 写入归属走牌自己的方法（`bindZone`）

牌区跨文件写不到牌的私有字段（见 Context 的可见性约束）⇒ 牌提供 `bindZone(牌区或空)`，牌区在自己那四种操作里调用它。它是**内核内部**的写入口：接口说明写「只有牌区自己用：放进 / 取出时维护」。不做运行时防御（工程口径：自己人之间的约定不写防御）。

### D5 挪牌入口落在 `core-move`，落点是目标区底部

`game:moveCard` 做的事就是「移动」，归属也在同一能力里；`core-game` 管的是局的所有权与工厂，不掺流程。

- **成批**：内容侧一次挪多张（弃牌堆批量回收）是常态，逐张调用会把「整批校验」这件事推给调用方。
- **整批校验后再动**（先收集每张牌的源区，再逐个移动）：这天然满足 `core-move` 既有的「校验全通过才改状态」口径，两种失败都不留半成品。
- **落点 = 目标区底部**（不接收位置参数）：弃牌堆 / 处理区这类目的地不关心顺序；要「塞到抽牌堆顶」时再加位置参数。

### D6 归属不产生事件

沿用原口径（旧需求里那句「MUST NOT 产生事件、记录或其它流程性副作用」保留在新需求里）：进出只是记账。将来要「牌离开某区」「牌进入某区」这类时机，另开变更一起定（那时还要处理归属与时机谁先谁后）。

## Risks / Trade-offs

- [内容侧可能在「牌还在区里」时又 `put` 一次，从静默成功变成报错] → 现有路径都满足新约束：建堆时是新牌、回收前都先 `take`（`use-card` / `respond` 取出后才挪）；`--test` 全量用例是这条的回归网。
- [有人绕开牌区直接改归属] → `bindZone` 的说明写明「只有牌区自己用」；按工程口径不做防御（不认识的外人放进来的是别人的包与文件，那才检查）。
- [旧用法（同一张牌同时放两个区）被去掉] → 主规格 REMOVED 那条需求并写了迁移路径（换区走移动 / `game:moveCard`）；工程内部只有一条薄模型用例依赖它，已替换成归属用例。
- [归属字段多看一处私有状态，重载后老实例怎么办] → 字段在牌实例上（不是模块级 `local`、也不在类表上），重载不影响实例字段（`Class` 走合并，见 `hot-reload`）。

## Migration Plan

- 代码已按上述决定落在工作树：`server/core/card.lua`（字段 + `getZone` / `bindZone`）、`server/core/zone.lua`（四种操作维护 + `put` 的拒绝）、`server/core/game.lua`（`M:moveCard` 由接口落成实现），配套用例与文档同步。本变更落地后按 `tasks.md` 逐条核对、勾选、归档，把需求同步进主规格。
- 回滚：三个内核文件回退到本变更之前即可（纯内存态，没有需要迁移的数据）。

## Open Questions

- 归属要不要再表达「属于谁」（现在只到牌区；「在谁手上」要靠牌区本身是玩家区还是公共区推）—— 等匹配系统那个功能点定。
- 将来「牌离开某区」要不要有时机（现在明确不产生）—— 那时一起定归属与时机的作用顺序。
