# Design

## Context

见 `proposal.md` 的 Why。设计要贴合的三条既有形状：

- **定义上的字段有先例**：`CardDef:limit(阶段名, 次数)` / `getLimit`（2026-09-22 落地）—— 链式方法写、内核只当值存、读接口给快照；阶段名 / 牌名对内核都是**不透明字符串**。
- **`canUse` 的内建条目**（`server/core/game.lua`）：有牌名 / 有同名定义 / **牌在使用者名下牌区里** / `'获取目标'` 给出非空合法目标 / 目标非空且是合法目标的子集 / 次数没用满 —— 之后才问内容侧 `'卡牌-能否使用'`。牌区解析用 `Player:findCard(牌)`（返回 `zone, index`）与 `Player:getZone(名字)`。
- **定义的声明期**：`Card '杀'` → `game:declareCard('杀')`，只能在加载规则集时调；名字路由 `game:getCard(名字)` 是「限定名直接用 / 裸名先本包、再按清单顺序」。加载顺序里默认包（`@基础`）排最前。

## Goals / Non-Goals

**Goals:**

- 分类（`kind`）与「从哪个区用」（`zone`）成为**定义自己的声明**，内核只存不解释；`zone` 参与 `canUse` 的内建判断。
- 公共模板（`基本牌` 这类）能被**拍平复制**进具体牌的定义，且复制结果与基类脱钩（改基类不会回头影响已复制的）。
- 三条都沿用既有风格：链式、无括号字符串调用（`: kind '基本'`）、下标不校验。

**Non-Goals:**

- 不做武将技能定义（技能系统还没做）。
- 不做装备牌本身（装备区、装备技能、距离修正仍不在本批）。
- `kind` **不参与**任何内核判断（不因为「是锦囊」而改变结算）；前端展示与 AI 用是它将来的价值。
- 不做「用完后进哪个区」（`'卡牌-结算后'` 的去向仍由内容包写死）。

## Decisions

### D1 `kind`：可叠多条，内核只记录

- `CardDef:kind(名字)`：链式、可多次调、**累加且去重**（同一个名字重复写不加第二条）。取值口径（用户 2026-09-22）：**省略「牌」字** —— `'基本'` / `'锦囊'` / `'装备'`。
- 读：`CardDef:isKind(名字)` → boolean；`CardDef:getKinds()` → **快照数组**（按声明顺序，深拷贝一份给调用方 ⇒ 拿出去改不影响定义）。
- 备选（否）：单值（延时锦囊既是「锦囊」又是「延时」、装备还要分「武器 / 防具 / 坐骑」，单值迟早要拆成两个字段）；`getKind()` 返回逗号串（调用方还要自己拆）。

### D2 `zone`：声明「必须从哪个区用」，由 `canUse` 判

- `CardDef:zone(区名)`（单值，重复调后者覆盖）+ `CardDef:getZone()`。
- `canUse` 的内建条目：先照旧 `findCard(牌)` 要求「牌在使用者名下某个牌区里」；**若定义声明了 `zone`**，再要求牌所在的就是 `user:getZone(区名)` 那个区（没这个区 / 牌不在里面 ⇒ 用不了，原因是给得出的一句话）。
- **没声明 = 现状**（在使用者任一牌区里即可）⇒ 不声明 `zone` 的既有定义与用例行为不变。
- 区名对内核仍是**不透明字符串**（内核不预设「手牌」这类名字）；解析走 `Player:getZone(名字)` —— 与 `moveCard` 的区名解析同一套概念（只是这里只在**使用者身上**找，不绕到局上的公共牌区）。
- 备选（否）：默认手牌（会把「没声明」的既有行为改严，且内核凭什么默认手牌）；只记录不判断（用户要的是 canUse 的内建判断）。

### D3 `extends`：加载期快照复制，钩子在先、字段深拷贝

- `CardDef:extends(名字)`：链式；用 `game:getCard(名字)` 解析（所以支持 `标准.杀` 这类限定名、以及「本包优先、再清单顺序」的裸名语义）；**必须在加载期调用**（定义只能加载期声明，天然满足）。
- 复制什么：
  - **钩子**：基类每个钩子的回调列表，插入到本定义自己的回调**前面**（基类先跑；谁后写谁覆盖状态的老规矩不变）。
  - **字段**：`kind` 列表、`zone`、限额表 —— 一律**深拷贝**（之后改子定义不会改到基类，反之亦然）。
- 找不到基类 ⇒ `error('找不到要继承的定义「X」')`（内容写错 = 真错误）。
- 多次 `extends` 依次合并：钩子按顺序追加、`kind` 累积（仍去重）、`zone` 与限额表**后者覆盖前者**。只是把语义定死，不为多继承加机制。
- **拍平、不与基类联动**（用户 2026-09-22 定）：复制完就脱钩 —— 之后 `game:getCard('基本牌'):on(...)` 不会影响已经复制过的【杀】。理由：加载期一次成型、行为可预测；「运行期还能改基类」是另一套东西（等真需要再加）。
- 备选（否）：读的时候沿父往上找（动态继承）—— 与用户要的"把基类的定义复制过来"相反，也会让「加载顺序」重新变成隐形约束。

### D4 三处接口一起写进 `env-meta.lua`

`CardDef` 的类型清单是包作者可见的契约（钩子是固定集合、拼错编辑期就报）：本批往它加 `kind` / `isKind` / `getKinds` / `zone` / `getZone` / `extends` 六条，并在 §12 的接口表里记一段。

## Risks / Trade-offs

- [`zone` 声明了但玩家没有那个区（或牌不在里面）⇒ 忽然用不了] → 原因文案里带上区名，一眼看出是声明与牌区对不上；没声明就完全不受影响（既有用例回归证明）。
- [复制是快照 ⇒ 后来给模板加的东西不会自动进已复制的牌] → 加载期一次成型是刻意的（D3）；`@基础` 排最前、模板先加载，所以「模板写在前面」天然成立；写成 design 的已知限制，真需要联动再谈。
- [`kind` 可叠 ⇒ 同一分类可能被重复声明] → 去重（`isKind` 只看有没有）；`getKinds()` 给快照，避免调用方拿到内部表乱改。
- [定义字段越长越多（limit / kind / zone …）] → 都是同一个模式：链式写、内核只当值存、读接口给快照；真到字段成灾时再谈"统一字段袋"（上一批已经明确否过一次，见 `archive/2026-09-22-add-phase-use-limit`）。

## Migration Plan

无（单进程、探索期、无外部消费者）：改完跑 `server/bin/moe-kill.exe --test` 全绿即可；不改 JSON-RPC，不回改 `openspec/specs/`。

## Open Questions

- `CardDef:getZone()` 与实例的 `Card:getZone()`（牌现在在哪个区）同名不同义 —— 现在靠类型区分（`CardDef` / `Card`）；若将来觉得别扭，改成 `getUseZone()` 只动一处定义 + 调用点。
- 模板条目 `Card '基本牌'`（不在牌表里）要不要在别处登记"它不是真牌" —— 现在不需要（牌表决定造哪些牌），等做装备 / 军争再看。
