# Design

## Context

现状（见 `proposal.md` 的 Why）：

- `Dying:settle()` = `fire('濒死-进入', self)` → 若 `player:isAlive()` 再 `fire('濒死-离开', self)` —— **用「存活」当「救活」的代理**。
- `@基础/濒死.lua` 的 `'濒死-进入'`：写 `'凶手'` 标签 → 绕圈求桃 → 循环末尾 `if 体力 < 1 then player:setAlive(false) end` —— **判死写在规则里**。
- `@基础/回复.lua`：`'回复-生效'` 只做 `heal.to:addAttr('体力', heal.amount)`。
- `game:enterDying(player, damage?)`：当场建 `Dying` → 驱动 + 等 → 返回结完的实例；内核没有「谁正在濒死」的账。
- 死亡之后的链路（不本批改）：`'玩家-死亡'` → 奖惩（`身份场/奖惩.lua`，读死者 `'凶手'` 标签）→ 胜负判定（`身份场/胜负.lua`，靠 `Depends` 定序）。

## Goals / Non-Goals

**Goals:**

- **杀死玩家归濒死结算**（`Dying` 效果收尾的事），规则侧只负责「救」与「判有没有脱离」。
- **脱离濒死是个瞬间事件**：体力恢复为正的那一刻就移除，`'濒死-离开'` 当场触发。
- 内核仍然**不认识体力**：识别「脱离」只看规则侧有没有喊 `dying:leave()`。
- 判据从「内核看存活」换成「内核看脱离标记」。

**Non-Goals:**

- 不改 `'玩家-死亡'` 及其之后的奖惩 / 胜负链路。
- 不引入「濒死中的其它状态」（例如濒死时不能被杀第二次这类特殊处理）。
- 不做 `player:isDying()` 这类便利查询（需要时再加；`game:getDying` 够用）。

## Decisions

### D1 `Dying` 记「有没有脱离」，`leave()` 当场发时机

```lua
--- 脱离濒死：体力恢复为正时由规则侧调（幂等）
function M:leave()
    if self.left then return end
    self.left = true
    self.game:fire('濒死-离开', self)
end
```

- 幂等：重复 `leave()` 不再发时机；已经死了（内核杀过）也允许调（无害）。
- 为什么当场发（而不是结算收尾）：规则里「体力回正 ⇒ 脱离濒死」是个瞬间事件，收尾再补一发会把「已经脱离但后来又被砸到 ≤0」这类情形说错（那时不该再补一发「离开」）。

### D2 `settle()` 收尾：还没脱离就杀死他

```lua
function M:settle()
    self.game:fire('濒死-进入', self)
    if not self.left then
        self.player:setAlive(false)     -- 濒死结算的结果：没脱离 ⇒ 死
    end
end
```

- 判死的**依据是「有没有脱离」**，不是 `isAlive()`：内核只搬运规则侧的结论。
- `setAlive(false)` 是既有的幂等入口（已经是死的不会再触发 `'玩家-死亡'`）。
- 时序上没变：`'玩家-死亡'`（以及奖惩 / 胜负）仍然发生在 `'伤害-后'` 之前、且在这次伤害的结算之内 —— 只是发起人从规则侧换成了内核。

### D3 一个玩家同时只有一个濒死状态（用户 2026-09-23 定）

- 内核按玩家记「当前那次 `Dying`」（1:1，**不嵌套**）：`game:getDying(player)` → `Dying?`。
- `enterDying(player, damage?)`：
  - 该玩家**正在濒死中**（有账且还没 `leave()`）⇒ **不新建、不重新结算**：把它的 `damage` 换成这一次（**最后一次伤害 = 致死伤害**）、**直接返回现有实例**（不 `apply()` / 不 `await()` —— 那次结算正跑着，重开会把求桃循环重来一遍）。
  - 否则 ⇒ 新建并当场结算（返回值是结完的实例）。
- 语意（用户原话）：**濒死状态中继续受到伤害算最后一个伤害杀死玩家** ⇒ 濒死期间又被砸到 ≤0 只是“这一下更狠”：求桃循环照旧继续（体力仍 ≤0），最终若是死，凶手按**最后一次伤害**算。
- 已经 `leave()`（脱离）但结算还没收尾的旧实例不算“正在濒死”⇒ 这时再进濒死会新建一个。
- 备选（否）：嵌套 `Dying`（上一版的做法）—— 一个角色同时有两个濒死状态与规则不符，也会让「致死伤害是谁」无从确定。

### D4 `@基础/回复.lua` 统一管「回正 ⇒ 脱离」

```lua
game:on('回复-生效', function (heal)
    local to = heal.to
    to:addAttr('体力', heal.amount)
    local dying = game:getDying(to)
    if dying and to:getAttr('体力') > 0 then
        dying:leave()
    end
end)
```

- 「体力 > 0」= 官方口径的「回复到 ≥1 就脱离濒死」（`@基础` 的现有判断也一直是 `< 1` / `> 0`）。
- 放在回血的地方（用户 2026-09-23 定）：任何回血来源都自动生效，求桃循环不必自己判断「救没救活」——循环条件 `体力 < 1` 自然退出。

### D5 `@基础/濒死.lua` 只求桃

- 保留：写 `'凶手'` 标签、绕圈求桃（`askCard(… '使用', { name = '桃', targets = { 濒死者 } })` → `game:useCard`）。
- **删掉**：循环末尾的 `if 体力 < 1 then player:setAlive(false) end`（改由内核在 `settle()` 收尾做）。
- `'濒死-离开'` 里清 `'凶手'` 标签，保持原样。

### D6 凶手改读那次濒死，`'凶手'` 标签退役

```lua
-- package/身份场/奖惩.lua
local dying  = game:getDying(player)          -- '玩家-死亡' 期间这张账还在（内核在结算收尾之后才清）
local killer = dying and dying.damage and dying.damage.from
```

- 为什么改：致死伤害现在会在濒死期间被**换掉**（D3），改用标签就得找个地方同步它；而那次 `Dying` 本身就是唯一真相源（`dying.damage`）——内容侧少一个状态、少一处同步。
- `@基础/濒死.lua` 不再写 / 清 `'凶手'` 标签（那段删掉）；`@基础/回复.lua` 的 `leave()` 也不用管它。
- 读取窗口：只在 `'玩家-死亡'`（内核 `setAlive(false)` 那一刻）期间有效；结算收尾后账就清了。将来若要「死后还查得到谁杀的」另存（现在不需要）。

## Risks / Trade-offs

- [`'濒死-离开'` 改由 `leave()` 当场发 ⇒ 谁忘了喊就永远「没脱离」，人会被内核杀死] → 现在只有一个回血入口（`回复.lua`）会喊，用例覆盖「给桃救活 ⇒ 脱离 + 标签清掉」与「一圈没人给 ⇒ 死」两侧。
- [内核开始「判死」（虽然是搬运结论）] → 判据是规则侧的 `leave()`，内核仍不认识体力；语义写进 `dying.lua` 的接口注释与两份技能文档。
- [嵌套濒死（同一人同时两个 Dying）] → **不存这段情形**：D3 定的是一个玩家同时只有一个濒死状态，濒死中再受伤只是换掉致死伤害。
- [旧用例把「内核不判死」当作契约] → 本批**刻意反转**那条契约（proposal 的 Why 就是原因）；内核用例改成「没人求桃 ⇒ 内核杀死他」，规则侧用例改成「救活走 `回复.lua` 的脱离路径」。

## Migration Plan

无（单进程、探索期、无外部消费者）：改完跑 `server/bin/moe-kill.exe --test` 全绿即可；不改 JSON-RPC，不回改 `openspec/specs/`。
