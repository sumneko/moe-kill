# Proposal

## Why

用户已确定实施顺序：**先把「一局游戏」的对象与流程骨架做出来并单元测试，session / 挂起机制最后再把它们串起来**；前面这些功能点都不得依赖 session。

现状：`script/engine/` 只有一个空表；已归档的 `headless-server`（`script/server/` 的会话外壳）与本批无关，引擎不得依赖它。

本批的硬约束（用户拍板）：

- **引擎的每一项能力都要导出成可以直接调用的接口**，测试直接调这些接口；将来 session / Room 只是这些接口的**调用者**。
- 因此引擎保持**纯逻辑**：不依赖 IO、不依赖协议、不依赖挂起机制；遇到需要玩家决策的点，通过**注入的决策者接口**请求输入。

## What Changes

- **对象模型**（`script/engine/`）：
  - **玩家**：身份、体力与体力上限、存活状态、手牌 / 装备区 / 判定区（区域操作与查询）。
  - **桌子**：座位与行动顺序的载体 —— 入座、行动顺序遍历、座位距离计算（遵循「沿桌面两侧取较小值、最小为 1」）。
  - **房间**：一局的装配根 —— 加入玩家、持有桌面与各牌堆、查询当前局面；对外暴露可直接调用的接口。
- **牌堆**：一个基类 + 抽牌堆 / 弃牌堆 / 处理区（放入、取出、洗牌、查看、计数）；随机源可注入，固定 seed 可复现整局。
- **开局装配**：按人数分配身份、洗牌、发牌（起手牌）。
- **回合阶段推进**：准备 → 判定 → 摸牌 → 出牌 → 弃牌 → 结束（本轮只跑通骨架与阶段边界，每阶段保留时机点扩展位；具体牌的效果不在本批）。
- **决策接口**：定义「引擎如何请求玩家决策」的接口（含超时/取消的表达位置），本批由测试里的**脚本化应答者**实现；将来由 Room 内部的挂起机制实现同一接口。

不在本批（用户已定顺序）：**卡牌（牌的定义与效果结算）要先预研**；**技能最后做**。

## Capabilities

### New Capabilities

- `game-objects`: 玩家 / 桌子 / 房间的数据与查询行为（身份、体力、区域、座位、行动顺序、距离）
- `card-piles`: 牌堆基类与抽牌堆 / 弃牌堆 / 处理区的行为（放入、取出、洗牌、查看、计数、可复现性）
- `game-setup`: 开局装配（身份分配、洗牌、发牌）
- `turn-flow`: 回合阶段推进骨架（阶段顺序、当前回合角色、阶段边界的可查询性）
- `engine-decisions`: 引擎请求玩家决策的接口契约（依赖注入；引擎不依赖 session / IO）

### Modified Capabilities

（无。`openspec/specs/` 现有 `headless-server` 与 `async-io` 两个能力，本批不修改它们。）

## Impact

- **新增**：`script/engine/`（对象与流程骨架）、`test/engine/`（单元测试）。
- **修改**：`script/moe-kill.lua`（`moe.engine` 门面挂上这些接口）。
- **不改**：`script/server/`（Session 原样保留、暂时无人依赖）、`script/async-io.lua`、协议层、前端。
- **文档**：`sanguosha-rules` 技能里「决策点统一走请求输入→挂起→恢复」的主语从"统一外壳"改为 **Room 内部**；`architecture.md` 补「引擎接口可直接调用」这条验收口径。
- **默认口径**（按标准版取自 `sanguosha-rules`，如与你的口径不同请指出）：身份配置按人数表、主公体力上限 +1、先手为主公、每回合摸 2 张、洗牌用可注入随机源。
