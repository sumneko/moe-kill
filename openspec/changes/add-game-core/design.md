# Design

## Context

用户确定的顺序：**先做一局游戏的对象与流程骨架（房间 / 玩家 / 桌子 / 牌堆 / 开局装配 / 回合阶段），并做好单元测试；session 与挂起机制最后再把它们串起来**，且前面这些功能点都不得依赖 session。

已归档的 `headless-server`（`script/server/`）本批不动，也不被依赖。当前 `script/engine/` 只有一个空表，是本次的落点。

硬约束（用户明确）：**每一项能力都要导出成可以直接调用的接口**；测试直接调这些接口，将来 session / Room 只是这些接口的调用者。

## Goals / Non-Goals

**Goals:**

- 引擎侧的对象与流程骨架可用**纯同步接口**驱动，无需会话、协议、网络或挂起。
- 需要玩家决策的点通过**注入的决策者接口**表达，测试用脚本化应答者即可跑通。
- 随机源可注入，相同 seed + 相同决策序列 → 相同局面。

**Non-Goals:**

- 卡牌定义与效果结算（**用户要求先预研再做**）；技能系统（最后做）。
- 会话外壳、协议、网络、前端。
- 身份信息隔离（"身份牌除主公外均隐藏"属于对外可见性问题，留到协议层）。
- 任何形式的协程让出（让出是决策者实现方的事，见 D3）。

## Decisions

### D1 落点与门面：`script/engine/` + `moe.engine`

对象与流程都放 `script/engine/` 下（玩家 / 桌子 / 房间 / 牌堆 / 装配 / 阶段），由 `moe.engine` 挂载。**不新建 `script/game/`**：那一层是"把协议方法翻译成引擎操作"，本批不涉及。

### D2 每一项能力都导出成可直接调用的同步接口（用户硬约束）

- 引擎方法都是**同步**的：不 `yield`、不 `await`、不开协程。
- 状态只放在对象实例上（房间 / 桌子 / 玩家 / 牌堆），不使用模块级全局状态，保证一个进程里可以同时存在多个房间互不影响。
- 测试的写法就是"建房间 → 调接口 → 断言对象状态"，不需要任何外壳。

### D3 决策者接口：注入 + 同步签名，挂起留给实现方

```lua
---@class Engine.Decider
---@field decide fun(self: Engine.Decider, room: Engine.Room, request: Engine.Request): ...
```

- 引擎发起请求时构造 `{ kind, payload? }`（**刻意与 `headless-server` 的"待处理事项"同形**，将来 Room 把 session 封进来时可直接复用）；返回值即决策结果，**支持多个值**。
- 本批实现：**脚本化应答者**（预置答案队列，可按序弹出；队列空则报错），供单元测试使用。
- 将来实现：Room 内部用挂起机制实现同一签名（内部 `moe.await.yield` 让出当前协程）——**引擎侧的调用代码一行都不用改**，因为"让出"发生在被调用的实现内部。
- 未注入决策者而进入决策点时：以明确错误暴露（不代选、不阻塞）。

这样"引擎不依赖 session"是真的成立：引擎只依赖一个自己定义的、同步签名的接口；挂起与否是实现方的自由。

### D4 桌子：座位与行动顺序，距离是求值

- 桌子持有座位数组（座位序号 = 入座顺序），行动顺序遍历**跳过已阵亡玩家**。
- 座位距离 = `min(顺时针, 逆时针)`，最小 1；修正来自玩家身上的"距离修正值"（本批由测试直接设置，将来由装备 / 技能修改），修正后仍最小 1。
- 距离是**求值函数**，不是缓存字段（装备变化后必须立即反映）。

### D5 牌堆：一个基类 + 三个子类

- `Pile` 基类：放入 / 取出 / 查看 / 计数 / 是否为空；对空牌堆取牌等非法操作**明确失败**，不静默返回 `nil`。
- 子类：`DrawPile`（按固定顺序取顶、可洗牌）、`DiscardPile`（收弃牌）、`ProcessingArea`（结算临时区，可整体清空）。
- 牌实例 `Card` 本批**只有一个唯一标识**（外加一个供测试断言的标签），定义（名称 / 花色 / 点数 / 效果）属于配置，留到卡牌批次；这样"牌堆能跑"不会被"卡牌定义没做完"卡住。

### D6 随机源：自带可实例化的伪随机数发生器

不使用全局 `math.random` 状态（多房间会互相干扰、也不便于复现）。引擎自带一个可实例化的伪随机源（按 seed 构造），洗牌用 Fisher–Yates 消费它；房间持有自己的随机源实例。

### D7 阶段推进接口

- `room:getPhase()` / `room:getTurnPlayer()` 查询；
- `room:enterNextPhase()` 推进一步（顺序固定：准备 → 判定 → 摸牌 → 出牌 → 弃牌 → 结束），走完结束阶段即交接给下一位存活玩家；
- 每个阶段的开始 / 结束都是可枚举的时机名（本批只提供枚举与查询，不挂技能）。

### D8 需要决策的阶段通过 D3 的接口表达

- 摸牌阶段：默认摸 2 张（直接执行，不需要决策）。
- 弃牌阶段：手牌数超过当前体力时，通过决策者请求一次 `kind = 'discard'` 的决策，把结果作为弃置结果应用；**引擎不代选**。

### D9 命名

代码标识符用英文（与现有代码一致），文档与断言描述用中文术语（牌堆 / 抽牌堆 / 弃牌堆 / 处理区 / 桌子 / 座位）。

## Risks / Trade-offs

- **[接口过早固化]** → 本批只承诺"可直接调用的同步接口"这一条硬约束；具体方法名可随卡牌 / 技能批次演进（规格描述行为，不锁死实现）。
- **[决策形状与将来的会话不一致]** → D3 刻意复用 `{ kind, payload? }` 同形结构，Room 封装 session 时无需翻译。
- **[复现性被全局状态破坏]** → D6 自带随机源 + 状态只在实例上，避免全局 `math.random`。
- **[把"卡牌"提前做了]** → D5 把牌实例压到只有唯一标识，卡牌定义与效果仍要等预研。
- **[阶段推进被写成"一路跑到底"]** → 本批只做单步推进（`enterNextPhase`），需要决策的点显式走 D3，不能顺手写死流程。

## Migration Plan

纯新增：`script/engine/` 下的新文件 + `moe.engine` 挂载 + `test/engine/` 测试。回滚即删除新增文件并还原 `moe.engine` 那一行。

## Open Questions

- **起手牌数**：按标准 4 张？（规格里写死为"配置的起手牌数"，默认值待确认）
- **默认人数**：实现覆盖 4~10 人的身份配置表（来自 `sanguosha-rules`）；测试默认用 4 人，是否符合预期？
- **初始体力**：默认等于体力上限（主公 +1 后），是否有例外？
- **身份信息隔离**：本批不做（留协议层），确认？
- **洗牌范围**：本批牌只有唯一标识，洗牌即洗这些实例；花色点数参与洗牌要等卡牌批次。
