# Design

## Context

- 现状：`package/基础`（默认值、`体力` / `体力上限` 属性、按牌表建堆洗牌）是「没有它就没法开局」的包，但**每个调用方都得在清单里手写它**：`load { '基础', '身份场', '标准' }`；漏写就只会在跑「游戏-开始」时表现为「状态没写」（回调报错被时机机制记录，见已归档的 `game-events`）。
- 已归档的规则集加载能力：来源列表（`package-vfs`）把多个来源合并成逻辑树；包 = 逻辑路径第一层目录（`add-package-routing`，已实现待归档）；清单是唯一入口（`rule-loading`）。
- 用户口径（2026-09-19）：`基础` 这类包做**特殊处理** —— 在名字前加 `@` 表示**默认加载**；`rule.depends` 里**不写**这个 `@`。

## Goals / Non-Goals

**Goals:**

- 用**来源侧的一个标记**表达「这一包默认加载」，清单与依赖都不再提它。
- 标记 MUST NOT 泄漏进逻辑名：清单、依赖、限定名、元信息里看到的永远是 `基础`。
- 顺序与去重可预期：默认包在前、彼此按逻辑名排序、与清单项合并后同一文件只执行一遍。

**Non-Goals:**

- **不做**「按名字关掉某个默认包」的开关（要排斥就写互斥 `!基础`）。
- **不做**按包设置更细的加载策略（先加载 / 可选 / 优先级…），只有「默认加载」一种。
- **不做**清单语法糖（如 `load { '@身份场' }`）——标记只放在**来源目录名**上。

## Decisions

### D1 标记放在**来源目录名**上

- 清单项与依赖项用的都是**逻辑名**（`基础`），而逻辑名是唯一标识 —— 在这里加标记会污染所有引用点（用户明确要求「depend 的时候不用写这个 @」）。
- 来源目录名是**唯一**既能做标记、又不进逻辑名的位置（`package-vfs` 已经在做「目录名 → 逻辑第一层」的映射）。附带好处：**来源可整体替换**，所以第三方可以替换掉带标记的那一包（`setRoots { './package/*', 'D:/我的基础包' }` 之类）。
- 备选（未采纳）：清单语法糖 `{ '@基础' }` —— 只解决清单、解决不了依赖，且要求加载器解析 `@`；写在**文件**名上（`@配置.lua`）—— 文件级「默认加载」没有语义（包不进清单时它的文件根本不会被枚举）。
- 标记沿用用户给的 `@` 字符。

### D2 在 vfs 层剥离 `@`（逻辑名唯一，引用点全都不用改）

- `vfs` 枚举来源时：来源目录名以 `@` 开头 ⇒ 记录「该逻辑包默认加载」+ 逻辑第一层用**去掉 `@`** 的名字。于是 `rule.depends`、`rule.card` 的包名、`getPackageMeta`、裸名路由**一行都不用改**。
- `@` **只认第一个字符**：`a@b` 这类名字不受影响。
- 目录名只有 `@`（后面没名字）⇒ 报错（会得到空逻辑名）。

### D3 `@` 只允许出现在第一层，位置错了就报错

- 逻辑路径的**非首段**出现以 `@` 开头的名字（包内子目录、文件名）⇒ 加载报错，并指出这个逻辑路径。
- 理由：标记只在包一级有意义；不校验的话会出现「看起来在标记、其实一点用都没有」的写法（比报错更难查）。
- 校验点放在**加载文件时**（`loadFile`），因为「有没有这种名字」只有引用到才会被枚举；错误信息给出逻辑路径。

### D4 顺序：默认包在前，彼此按逻辑包名排序

- `load(清单)` 的最终顺序 = **默认包（按逻辑名升序）** + 清单项（原样）。这样「基础先于内容包」是稳定的，不依赖清单怎么写。
- 与清单**合并后去重**沿用既有的「同一文件只执行一次」：显式写进清单也不会执行两遍。
- 多个默认包之间有依赖时仍由 `rule.depends` 定序（依赖是执行到那行时同步加载），所以排序只影响「谁先被扫到」，不影响正确性。

### D5 多个来源都带标记时：**任一来源带标记即为默认加载**

- 「标记只增不减」：同一个逻辑包，只要有一个来源写了 `@`，它就是默认加载的包。
- 取舍：另一种做法是「按来源顺序，最后一个来源说了算」（与文件级覆盖同构），但那会出现「后一个来源只想覆盖文件、却顺手关掉了默认加载」这种难解释的行为；`@` 表达的是「这个包是基础」这一**意图**，用「或」更贴近意图，也更好解释。
- 要真的关掉，改自己目录的名字即可（或者不引入带标记的来源）。

### D6 不做排除开关

- 排斥某个默认包的正确写法是**互斥声明**（`rule.depends { '!基础' }`），已有能力，不必再开一个「按名字排除」的入口。
- 也避免出现「同一个包既默认加载又被排除」的第三种状态需要定义。

## Risks / Trade-offs

- [目录名以 `@` 开头在编辑器 / 终端里不常见] → 只在 `package/` 这一层用一次（目前只有 `@基础`）；文档写清楚含义。
- [`@` 是新的保留前缀，可能与用户自己的目录名冲突] → 只认**开头第一个字符**；位置不当（第二层以后）会明确报错而不是静默忽略。
- [默认包自动加载让「清单是唯一入口」这条口子开了] → 只对**带标记**的包开口，且顺序确定；清单仍然是唯一能引用任意包的地方。
- [默认包与清单项都想控制顺序时会打架] → 默认包恒在前，内容包之间用清单顺序；需要更细的顺序就写 `rule.depends`。

## Migration Plan

- 数据：`package/基础` → `package/@基础`（`git mv`，文件内容不变）；`package/身份场/开局.lua` 的 `rule.depends { '../基础' }` **保持不动**（正好验证「引用不写 `@`」）。
- 调用方：清单里的 `基础` 可以删掉（留着也不报错、不会执行两遍）；测试里的清单接着删。
- 回滚：把目录名改回去、去掉 vfs 的剥离逻辑即可，无数据迁移。

## Open Questions

- 将来若出现第二个「默认加载」的包（例如国战的自有基础），是否需要「按模式选择哪些默认包参与」——等真有这个需求再定（现在用来源 / 互斥表达）。
