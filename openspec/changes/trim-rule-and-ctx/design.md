# Design

## D1 为什么统一成「建实例总是加载」

`packages` 的可省有两种做法：省了**不装**（现状）或省了**装默认包**（场地现状）。选后者：

- 默认加载标记（`@基础`）的用意就是「这包总要装，别每次都写」；那么「什么都没给」最自然的含义就是「只装那些总要装的」。
- 场地省略 `packages` 就是这么做的。两处一致后，`moe.rule.create {}` / `room.create { desk, random }` 都是「一局最小装配」，不必再记例外。
- 想装别的包就 `rule:load(清单)`（清空重载），或建实例时给 `packages` —— 能力没有减少，只是「不给」的默认含义变了。

## D2 场地与规则实例的相互引用

`rule:getRoom()` 要求规则实例知道自己的场地，于是两者互指（场地 → 规则：`room:getRule()`；规则 → 场地：`rule:getRoom()`）。Lua 的 GC 处理循环引用没有问题，这是**一局游戏内部的自然双向关系**，不做弱引用之类的花活。

绑定顺序：**先建场地对象（此时还没有规则）→ 用它建规则实例（`moe.rule.create { room = 场地, ... }`）→ 再装回场地**。这样规则实例**从建出来那一刻起**就有场地（加载期代码也能 `rule:getRoom()`），不存在「绑之前」的窗口；代价是场地对象在工厂里分两步填字段，可以接受。

`getRoom()` 在没有场地时报错（而不是返回 `nil`）：独立建的实例（测试、将来「先建规则试跑」这类用法）确实会缺场地，属于**运行期真的会缺**的情况，报错比让调用方拿到 `nil` 后再炸更清楚。

## D3 上下文的定位：只承载事件参数

- 上下文 = **这个时机对外声明的事件参数**。`'游戏-开始'` 没有参数 ⇒ 空表；将来 `'伤害-后'` 就是 `{ 目标, 伤害值 }` 这类。
- **环境对象不进上下文**：场地（以及它提供的桌子 / 随机源）属于**这一局的规则实例**，从 `rule:getRoom()` 取。于是包不必记住「桌子、随机源、场地分别挂在 ctx 的哪个字段」，将来 ctx 增删事件参数也不会把它们挤出去。
- `env-meta.lua` 里 `'游戏-开始'` 的上下文类型就写成**空类**（`---@class Moe.Rule.EventCtx.游戏开始`，不声明字段）—— 类型仍然存在，方便将来补字段，也保持「每个时机一条类型」的写法。

## 被否掉的方案

- **让 `ctx` 里同时留环境对象与事件参数**（先兼容一段时间）：两套写法会长期并存，规则包与文档都会分叉。
- **`rule:getRoom()` 返回 `nil` 而不是报错**：调用方每次都得判空，且「忘了绑场地」会退化成 `attempt to index a nil value`，比明确报错更难查。
