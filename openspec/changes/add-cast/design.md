# add-cast

## D1 为什么是「一个效果」而不是「发个通知」

用户 2026-10-01 定：这是**归因**，不是播报。我们现有的归因通道就是 `Effect.parent`（结算嵌套链）+ 记牌器（根效果），所以正确落点是**让「发动」成为一次结算** —— 里面起的动作（`moveCard`）天然挂在它下面，事后 `move.parent.source` 就追得到，不必另建一套记录。

形状由用户给出：`skill:cast(function () … end)`。

## D2 `Cast` 的两条通道各自由两个入口算

| | `Skill:cast` | `Card:cast` |
| --- | --- | --- |
| `source` | 技能实例 | 那张牌 |
| `from` | `skill.owner` | `card:getZone()?.owner` |

用户口径：「`from` 应该可以从技能或卡牌上获取」—— 所以 `Cast` 不自己分辨 `source` 的类型（那要靠「有没有 `owner` 字段」猜，脆），而是让**各自知道答案的入口**把 `from` 算好传进来。

## D3 它是一个普通效果

- 照跑「效果-能否生效」三段（用户：「跑呗」）—— 这多半是好事，将来「技能无效」那类可以在这里拦。
- **在时机回调里调 ⇒ `parent` = 那次结算 ⇒ 不是根 ⇒ 不进记牌器**（用户本来就要这个结果）。
- 平地上调（比如装配侧直接发动）⇒ 是根 ⇒ 照旧进记牌器，符合既有口径。
- 嵌套深度只 +1（逻辑层），扁平调度之后 C 栈不涨 ⇒ 无风险。

## D4 记牌器的名字

用户 2026-10-01 指出「那个所谓的记牌器名字起的不好」—— 它其实是**根效果列表**（只收 `parent == nil` 的）。本次**不改**它（名字与口径都留给以后），只是确认 `Cast` 的语义与它无关：`Cast` 待在该待的位置（作为响应挂在链上）。
