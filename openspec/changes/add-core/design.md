# Design

## Context

用户确定的顺序与分界线：**先做内核（core）并单元测试，规则集与 session 都排在后面**；「目前的实现应该和游戏流程规则完全无关」。

追加口径（用户拍板）：

- **牌区是通用容器**，内核不写死是什么区域（手牌 / 装备 / 判定在 core 眼中没有区别）；具体功能差异（如可见性）做成**区域参数**并通过接口修改；支持**动态添加 / 删除 / 禁用**。
- **牌堆与区域合并成同一套抽象**（一个基类 + 参数 + 少数能力），手牌区 / 装备区 / 判定区 / 抽牌堆 / 弃牌堆 / 处理区都是它的实例。
- **接入 `sumneko/utility` 的 `attribute` 库**做通用属性；属性名与公式由调用方（将来的规则集）定义，内核不预设。
- 玩家叫 `Player`；房间不设人数上限。
- **规则集目录**：项目根 `game/`（中文包名，如 `game/基础规则/`、`game/卡牌包/标准/`），与 `script/` 平级；本批只建立目录与加载路径，不实现规则。

现状：`script/engine/` 只有一个空表（`---@class Engine`）。本批改名为 `script/core/` 并填入内容；已归档的 `headless-server`（`script/server/`）不动也不被依赖。

## Goals / Non-Goals

**Goals:**

- 内核对象可用**纯同步接口**驱动：测试建房间、调接口、断言对象状态，不需要会话、协议或协程。
- 内核与规则彻底分离：没有具体区域名、没有具体属性名、没有"张数 / 顺序 / 时机"默认值。
- 牌区、属性、随机源三者都可注入、可组合、可单测。

**Non-Goals:**

- 开局装配（身份 / 起手牌数 / 发牌 / 先手）、回合阶段推进、牌的效果与结算、技能、规则集内容。
- 决策者接口：内核没有流程，本批没有消费者，留到规则批次。
- 会话外壳、协议、网络、前端；身份信息隔离（属对外可见性，留协议层）。
- 牌的定义（名称 / 花色 / 点数 / 效果）——属配置，后续批次。

## Decisions

### D1 落点与门面

- `script/engine/` → `script/core/`（`---@class Engine` → `---@class Core`），门面 `moe.core`。
- **规则集放项目根 `game/`**，与 `script/` 平级：`game/` 是"内容/包"，`script/` 是"代码根"（引导、内核、会话、工具）。依赖方向只能是 `game/ → script/core`，内核永不反向依赖 `game`。
- `make/bootstrap.lua` 的 `package.path` 补 `game/?.lua`、`game/?/init.lua`，使 `require '基础规则.主公'` 这类包路径可用。
- 不把 `script/` 改名为 `core` / `server`：它同时含 `tools/`、会话外壳、引导与调试，改名名不副实且要动引导脚本。

### D2 内核与规则的分界线（本批最重要的约束）

判断标准：**出现"具体区域名 / 具体属性名 / 张数 / 顺序 / 时机"这类规则内容，就越界了**。

- 内核提供：通用容器与访问器（牌区放入取出、属性读写、座位距离求值）。
- 规则集将来提供：`发一手牌`、`开局`、`进入下一阶段`、`结算某张牌`、`主公体力上限 +1` 这类**组合动作与默认值**。
- 测试场景由测试**自己组合内核接口**搭出来（连续取牌 + 放入牌区即"发牌"），这同时验证内核没有夹带规则。

### D3 牌区：一个基类 + 参数 + 能力标记

- 基类 `Zone`：放入 / 取出 / 查看 / 计数 / 列举 / 清空；对空区取牌等非法操作**明确失败**。
- **区域参数**：不透明键值（如可见性、归属），内核只保存与读取，不解释含义。
- **动态增删禁用**：玩家持有一组牌区，可添加 / 删除 / 禁用 / 启用；被禁用的牌区不出现在默认列举中，对其操作明确失败。
- **有序能力**：声明了"有序"的牌区（如抽牌堆）支持取顶与洗牌（消费注入的随机源）；未声明该能力的牌区被要求取顶/洗牌时明确失败。
- 手牌区 / 装备区 / 判定区 / 抽牌堆 / 弃牌堆 / 处理区**都是它的实例**，名字与用途由调用方决定。

### D4 属性：接入 `attribute` 库，内核不预设属性名

- 照搬 `sumneko/utility` 的 `attribute.lua` 到 `script/tools/attribute.lua`（照搬区，**不要随便改**），并在 `moe-kill-dev` 技能的 `tools/` 清单里登记来源与版本（该文件在 LuaLS 4.0.0 里没有，属通用能力库上游）。
- 内核只做**接入**：调用方先声明属性（名字、上下限、公式），再创建实例；玩家持有的就是这样一个实例。
- 因此"体力 / 体力上限"**不在内核里**：它们是规则集声明的属性名。
- 备选与取舍：自己写一套属性系统——否决，`attribute` 已提供上下限、公式、惰性重算与变更事件，且是本项目工具的既定来源。

### D5 桌子：座位与行动顺序，距离是求值

- 座位序号 = 入座顺序；行动顺序遍历跳过"不参与行动"的玩家（规则层把"阵亡"映射为该标记）。
- 座位距离 = `min(顺时针, 逆时针)`，最小 1；修正值由调用方设置，修正后仍最小 1；距离是**求值函数**不是缓存字段（装备/技能变化必须立即反映）。

### D6 随机源：自带可实例化实现

不使用全局 `math.random` 状态（多房间互相干扰、也不便复现）。内核自带按 seed 构造的随机源，采用 `DrawPile` 洗牌消费它；房间持有自己的实例。

### D7 命名与目录

- 代码标识符用英文（`Core` / `Room` / `Player` / `Table` / `Zone` / `Card` / `Random`）；规则集目录用中文（`game/基础规则/`）。
- 内核在 `moe.core` 下扁平挂载（`moe.core.room` / `player` / `table` / `zone` / `card` / `random` / `attribute`）。

## Risks / Trade-offs

- **[内核被规则污染]** → D2 的可执行判断标准 + 测试里"自己组合接口发牌"的用例。
- **[统一容器后概念过多]** → 牌区只有"参数 + 一个有序能力"两处变量，其余行为共用；不引入继承树深层结构。
- **[照搬 `attribute` 与上游分叉]** → 保持原样照搬，不改；如需改动先问用户，并在 `tools/` 清单登记。
- **[`game/` 中文路径]** → 已实测项目支持 UTF-8 路径（构建产物路径含中文亦可运行）；`require` 走 `package.path`，不依赖文件名 ASCII。
- **[牌实例过于简陋，将来要改]** → 只承诺"唯一标识 + 标签"，牌定义批次再扩展（加字段，不改语义）。

## Migration Plan

改名 + 纯新增：`script/engine/` → `script/core/`、新增 `script/core/*`、`script/tools/attribute.lua`、`game/`（目录 + README）、`test/core/`、`moe.engine` → `moe.core`。回滚即还原目录名与门面那一行，并删除新增文件。

## Open Questions

- 规则集目录首版放哪些占位（`game/基础规则/`、`game/卡牌包/标准/`）？本批只建目录与 README，内容等你开规则批次时定。
- 属性实例由谁创建：玩家创建时由调用方传入"已声明好属性的系统"，还是玩家内部按默认系统创建？（我倾向前者：属性集属于规则，必须由调用方提供）
- 牌区的有序能力用"参数"还是"子类"表达？（我倾向子类 `DrawPile`，其余能力走参数）
