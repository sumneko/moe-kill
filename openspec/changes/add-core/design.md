# Design

## Context

用户已确定实施顺序：**先把内核（core）做出来并单元测试，规则与 session 都排在后面**，且明确要求「目前的实现应该和游戏流程规则完全无关」。

内核的定位因此是**纯对象与容器**：它认识玩家、座位、牌区，但**不认识**起手牌数、身份配置、谁先手、阶段顺序。已归档的 `headless-server`（`script/server/`）本批不动，也不被依赖。当前 `script/engine/` 只有一个空表（`---@class Engine`），本批改名为 `script/core/` 并填入内容。

## Goals / Non-Goals

**Goals:**

- 内核对象可用**纯同步接口**驱动：测试建房间、调接口、断言对象状态，不需要会话、协议或协程。
- 内核与规则分离：凡是"多少张、什么顺序、什么时机"的默认值都不进内核。
- 随机性可注入、可复现，且多房间互不干扰。

**Non-Goals:**

- 开局装配（身份分配 / 起手牌数 / 发牌 / 先手）、回合阶段推进、牌的效果与结算、技能。
- 决策者接口：内核没有流程，本批没有消费者，留到规则批次与阶段推进一起设计。
- 会话外壳、协议、网络、前端；身份信息隔离（属对外可见性，留协议层）。
- 牌的定义（名称 / 花色 / 点数 / 效果）——属配置，后续批次。

## Decisions

### D1 落点与门面：`script/core/` + `moe.core`

- `script/engine/` → `script/core/`（`---@class Engine` → `---@class Core`），`moe.engine` → `moe.core`。
- 不新建 `script/game/`（协议翻译层）也不现在定规则层目录名（规则层后续批次再定，见 Open Questions）。

### D2 内核与规则的分界线（本批最重要的约束）

判断标准：**只要涉及"张数 / 顺序 / 时机 / 身份"这类规则默认值，就不属于内核**。

- 内核提供：容器与访问器（`player:addHandCard`、`drawPile:draw`、`table:distance` …）。
- 规则层将来提供：`发一手牌`、`开局`、`进入下一阶段`、`结算某张牌` 这类**组合动作**。
- 测试里的场景由测试**自己组合内核接口**搭出来（连续取牌 + 加手牌即"发牌"），这也正好证明内核没有偷偷夹带规则。

### D3 桌子：座位与行动顺序，距离是求值

- 座位序号 = 入座顺序；行动顺序遍历跳过已阵亡玩家。
- 座位距离 = `min(顺时针, 逆时针)`，最小 1；玩家身上的"距离修正"由调用方设置（将来由装备 / 技能设置），修正后仍最小 1；距离是**求值函数**不是缓存字段。

### D4 牌堆：一个基类 + 三个子类

- `Pile` 基类：放入 / 取出 / 查看 / 计数 / 是否为空；对空牌堆取牌等非法操作**明确失败**。
- 子类：`DrawPile`（按顺序取顶、洗牌）、`DiscardPile`、`ProcessingArea`（临时区，可整体清空）。
- 牌实例只承载**唯一标识 + 标签**，不携带任何牌的定义信息；这样"牌堆能跑"不会被"牌定义没做完"卡住。

### D5 随机源：自带可实例化实现

不使用全局 `math.random` 状态（多房间互相干扰、也不便复现）。内核自带按 seed 构造的随机源（取范围整数 / 取元素 / 洗牌），洗牌消费它；房间持有自己的实例。

### D6 决策者接口移出本批

原计划里的 `Engine.Decider`（注入式决策请求）在本批**没有消费者** —— 内核不含流程，没有任何地方需要请求玩家决策。它和"进入下一阶段""结算一张牌"同属规则批次，届时再设计（形状仍建议复用 `headless-server` 的 `{ kind, payload? }` 同形结构）。

### D7 命名

代码标识符用英文（`Room` / `Player` / `Table` / `Pile` / `Random`），文档与测试描述用中文术语（房间 / 玩家 / 桌子 / 座位 / 牌堆 / 抽牌堆 / 弃牌堆 / 处理区）。

## Risks / Trade-offs

- **[内核被规则污染]** → D2 给出可执行的判断标准（出现"张数/顺序/时机"默认值即越界），并在测试里用"自己组合接口发牌"钉住。
- **[牌实例过于简陋，将来要改]** → 只承诺"唯一标识 + 标签"，牌定义批次再扩展（扩展是加字段，不是改语义）。
- **[改名影响面]** → 只涉及 `script/engine/` 目录、`moe-kill.lua` 两行、技能文档两处、以及 `setup-backend-infra/design.md` 一句过期描述；`headless-server` / `async-io` 主规格不受影响。
- **[距离修正的归属含糊]** → 内核只按调用方设置的修正值求值，不判断修正从哪来（装备 / 技能属规则层）。

## Migration Plan

改名 + 纯新增：`script/engine/` → `script/core/`，新增内核文件与 `test/core/`，`moe.engine` → `moe.core`。回滚即还原目录名与那一行门面。

## Open Questions

- **装备区 / 判定区算内核还是规则？** 暂按内核（它们是玩家的固定容器，容量与含义由规则层决定）。
- **标签字段的命名**（暂用不透明 `role`，规则层赋值）是否合适？
- **体力上限**：内核只提供"受上限约束"的计数器、具体数值由调用方设置 —— 认可吗？
- **房间是否需要"玩家上限 / 座位数上限"**这类概念？（我倾向不做，由调用方控制加入数量）
- **规则层目录名**（`script/rules/`？）与决策者接口的落点，等规则批次再定。
