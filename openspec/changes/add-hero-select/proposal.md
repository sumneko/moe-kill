# 变更：选将流程（`askHero` + `'游戏-准备'` + 武将分类）

## 需求

开局要能**选武将**：装配侧在比 `'游戏-开始'` **更早**的一步（`'游戏-准备'`）里发身份、再让玩家选将 —— 主公先选（备选 = **全部「君主」武将** + 随机 N 张其他武将，不封顶），其余人紧接着按座位依次选（备选 = 随机 N 张；**互斥**、选完公开）。选完剩下的武将就是官方的**武将牌堆**。

为此需要三件内核能力：
1. **武将分类**（`HeroDef` 的 `kind` / `addKind` / `isKind` / `getKinds`，照 `CardDef`）—— 「哪些武将能当主公」靠它认（标准包：曹操 / 刘备 / 孙权，`addKind('君主')`）；**不做继承 / 公共模板**（用户 2026-10-09 定）。
2. **`AskHero`**（新的询问类 + 时机 `'武将-询问'` + `game:askHero`）—— 武将既不是牌也不是角色，单开一个类；左慈那类「看 / 拿别人的武将」将来也归它。
3. **`'游戏-准备'`** —— 比 `'游戏-开始'` 更早的一步（身份要先发，选将才知道谁是主公）。

## 为什么

- 现在**没有选将**：测试里各武将用例靠 `support.start` 的 `beforeStart` 手动 `setHero`；`package/身份场/开局.lua` 的 `'游戏-开始'` 只发身份 + 主公体力加成。**标准包 25 将全做完之后，唯一挡着「真正开一局」的就是这一步**。
- 为什么单开 `askHero` 而不是复用什么：**武将不是牌、也不是角色**（`askCard` 的候选来自牌区、`askPlayer` 的候选来自存活角色）；`askHero` 的候选是**发起方给的一份名单**（`HeroDef[]`），与「选将」和「左慈看别人武将」两种用途都对得上。
- 为什么要 `'游戏-准备'`：底本 `Chapter2/Section3` 把「亮出武将牌」放在「武将牌堆」形成之前 —— 选将**早于**开局；而主公先选要求**身份已发**（`玩家.identity`）⇒ 发身份也得挪到这一步。

## 做什么

1. **内核**：`HeroDef` 加分类（`server/core/hero.lua`）；`AskHero`（`server/core/effect/ask-hero.lua`）+ `game:askHero` + 时机 `'武将-询问'` / `'武将-答复'`；`'游戏-准备'` 的时机声明（`env-meta`，由装配侧 fire，照 `'游戏-开始'` 的先例）。
2. **内容**：曹操 / 刘备 / 孙权 打 `addKind('君主')`；（**选将流程本身**见下一条）。
3. **协议面（`specs/` 增量）**：`askHero` 的条件 / 答复形状 + `'游戏-准备'` 的位置 —— 都是对外契约 ⇒ **不设** `skip_specs`。

## 不做什么（本批）

- **选将流程本身**（`身份场/选将.lua`：备选怎么算、武将牌堆、`{ skip = true }` / `{ heroes = {…} }` 的跳过选项、身份可见性读法）—— 下一批，等内核这层绿了再上。
- **武将继承 / 公共模板**（用户 2026-10-09 定：不用继承，直接给特定武将 `addKind`）。
- **`game:getHeroes()`**（列全部武将）—— 池子由内容侧**显式列名单**（名字与卡牌的「牌表」同理）；真需要再补读法。

## 验收

`server/bin/moe-kill.exe --test` 全绿；问题面板 information 及以上 0；反向验证逐条报数；`openspec validate --all --strict` 通过（本变更**有** specs 增量）。
