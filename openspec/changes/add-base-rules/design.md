# Design

## Context

- 现状：内核有 `Card`（唯一标识 + 不透明标签）/ `Zone` / `OrderedZone`（取顶 + 消费随机源洗牌）/ `Attributes`（`AttributeSystem` + 实例）/ `Random`（可按种子实例化）/ `Event`（时机）；加载器与包路由齐备；`package/` 目录**尚未创建**。
- 已定原则（不要在这些上返工）：内核**不含任何游戏流程**、不预设区域名 / 属性名 / 牌名；距离与范围是**求值函数**不是缓存字段；"发牌等高层动作由调用方组合内核接口完成"；属性**未写入过读数为 0**，下限只在写入时钳制（所以初始化必须显式写入）。
- 用户口径：本批做到「**开局装配跑通**」；牌表本批给；无武将时全体默认上限 4、主公 +1；属性名 `体力` / `体力上限`；主公固定 1 号位、行动顺序按座位号递增；身份按人数表随机（固定 seed 可复现）；人数表 4~8。

## Goals / Non-Goals

**Goals:**

- 一份能开局的规则内容：`package/基础` + `package/身份场` + `package/标准`（牌表），加一次能跑通的开局装配（由测试驱动）。
- 内核补齐坐次与玩家这两个"业务马上要用"的最小形状，且不引入任何游戏流程。

**Non-Goals:**

- **不做**摸牌 / 回合流程 / 出牌阶段 / 胜负判定 / 奖惩（下一个功能点）。
- **不做**武将（体力上限暂时来自规则数值，武将以后接管）。
- **不做**距离修正来源（装备 +1 马 / -1 马）——只留求值形状。
- **不做** Room / 会话 / 协议（装配由测试组合内核接口驱动）。

## Decisions

### D1 规则集执行环境只注入 `rule`（内核能力经规则层收口）

- **规则包 MUST NOT 直接调内核**（用户 2026-09-19 定）：注入面只有 `rule` + 标准库白名单，`core` / `require` / `io` / `os` 与项目内部的其它全局（`moe.util`、`moe.server`）一律不给。
- 规则包需要的内核能力由 `rule` 提供**最小工厂**（不新增游戏语义接口 —— 不下放「牌堆 / 手牌区」这类概念）：
  - `rule:createAttributeSystem()` → 属性系统（包的 `define` 照旧）
  - `rule:createCard(name)` → 牌实例（牌名写进不透明标签，与旧口径一致）
  - `rule:createZone()` / `rule:createOrderedZone()` → 牌区（有序那个即牌堆）
- 理由：分层应当是 `package/ → rule → core`。内容是「规则」，不该认识内核的实现面：内核接口演进时不必直接破包，第三方包看到的也只是规则层明确允许的窄面。
- **装配方不受此限**：测试与将来的 Room 本来就要组合内核接口（`moe.core.*`）来开局 —— 它们不是包。
- 备选（未采纳）：注入内核门面 `core`（早期方案，已被用户否决）；让规则包自己 `require` 内核（注入面白名单不允许，且绕过了规则层）。

### D2 内核最小形状：只加马上要用的

- `Core.Desk`：`create(座位数)`、`sit(座位号, 玩家)`、`getPlayer(座位号)`、`getPlayers()`、`getIndex(玩家)`、`getNext(玩家)`（下一个行动者）、`getDistance(from, to)`。
- `Core.Player`：`create { 属性系统, 名字? }`、`getAttributes()`、`addZone(名字) -> disposer`（可叠加 → 返回 disposer，符合项目约定）、`getZones()`、`setTag(键, 值)` / `getTag(键)` / `removeTag(键)`、`setActing(bool)` / `isActing()`。
- 明确**不加**：装备槽、手牌上限、死亡处理、身份（身份是标签）。

### D3 行动顺序与"参与行动"

- 顺序按**座位号递增**（不按入座先后），跳过空座位与 `isActing() == false` 的玩家。
- "不参与行动"是玩家上的一个标记；内核**不解释**为什么（阵亡、跳过、离场…由规则层置位）。

### D4 距离：当场求值，最小 1

- `getDistance(from, to)`：设座位差 `d = |a - b|`、总座位数 `n`（含空位），距离 = `min(d, n - d)`，再取 `max(1, ...)`。
- 不缓存成字段（既有口径："距离必须动态求值"）；修正来源以后接入（届时给求值加钩子或参数，不破坏调用形状）。

### D5 规则数值（`rule:setValue` 家族）

- 全局**一张**表，键是字符串；`setValue` 单条、`setValues` 批量；`getValue` 未设置返回 `nil`；`getValues` 返回快照。
- **后者覆盖前者**：这是有意提供的"覆盖通道"（国战改血量上限就再写一份配置），与包路由的"同名并存"是两套语义 —— 文档里与 VFS 来源合并一起做对照表。
- 与规则表同生命周期（`load` 时清空）；**不做**类型校验、不做默认值表（默认值写在规则包里，读时 `or 默认`）。

### D6 开局装配留在调用方

- 内核不写流程：装配 = 建属性系统 → 建 Desk / Player / 牌区 → `rule:fire('游戏-开始', ctx)` → 断言。
- `ctx` 里带 Desk 与随机源（只读约定）；`'游戏-开始'`这个时机名由规则包自己约定（内核不认识）。
- 本批用 `server/test/rule/setup.lua` 跑一次 **8 人完整开局**作为验收。

### D7 身份：标签 + 主公坐 1 号位

- 身份写进玩家的**不透明标签**（内核只记录）；身份场的"身份配置"用规则数值承载（可覆盖）。
- 主公**固定坐 1 号位**（用户口径的简化写法），于是"按座位号递增"的行动顺序天然让主公先手 —— 不需要给 Desk 加"起始行动者"概念。
- 主公体力上限 +1 走**改属性上限**（`attrs:add('体力上限', 加成)`? 或 `set('体力上限', 上限 + 加成)`）；实现时按属性系统能力选最小的一步，MUST NOT 直接改体力值。

### D8 牌表：数据在内容包，机制在基础包

- `package/标准/` 提供牌表（每种牌的张数）写到规则数值里（键如 `牌表`）；**花色点数按需再加** —— 到需要判定 / 拼点的时候再补齐数据形状，现在先只放最小可用的一列；
- `package/基础/` 注册「游戏-开始」：读牌表 → `rule:createCard(名字)` 建实例（牌名写进**不透明标签**）→ 放进 `rule:createOrderedZone()`（牌堆）→ `shuffle(随机源)`；牌表缺失时报错（不静默建空堆）。
- 内核全程不认识"杀"、"红桃"这类词。

### D9 体力属性由基础包定义

- `rule:createAttributeSystem()` → `define('体力', { simple = true, min = 0 })`、`define('体力上限', { simple = true, min = 0 })`；
- 「游戏-开始」时**显式写入**体力上限与体力（未写入过读数为 0 是既有口径，必须主动初始化）。

### D10 时机命名与事件参数 meta（用户 2026-09-19 定）

- **命名风格**：时机名用 `分类-动作`（`游戏-开始`、`回合-开始`、`伤害-后`…），前一段是分类、后一段是动作 —— 能让事件列表按分类聚合，也避免中文名长短不一。时机名仍然**不预设**（内核与加载器不认识任何名字），这只是一条**项目约定**（写进 `architecture.md` 与 `sanguosha-rules`）。
- **参数类型集中声明**：新增一个**纯类型 meta 文件**（`server/rule/event-meta.lua`，顶部 `---@meta`，不参与运行），把每个时机的上下文类型与注册/触发的签名写成重载：

```lua
---@class Rule.EventCtx.游戏开始
---@field desk Core.Desk
---@field random Core.Random

---@class Rule
---@field on fun(self: Rule, name: '游戏-开始', callback: fun(ctx: Rule.EventCtx.游戏开始))
---@field fire fun(self: Rule, name: '游戏-开始', ctx: Rule.EventCtx.游戏开始)
```

  - 类名用**去掉连字符**的事件名（`游戏-开始` → `Rule.EventCtx.游戏开始`）：连字符不是合法的 LuaDoc 类型名字符，去掉后既保留可读性又能被分析器识别。
  - 用 `---@field` + 函数类型（而不是 `---@overload`）：同名的多行 `@field` 会被分析器当成多个签名候选，调用点能按字面量事件名收窄 —— 但**必须先确认 LuaLS 不报 `duplicate-doc-field`**（实现时逐条实测，若报就改用 `---@overload` 或联合函数类型）。
  - 这两个 `@field` 声明在 meta 文件里给出**分析器可见的签名**；运行时实现仍在 `server/rule/init.lua`（meta 文件只是类型契约）。

## Risks / Trade-offs

- [meta 文件与实现可能脱钩（改了签名忘了改 meta）] → 任务里把 meta 与实现放在同一节，且类型不完备时调用点会报诊断，能把脱钩暴露出来。

- [`rule` 成了内核能力的唯一出口，接口容易越长越胖] → 工厂按需最小形状（目前只有 4 个）；新增时先问「这是规则层概念还是内核实现细节」，后者不该长在 `rule` 上。
- [主公固定 1 号位是简化假设] → 只写在身份场里，将来要随机座位只改身份场，不动内核。
- [距离不做修正 ⇒ 有装备时要改] → 求值形状已定；修正来源按需加，调用点不变。
- [牌表数据（张数）可能不准] → 本批先落一版并在 tasks 里加"逐条核对"；数据在规则包里，错了只改数据。
- [规则数值是"有意覆盖通道"，容易与包路由的"并存"混淆] → `architecture.md` 第 9 节的对照表补第三行（VFS 来源合并 / 规则数值 / 包路由）。

### D11 失败信号的形状：被时机机制隔离之后

- 已归档的 `game-events` 规定：**单个回调报错 MUST NOT 打断其余回调，也 MUST NOT 让触发本身失败**（错误走 `log.error`）。于是规则包在「游戏-开始」里报错时，`rule:fire()` 仍会正常返回 —— 这是既定机制，不要为了"失败看得出来"去改它。
- 因此本批的失败信号统一成**“状态没写”**：牌表缺失 → 不写 `牌堆`；人数不在配置里 → 不写身份。装配方（将来的开局装配 / 会话）负责在 `fire` 之后断言必需状态是否存在，从而把失败抛给上层。
- 相应地，`add-base-rules` 的两条场景写成"回调报错（被记录）且状态没写"，而不是"触发以错误结束" —— 后者与 `game-events` 相冲突。

## Migration Plan

- 纯新增：两个内核模块 + 门面两个能力（规则数值、四个内核能力工厂）+ 三个规则包目录。回滚 = 删掉这些并在注入面里恢复旧口径。
- 兼容性：既有内核与加载器行为不变（新能力都是加法）。

## Open Questions

- 座位分配是否要支持"随机座位 / 指定座位"（现在主公固定 1 号位）—— 等真的多人开局需求出现再定。
- 体力上限与武将的关系（武将接管上限）—— 做武将时定，本批只留"来自规则数值"的入口。
