## 1 已经跑通的一条链

```
moe.game.create（建局 + 装包）→ '游戏-开始'（建牌堆 / 定义属性 / 分身份）
  → game:runFlow()（回合流程：准备→判定→摸牌→出牌→弃牌→结束）
  → 出牌阶段：game:askUseCard(player, '出牌', { zone = '手牌' })（「使用」的语义由类型携带：候选逐张跑 canUse，用不了的牌不进选项；选项带各自的可用目标；答复到手内核直接把它用出去）
  → game:useCard（canUse 二次校验（含次数）→ 记一次账 → 取出牌 → 牌自己的「使用」钩子（一次）→ 逐目标 CardEffect「生效」（声明 `: skipEffect()` 的牌不发起））
  → 伤害 / 回复（内核只发时机，扣血 / 回血写在 @基础）
  → 濒死求桃（就在这次伤害结算里）→ 死亡 → 奖惩（先）→ 身份场胜负判定（后）→ game:endGame 收掉流程
  （另一条结局：牌堆与弃牌堆都没牌 ⇒ 基础规则就地判平局）
```

  ① **结果与收口分开**：`resolve` / `reject` **只把结果记下来**（不叫回调、不叫醒、不 `Delete`）；「收口」（叫 `_onResolved` / `_onRejected`、叫醒等待者、收掉自己的执行体）**只有 `Task:__del` 会走到** ⇒ **谁 `Delete` 谁收口**。驱动层在**执行体末尾** `Delete(self)`，`cancel` 里也 `Delete`。

  ③ **一个任务一条协程**：`threads: thread[]` → `thread?`（外面没人用、也没有第二处 `execute`）；`execute` 拆成 `executeSync`（立即跑）/ `executeAsync`（先让出一笔调度）。
  ④ **停住自己的执行体**（实测出来的形状）：不能在 `__del` 里让出 —— 让出会把 `runDel` 后面几层收尾（`GCHost:__del` 放掉 GC 绑定）**整段丢掉**（探针：『自己取消自己』『正常跑完』两条路的绑定释放都变成 `false`）；另外「不能关当前协程」也不成立 —— 实测 `coroutine.close(当前协程)` **可以**（不返回、当场终止、挂着的 `<close>` 会跑）。最终写法定为：`cancel` 里 **`Delete` 之后**让出一笔调度，`__del` 早先把「关掉这条协程」**登记到下一笔调度**（新增 `moe.await.wake`：不让出、只登记）⇒ 下一笔先关（协程变 `dead`）、第二笔发现不是 `suspended` 就跳过。被别人取消（挂起中）仍是当帧就地 `close`。

## 3 用户已表态、还没做的方向

- **「视为」机制：产出一张虚拟牌的本事（2026-09-30 讨论；**最小形状已做** = `add-view-as`，见 §1）**：已落地 = 声明对象 `ViewAs`（`player:addViewAs('牌名')` + `'发动'` 钩子）+ 打出族询问**按声明创建顺序依次尝试**（全不成再走实体牌）；【八卦阵】已改写。**已定的形状与口径**：**窗口制**（不是「声明牌进候选」）、**依次尝试**（不是「让玩家挑一个」）、只按牌名匹配（`condition.names`）、不参与 `zone` / `card` / `min` / `max`、**声明不持虚拟牌实例**（牌由内核照声明造）。**素材已做**（2026-09-30，`add-zhangba-spear`）：声明带 `AskCard.Condition`、内核按条件收素材、钩子省略即默认成立；【丈八蛇矛】落地。**候选侧也已做**（同日，`add-view-as-in-use`）：使用族（`askUseCard`）把声明当成一个**选项**，玩家在候选里挑、并在同一份答复里给目标，答复之后内核收素材、造牌。**剩下未做**：① **优先级字段**（现在就是创建顺序，以后显式提供「武将技能 ＞ 装备技能」）；② 可选：产出的牌由内容侧指定「获取目标」以外的目标 / 再入标这类扩展（现在完全靠牌自己的 `'获取目标'`，丈八这级够用）。

- **客户端答错要能正确阻止（用户 2026-09-29 定；内核侧已先吃一遍）**：外部给的答复（协议层解出来的客户端答复、将来的 AI）**答错**的每一种——牌不在候选、目标不在选项、**个数不在选项的 `min` / `max`**、**目标重复**、无目标牌给目标、空答复……—— 服务器都必须**正确阻止**（拒收 / 不生效，不崩、不静默收下）。**内核侧已做（2026-09-29）**：拒收点齐备 + 用例成套（见 §1 最后两条）。**待做**：等**会话 / 协议层**接上来后补**端到端**用例 —— 包括协议解出来的奇怪形状（非玩家 / 乱序 / 超量 / 类型不对）与「拒收之后怎么回话给客户端」的口径。
- **阵亡清算（记，用户 2026-09-28 定）**：角色阵亡 ⇒ 其区域里的牌（判定区 / 手牌 / 装备）置入弃牌堆 —— 延时锦囊那批**不做**，整个记到以后的**「死亡规则」批次**（那批顺带处理「死后判定区里剩的牌留在原地」这个临时状态）。

- **worker / master 与单局模式（用户 2026-09-28 定，已记成变更 `add-worker-mode`，暂不实施）**：一局 = 一个 VM（`bee.thread.create` 起子线程 + 独立 `lua_State`）；**开发与测试直接以 worker 身份进行**（单局模式：只开 worker，不需要 master），等 game 功能做完再加 master（lobby + 调度 worker 开单局）；两种模式共存。worker ↔ master **直接说现有 JSON-RPC**（协议本来就只有请求 / 反向请求 / 通知三种形状，正好是这条边界需要的三种）⇒ master 只转发与调度、不认识牌 / 阶段 / 胜负，**宿主可换**（将来真要进程级隔离就把 worker 丢进子进程，worker 代码不动）。自唤醒通道名**直接拼 `thread.id`**。另外两条同日决定：**「卸载 / 重装」整块不要了**（`game:resetContent()` 与 `install` 的清空重装路径退役 —— 清理手段改成「销毁 VM」）；**包清单在 VM 启动时就定死**（服务器模式 master 传入、单局模式自己做个简单交互来选）。**本变更只记录决策、不实施**；形状 / 取舍 / 关停顺序 / 删除面见 `openspec/changes/add-worker-mode/{proposal,design,tasks}.md`。两个已验证的前提（2026-09-28）：探针实测「起线程 + 载整个内核 ≈20ms、建局 + 开局 ≈13ms、VM 内存 ≈1.4MB、channel 往返 ≈2µs」；`bee.thread` **没有强杀**（退出只能靠入口自己返回）且 `errlog()` 是进程级共享、不带线程 id。
