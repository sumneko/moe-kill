# 架构

## 1. 分层

```
前端（任意实现，默认浏览器 / TS）
    ↕ JSON-RPC（通用协议）
[transport]  帧编解码、连接生命周期、反向请求路由
[proto]      方法名 / 参数 / 返回结构的唯一定义（前后端共用事实来源）
[game]       规则集：项目根 `package/` 按包组织（现有 `基础` / `身份场` / `标准`），只拿注入的 `game`（**这一局的局对象**）与 `Card` / `Depends` / `Class` / `New` / `Extends` / `Delete` 环境函数、加一张共享袋 `rule`（**规则数值与内容数据都挂它**，见 9.7；工具集由默认包 `@tools` 提供）—— 需要的内核对象全从 `game` 取（依赖方向 `package/ → moe`）
[session]    会话外壳：会话容器 + 决策挂起/恢复通道 + 事件收集（`server/session/`）
[core]       内核模块组（`server/core/`）：牌 / 牌区（移动、洗牌；**五个基础区由内核建** —— `抽牌` / `弃牌` / `手牌` / `装备` / `判定`）/ 属性 / 随机源 / 桌子（座位与行动顺序）/ 玩家（牌区、标签）/ **局**（一张桌子 + 一个随机源 + 内核建好的基础牌区 + **这一局的规则内容** + **使用牌的机制**，见第 12 节）/ **效果族**（`core/effect/`：`Effect` 与它的全部子类 —— `Effect` 基类在 `core/effect/effect.lua`）/ 规则装载器（`core/loader/`）（**与游戏流程规则无关**，可直接单测）
[tools]      基础设施：event-loop / await / timer / log / json / inspect / uri / reload …
```

依赖方向只能自上而下，且门面全部**直接挂在 `moe` 上**（`moe.desk` / `moe.game` / `moe.loader` …，没有 `moe.core` 中间层；类名与类型注解**直接用类名本身**，不带命名空间前缀）；**门面（API 表）里只放工厂**（`moe.player.create(game, { … })`），类的方法只能从实例上访问（API 表的类型写成「类名.API」；门面由**模块自己建**：`moe.player = {}`，不再 `local API = {}` + `return API`）。**`core` 不得依赖任何具体规则集内容、会话、协议、网络与任何 IO** —— 它只提供「装载规则」的机制（加载器本身在内核模块组里）；这样内核可以脱离协议与网络被直接驱动。协议方法到规则操作的翻译层属会话/协议批次，目录名待定。

### 1.1 内核知道「功能」，不知道「规则」

「内核与游戏流程规则无关」说的是**内核不做规则的取舍**，**不是**「内核什么都不知道」。内核必须**认识每一项功能的形状**并把它表达出来，只是由规则决定用不用、怎么用：

| 内核必须知道（机制本身） | 内核不需要知道（规则的取舍） |
| --- | --- |
| 牌区有「谁能看见」这件事，且读得出来 | 哪些区域可见、谁看得见谁 |
| 玩家有座位，桌子有行动顺序 | 几人局、首回合谁先、什么条件下跳过人 |
| 牌能移动 / 洗牌、属性有上限 | 「杀」怎么结算、用掉的牌去哪、身份的取值 |

判据：**换个规则集，这个概念还存不存在？**

- 存在性不变、只是取值变（可见性、座位数、体力上限、行动顺序）⇒ **内核功能**：做成**一等字段 / 方法**（`zone.visible` 这类），取值由规则声明。
- 换个规则可能压根没有（「身份」、「弃牌堆」、「杀」这些名字与取值）⇒ **规则内容**：内核只搬运、不解释。

**落点是三层，不是「内核字段 or 标签袋」二选一**（用户 2026-09-30 提醒：规范早改了 —— 大量内核代码已挪进内容包，内容包也能给内核类注入方法与字段，见 9.6）：

| 落点 | 什么时候用 | 例 |
| --- | --- | --- |
| **内核字段 / 方法** | **内核自己**要读它才放这儿（读它才能干活） | `Zone.visible`（发 `'卡牌-进入区域'` 时要判可见性）、`Zone.game`（按定义查内容）、`Desk.players`、`Player.tags` |
| **内容包注入的字段 / 方法**（`Class 'Player'` / `Class('Judge', 'Effect')`，2026-09-28 起可用；用户口径：**少用 `setTag`、直接注入字段**） | 概念**内核不需要读**、但内容侧与协议要读 —— 「换个规则集就不存在」的东西住这一层 | `player.identity`（`身份场/身份.lua`）/ `player.dying`（`@基础/濒死.lua`）/ `player.hero` / `player.sex` / `player.kingdom` 与 `Player:setHero`、`Player:distance`、`Player:enterDying`；`Judge` 这类内容自定义的 `Effect` 子类 |
| **标签袋**（`Player:setTag` / `Effect` / `Phase`） | 只装**临时数据**：一次结算里挂的中间值 | 测试里的记数、结算过程里临时传递的值 |

判据不是「谁写进去的」，而是**有没有名字**：正式字段有类型、拼错编辑期可见、协议层知道该读哪个键；标签袋是任意键值袋，这三样都没有。于是两头都要说清：

- **「内核不认识它」不能当借口把功能塞进不透明袋子**（可见性若做成任意键值袋，表现层与协议没有任何人能知道该读哪个键）；
- **但「内核不认识它」也不等于要往内核加字段** —— 内容包自己注入即可，这正是「把内核代码挪进内容包」的做法（`Dying` 的判定、`HeroDef` 的牌面数据、`distance` 都这么挪的）。

反过来，内核给了字段也不等于在做规则判断，它只是**承载**这个功能。

据此，`Zone` 的通用 `params` 袋（2026-09-23 删）方向是错的：它把「功能性信息」降级成不透明数据。**实际照这个口径落地的是可见性**（2026-09-23）：`Zone.visible`（一等字段，默认 `true`）+ `Zone.owner`（玩家建区时自动记）+ `zone:setVisible(值)` / `zone:isVisibleTo(视角)` —— 内核给字段、内容侧给取值（哪个区是暗的、谁看得见）。**2026-10-09 把 `setVisible` 收成「名单」语义**（用户定：「完全按照参数语义」）：`true` = 所有人、`false` = 无人、给一名或一批角色 = **只有他们**；**`owner` 不再参与可见性**（原来的潜规则「暗区的持有者总能看见」去掉）⇒ 「手牌只对自己可见」现在显式写成 `setVisible(持有者)`，`isVisibleTo` 就是「名单里有没有他」。**`Zone.game` 也是同一形状的字段**（2026-09-24 用户让补上，**必填**）：`Zone:__init(game)` / `moe.zone.create(局)` / `moe.orderedZone.create(局, 随机源?)` 都要给局（与 `moe.desk.create(局, 座位数)` / `moe.player.create(局, …)` 同一口径；公共区由 `game:createZone` 传 `self`、玩家建区也是**建区时就传局**（`Player:addZone` 拿 `self.game`），`bindOwner` 只记归属者 —— 所以拿出来的 `zone.game` 不用判空），`'卡牌-进入区域'` 靠它查内容定义。

## 2. 启动与运行模型

- exe + `bin/main.lua` 引导（照搬 LuaLS 4.0.0）：引导脚本设好 `package.path`，再按参数决定进「服务模式」还是「测试模式」。
- 服务模式：建立 event-loop → 起 transport → 进入事件循环。
- 测试模式：**不建 transport**，直接 `require 'test'`（即 `server/test.lua`）加载测试套件。
- 空闲与等待：循环空闲时**阻塞等待到「下一个定时任务到期」**（没有定时任务则无限阻塞），等待 / 唤醒由 `bee.epoll` 承担（`server/loop-waiter.lua`）；停止走自唤醒通道，不靠轮询也不靠分片。
- **效果与等待**：一次结算 = 一个**任务**（`server/tools/task.lua`），效果体跑在它自己的协程里 —— 所以**结算体与时机回调里可以直接 `await`**（`moe.await.sleep` / `moe.await.yield`，恢复绑在**调用它的那个协程**上；应答方就是这么让出的），要等另一次结算结完用 `效果:await()`。**没有**「让出理由分派」与「让出逐层原样转发」这层机制（`Effect:suspend` 整层已于 2026-09-20 删除，理由：顺序请求、不会有外部打断）。

## 3. 协议设计原则（通用协议，一个后端对接多种前端）

1. **不出现任何前端概念**：协议只描述游戏语义与表现事件；贴图路径、动画时长、音效等由前端自行映射资源 id。
2. **方法命名**统一 `域.动作`（点号分层，如 `Player.Update` / `Player.UpdateCustom`）—— 落点是 `server/proto.d.lua` 的类型声明：**线上消息本身的形状**是 `JSONRPC.*`（通知 / 请求 / 结果 / 错误），**游戏消息**是 `Proto.Notify.<动作>`（`Proto.Update` = 一次玩家数据下发；可取消请求另有 `Proto.Cancelable` / `Proto.Notify.Cancel`），禁止散落在业务代码中拼字符串。
3. **后端权威、前端无状态**：目标合法性、距离、可用操作列表一律由后端计算下发；前端永不自行推导规则。
4. **两种下行数据各司其职**：
   - 事件流（notification）：一次操作产生的表现序列，供前端顺序播放动画。
   - 状态快照（request 的 result）：完整状态，用于开局、重连、纠错。前端不维护权威状态。
5. **需要玩家输入时由后端发起反向请求**（后端 → 前端的 request，前端回 result）。这天然表达「后端挂起等你」，也避免了前端轮询。
6. **每个决策带状态版本号**：后端在下发的请求里带 `version`（或 `seq`），前端提交决策时必须回带；后端据此拒绝过期输入。
7. **可重连**：重连由专门方法（如 `game/syncState`）返回全量状态 + 当前未完成的请求列表，**不依赖重放增量事件**。
8. **协议版本协商**：开局 `initialize` 交换协议版本与客户端能力（照搬 LSP 的做法），版本不匹配时明确报错而非静默降级。

## 4. 数据流（一次玩家操作）

```mermaid
sequenceDiagram
    participant FE as 前端
    participant TR as transport
    participant RM as Room（内含会话外壳）
    participant G as game 规则集
    participant C as core 内核

    FE->>TR: game/submitDecision(version, decision)
    TR->>RM: 分发请求
    RM->>G: 应用决策（规则）
    G->>C: 调内核接口（移动牌 / 读写属性 / 洗牌）
    G-->>RM: 产生的表现事件
    RM-->>TR: 通知 game/event × N
    TR-->>FE: 事件流（播放动画）
    G->>RM: 请求下一次决策（挂起在 Room 内部）
    RM-->>TR: 反向请求 game/requestInput(...)
    TR-->>FE: 请求（渲染可选项）
```

## 5. 重要边界

- 规则集只进 `package/`（项目根）；内核只进 `server/core/`；协议路由与序列化只进 `transport` / `proto`（翻译层目录名待定）。
- 引擎的随机源必须可注入：固定 seed 能复现整局（便于回放、复现 bug、写测试）。
- 事件流是**表现层契约**：一旦下发就应稳定，不能因为前端改需求而让引擎改逻辑。
- 跨线程 / worker 边界只传可序列化 plain data。

## 6. 无头可测（硬性要求）

- 「无前端也能跑完整对局」是验收条件，因此：
  1. 引擎 API 必须是可直接调用的纯 Lua 接口，不经过 JSON-RPC；内核（`server/core/`）的接口同样如此，**场景由调用方自己组合**（例如「发牌」= 抽牌取顶 + 放进手牌，内核不提供「发牌」）。
  2. 决策点走同一套「请求输入 → 挂起 → 恢复」路径，测试用「脚本化玩家 / AI」自动应答，而不是给引擎开测试专用后门。
  3. 另设一层协议契约测试：对 `proto` 里每个方法做编解码往返与错误分支验证，不必真的开 socket。
- 回归口径：改引擎必须能只用测试二进制跑完整对局并复现。

## 7. 外壳接口约定（headless-server）

`server/session/` 是当前唯一的「服务」层，只做容器：它不认识牌、阶段、胜负。规则与协议两边各接一个形状，外壳自身不用改。

### 7.1 逻辑处理器（挂在会话上的规则入口）

- 形状：table + `run(self, session)`（写作 `handler:run(session)`），**入口必须是异步函数**（可被协程承载），否则表现为「会话卡住不动」。
- 约定：入口内用 `session:requestInput(...)` 索取输入、`session:emit(...)` 上报表现事件、`session:finish()` 结束；入口**正常返回也视为结束**。
- 入口抛错：会话转「已中止」，原因可用 `session:getAbortReason()` 取到。

### 7.2 驱动者（给输入的一方）

只需三个动作，测试里的「脚本化驱动者」与将来的协议层实现同一形状：

| 动作 | 说明 |
| ---- | ---- |
| `session:getPendingRequests()` | 读当前**所有**在等的请求（快照，按登记顺序），形状 `{ kind, payload? }` |
| `session:submit(request, ...)` | 答复其中一条（把名单里拿到的那条给它），支持多个值；这条不在名单里时报错 |
| `session:cancelRequest(request, reason?)` | 取消其中一条，挂起方收到取消错误 |

- **可以有很多条请求同时在等**（互不干扰、各自带各自的超时）：`requestInput` 不再独占会话。会话结束 / 中止 / 销毁时，所有挂起方一起被叫醒。
- 事件的形状同为 `{ kind, payload? }`，`session:getEvents()` 返回只读快照（后续发出的事件不会影响已取得的快照）。
- `requestInput` 的第三个参数是超时（秒），超时会以错误交回发起方，不静默卡住。

### 7.3 会话阶段

`pending → running → finished / aborted → destroyed`。`finished`、`aborted`、`destroyed` 都是**终态**，之后任何生命周期操作（启动 / 结束 / 中止 / 提交 / 取消 / 发事件）一律报错；阶段常量在 `moe.server.Phase`。

### 7.4 主循环归属

`server.start()` / `server.stop()` **不接管事件循环**，只做状态标记与日志；主循环仍由入口负责 —— 服务模式由 `main.lua` 常驻，测试模式由 `test.lua` 控制。这样外壳的启停是同步的、可直接被测试驱动，也不会在测试里嵌套启动事件循环。

## 8. 热重载（`moe.reload`）

> **先分清两件不同的事**（用户 2026-09-19 明确要求）：
> - **热重载**（本节）= **开发期**工具：改代码（修 bug）后不重启进程。触发者是开发者。
> - **规则集重载** = **游戏业务**功能：运行期重新装置/切换规则集（清空规则表、重新加载规则集）。触发者是业务侧。
>
> 两者**定位、触发者、生命周期、影响范围都不同**，**不要互相替代、也不要把后者当成前者的一种用法**。规则集加载见第 9 节。

### 8.1 加载方式即边界

- `include 'x'` = **可重载**入口：与 `require` 等价，但会把模块登记进重载集合（登记顺序即加载顺序）。
- `require 'x'` = 一次性加载：**永不参与重载**。因此**不需要**任何名单 / 过滤配置来划分范围。
- **加载顺序由 `init.lua` 维护，模块内不要单独 `require` 自己的父模块**（用户 2026-09-28 定）：一组模块（`core/init.lua` → `core.effect` → `core.effect.*`）在 **`init.lua` 里按依赖顺序 `include`**（父模块写在子模块前面），顺序的真相源只有这一处；子类文件开头再 `require` 一次父模块是**多余的防御**（`include` 本身就是 `require` + 登记 ⇒ 那行只会命中缓存），而且会让人误以为「顺序是在文件里保证的」。内核里那 15 处（`core.effect.*` → `core.effect.effect` / `ask-card`、`ordered-zone` / `slot-zone` → `core.zone`）已于 2026-09-28 删掉。
- 目前只有内核（`core/`）用 `include`（`server/core/init.lua` 逐个登记）；`server/tools/`、`session/`、`loop-waiter.lua` 以及热重载自身一律 `require`，从根上避免基础设施被换掉。
- **日志先就绪**：`log` 实例与 `moe.env` 在 `server/moe-kill.lua` 里创建，位置早于任何 `include`，所以可重载模块里可以直接用 `log.*`，加载器也能用 `log.error` 报错。
- `package/` 规则集**不**走 `include` 也不走 `require`，而由自建加载器读文件执行（第 9 节），因此它从根上不参与热重载 —— 这不是「暂且如此」，而是设计要求。

### 8.2 接口

| 接口 | 说明 |
| ---- | ---- |
| `moe.reload.reload()` | 重载全部已登记模块，返回被重载的模块名列表 |
| `moe.reload.onBeforeReload(cb)` / `onAfterReload(cb)` | 重载前后回调，**返回撤销函数**；回调自动记录注册它的模块，该模块被重载时回调自动注销（不会重复堆积） |
| `moe.reload.isReloading()` | 当前是否正在重载（重载期间回调与模块加载都对真） |
| `moe.reload.getIncludeName(fn)` / `getCurrentIncludeName()` | 反查函数 / 当前加载属于哪个可重载模块（将来按模块清理 timer 与订阅要用） |
| `moe.reload.recycle(cb)` | 立即执行并在每次重载后重跑，同时在重载前回收它登记过的对象 |
| `include 'x'` | 加载并登记；失败**记日志（带堆栈）并抛出错误**（不再返回 `false`）；重载过程中的失败由 `fire()` 用 `pcall` 隔离，不会中断整轮重载 |

触发端（开发期文件监视、前端协议方法）本批**未实现**，只提供接口。编辑器侧靠 `.luarc.json` 的 `runtime.special` 把 `include` 当作 `require` 解析。

### 8.3 语义与限制

- **同名类合并**：重载时 `Class 'X'` 复用**同一张类表**（`tools/class.lua` 的 `declare` → `config:reset()`），因此**已存在的实例立即用上新代码**，无需重建对象。
- 限制一：**删除不生效** —— 合并只覆盖字段，源码里删掉的方法仍留在类表上。所以不要给公共方法改名或删除。
- 限制二：**老实例不会重跑 `__init`** —— 新代码若要求实例多一个字段，老实例没有它，读字段要容忍 `nil`。
- 模块级 `local` 只允许放**不可变常量与纯函数**（如 `random.lua` 的常量、`zone.lua` 的 `slotNameOf`）。
- 现状核对（2026-09-22）：`random.lua` 只有常量与纯函数；`zone.lua` 只有 `slotNameOf` 纯函数；`ordered-zone.lua` 与 `attribute.lua` 只有类表与模块引用 —— 内核已无模块级可变状态（原先唯一的例外「牌 ID 计数器」已改成**局实例上的字段**，见 8.4）。

### 8.4 跨重载存活的数据

必须存活的数据挂到「重载后仍是同一份」的载体上，写成「有则复用」：

```lua
moe._x = moe._x or <初值>   -- 挂在门面表上：写法必须是「有则复用」
```

- **载体一：局实例**（`game` 上的字段）—— 已建好的局跳重载照常可用、`__init` 也不会重跑，所以挂在局上的东西既不会丢也不会被换成新的。**发号器与阶段栈就是这么放的**：`game:nextId()`（局内递增、牌与将来的技能共用）、`game.phase` / `game.phaseStack`（当前阶段与嵌套栈）—— 两者都在 `__init` 里给初值、**不放进 `resetContent`**（重装规则集不应清它们）。属于某一局的数据一律用这个载体，不要往内核级状态上挂。
- **载体二：门面表 `moe`**：它是**内核级、跨局**的数据才开始考虑的地方；这张表在 `server/moe-kill.lua`（入口文件）里建立，而入口只执行一次、dev 重载只重跑 `include` 登记过的模块，所以它**永不重建**。**现在还没有这类数据**（上一条唯一的实例「牌 ID 计数器」已改成局上的字段）—— 要用时按上面的形状写「有则复用」，否则重载会把状态清掉。
- **命名用 `_` 前缀 + 赋值处标 `---@package`**：`_` 只表示「内核内部状态，不是对外接口」（`moe` 是普通表，框架不会碰它，`_` 本身没有语言含义）；真正能拦住跨文件用的是 **`---@package`** —— LuaLS 会把它当「只有这个文件可见」（实测：别的文件访问报「字段 `X` 只能在相同的文件 … 中才能访问」）。本工程没定义过「包」的边界，`package` 退化成按文件判定，与 `---@private` 同效。
- **不要挂类表**：`Class` 的 `Extends` 会把父类**非 `__` 开头**的字段复制给子类（并记入 `extendsKeys`），重载时 `Config:reset` 又把这份拷贝清掉 —— 挂在那种名字上会串到子类、还会在重载时被清掉。`__` 开头能躲开这两件事（框架自己就是这么用的：`__config` / `__getter` / `__keyMap`…），但那是**借框架的私有前缀**，不如压根不挂。
- **也不要挂模块门面**（`moe.card` 这类表）：门面由模块自己建（`core/card.lua` 里 `moe.card = {}`），而 `include` 就是 `require` + 登记、重载时会重新执行模块文件 ⇒ 门面每次都是**新表**，状态挂上去每次都被换掉。实例之所以跨重载照常可用，是因为它们持有的是**类表**（`M._classes` 复用同一张），与 API 表无关。
- `server/core/init.lua` 只写一串 `include 'core.card'`：登记 + 执行模块文件（门面由模块自己建）；`include` 失败会**抛错**（同时已记日志），所以这里不需要再包一层失败处理。

### 8.5 撤销与自动注销的分工

**自动注销是默认，disposer 是例外**（用户 2026-09-19 定）：

在**可重载**模块里注册、且跟着该模块走的东西，重载这个模块时会被自动注销，模块重跑时再自动注册 —— 这种**不要**写 disposer，否则每次重载都会多一层无谓的显式管理。

只有下面两类才需要显式处理：

| 场景 | 做法 |
| ---- | ---- |
| 注册发生在**不可重载**的模块里（回调的 `name` 为 `nil`，永远不会被自动注销，会一直留着） | 用 `onBeforeReload` / `onAfterReload` **返回的 disposer** 精确撤销 |
| 自动注销**盖不到、必须重建或显式释放**的资源（外部系统里的注册、timer、socket、缓存对象…） | 用 `onBeforeReload` **捕获**引用做清理，`onAfterReload` 重建；或直接用 `recycle(cb)`（立即执行 + 每次重载后重跑 + 重载前 `Delete` 登记过的垃圾） |

口诀：**能靠自动注销就不要写撤销；撤销只留给“注销不掉需重建”的资源。**

## 9. 规则集加载（`moe.loader` + `moe.game`）

> 定位：**游戏业务**功能 —— **一局游戏装哪套规则**。装载器（`moe.loader`）是**无状态**的机制：它把一套规则装进**某个局**；内容状态全在**局**（`moe.game`）上，所以改规则（含清空重载）只影响这一局。与第 8 节的**开发期热重载**仍是两条互不相干的通道：不共用登记、不共用回调、不互相替代 —— 区别只在于**装载器与局这两份代码本身**与其它内核模块一样可热重载。

规则集（`package/`）是**内容/数据**：加载方式是**读文件并执行**，MUST NOT 走模块系统（`require` / `include`），因此**被加载的规则集文件**不参与热重载，也不出现在 `package.loaded` 里。契约见 `server/test/rule/init.lua` 与 `server/test/rule/vfs.lua`（规格快照已冻结，见根目录 `AGENTS.md` 的「工作流」）。

### 9.1 落点与外观

- 装载器在 `server/core/loader/`：`init.lua`（`Loader` 模块：`install` / `declareDepends` / 名字路由 / 按预解析结果的执行）、`vfs.lua`（包来源合并成的虚拟文件系统）、`preparse.lua`（试跑）、`env-meta.lua`（纯类型文件：注入的 `game` / `Card` / `Depends` / `Class` / `New` / `Extends` / `Delete` / `rule` 与各时机上下文）。**局**在 `server/core/game.lua`（`Game` 类）。
- `server/core/init.lua` 里与其它内核模块一样 `include 'core.game'` / `include 'core.loader'`（门面 `moe.game` / `moe.loader` 由模块自己建；两份都可热重载）。
- `moe.game.create { seats, random, sources?, packages? }` 建**一局**并**立刻装好规则**：**桌子由局自己建**（`seats` = 座位数，建完就是 `game.desk`），除座位数与随机源外，规则表、包顺序、包元信息、**规则数据袋（`game.rule`）**、时机注册、属性系统、来源全挂在局上，**局之间互不影响**；`packages` 省略视同空清单 ⇒ 只装默认加载的包（见 9.3）—— 即 `create { seats, random }` 与 `create { seats, random, packages = {} }` 行为一致。要换规则走 `moe.loader.install(game, { packages = 清单 })`（省略参数就复用局上记的来源与清单）。
- **包手里的 `game` 就是那一局**：规则包要这一局的牌区 / 桌子 / 随机源就直接用注入的 `game`（`game:createZone` / `game.desk` / `game.random`）—— 不再有「规则实例」这一层，也不存在「实例与场地互指」（见 9.6）。
- 测试套件：`server/test/rule/init.lua`（加载/依赖/重装，`--test rule`）与 `server/test/rule/vfs.lua`（来源与合并，`--test rule.vfs`）；局本身在 `server/test/core/game.lua`（`--test core.game`）。

### 9.2 包来源与虚拟文件系统（`server/core/loader/vfs.lua`）

多个**来源**合并成一棵**逻辑目录树**，加载器只认逻辑路径。来源写法只有两种（`*` 是**特殊语法**，不是通配匹配，只允许出现在结尾）：

| 写法 | 含义 |
| ---- | ---- |
| `X` | X **本身**是一个来源，逻辑第一层 = X 的目录名 |
| `X/*` | X 是**包容器**，其下每个子目录各是一个来源，**容器名不进逻辑路径** |

两种写法归一成「逻辑路径第一层 = 来源目录名」，于是同名逻辑包天然对齐。

来源目录名以 `@` 开头时表示**默认加载**（`package/@基础` ⇒ 逻辑包名 `基础`，且默认加载）：`@` 只从**逻辑第一层**去掉，不进任何逻辑路径（也不会出现在清单 / 依赖 / 限定名 / 元信息里）；`@` 只允许出现在这一层 —— 包内的子目录名或文件名带 `@` 前缀会在**加载时报错**；目录名只有一个 `@`（后面没名字）也报错。

| 接口 | 说明 |
| ---- | ---- |
| `moe.loader.install(game, { sources?, packages? })` | 装一套规则进这个局：先清空局上的内容 → 按清单依次加载；返回**实际执行的文件（逻辑路径）**，按执行完成顺序 |
| `game.sources` / `game.list` | 这个局的来源（**顺序即优先级**，默认 `{ './package/*' }`）与上一次用的清单（`install` 写入，供省略时复用） |
| `game.loadedFiles` | 上一次装的时候实际执行过的文件（同上，随时可读） |
| `Depends { '基础规则/回合流程' }` | **规则集侧**声明依赖，只能出现在加载过程中 |

- **合并规则**：同一逻辑路径在多个来源里都有时，**只取最后一个来源的那个文件**（文件级覆盖）；不同路径取**并集**，同名目录的内容**跨来源合并**（不是整目录替换）。
- **不缓存**：每次 `install` 当场重新枚举并合并，运行期换包 / 加包立刻生效。
- 来源路径在磁盘上**不存在 ⇒ 报错**；`X/*` 匹配到 0 个包 ⇒ 允许；逻辑路径**归一化**（`.` / `..` 会折叠）在逻辑层面做，越出规则集根报错。

**三套机制的方向各不相同，别记反：**

| 机制 | 解决什么 | 排序方向 |
| ---- | ---- | ---- |
| 来源合并 | 用户**替换同一个逻辑文件** | 来源列表里**后者覆盖前者** |
| 规则数据（`rule` 袋，见 9.7） | 后续包**覆盖同一个字段** | 加载顺序里**后者覆盖前者** |
| 包路由（见 9.4） | 不同包**同名并存** | 清单里**先加载的包优先**（包内裸名则先取本包） |

### 9.3 清单与依赖项都是逻辑路径

- 清单项解析顺序：**文件 → 补 `.lua` 的文件 → 目录**（目录递归、只取 `.lua`、按路径排序保证确定性）；都不存在 ⇒ 报错。
- `Depends` 的项也是逻辑路径，且**支持相对路径**：以 `.` / `..` 开头的按**声明它的文件所在目录**解析，其余按逻辑根；归一化后去重（同一文件的不同写法只执行一次）。
- **清单是唯一入口**：加一个文件进清单即生效，从清单移除即失效。清单由**调用方**给：装配方用 `moe.game.create { seats, random, packages = ... }` 定下这一局要装的包，重装与临时脚本直接用 `moe.loader.install(game, { packages = ... })`。
- **互斥声明**：项以 `!` 开头（`Depends { '!国战' }`）表示「本轮不能有这一项」—— 它与依赖项走**同一套解析**（含相对路径）；判定「已加载」是本轮文件里有落在该项（包目录 / 文件）之下的（前缀匹配带分隔符，所以 `国战` 不会误判 `国战外传`）；**没被加载就不报错**；冲突时错误指出**声明者**与被排斥的项。校验做了两次：**执行前一次 + 结束前兜底一次**（任何清单顺序都拦得住）。
- **默认加载的包**：来源里带 `@` 标记的包（见 9.2）由加载器自动加入，且**排在清单项之前**（彼此按逻辑名升序，顺序确定）；清单里不必写它们，写了也不会执行两遍（「同一文件只执行一次」）。**内容包也不必为它们写 `Depends`**（自动装且排在最前 —— `package/身份场/胜负.lua` 就是直接 `game:on(...)` 开头）。要排斥它就用互斥声明（`Depends { '!基础' }`），没有「按名字关掉默认包」的开关。

### 9.4 包与名字路由

包 = **逻辑路径的第一层目录**（目录名即包名），包内子目录只作组织、不参与命名；规则集文件必须位于包目录里（**根下散落文件报错**）；包名与条目名都**不许含 `.`**（完整名由加载器拼）。

```lua
-- package/标准/卡牌/杀.lua
local slash = Card '杀'          -- 登记为 标准.杀
    : on('使用', function () end)
```

| 接口 | 说明 |
| ---- | ---- |
| `Card '名字'` | **只在加载过程中可用**（环境函数）：声明本包的一条定义；同包重复声明报错（报错指出两处来源） |
| `game:getCard('名字')` | 查询：裸名带**包内作用域**，限定名（`军争.杀`）精确取到指定包 |
| `Card:on(事件, 回调)` | 链式登记回调，返回同一条定义；**跨文件追加回调用 `game:getCard` + `Depends` 定顺序**。事件名是**固定集合**（`'卡牌-进入区域'` / `'卡牌-离开区域'` / `'使用'` / `'生效'` / `'被动'`），清单在 `env-meta.lua`；**: `event(名, 回调)` / `: globalEvent(名, 回调)`**（2026-10-09，`add-skill-event-decl` 的装备批；与 `SkillDef` 那对**逐字同形**）—— **声明式订阅时机**（可多次调）：`event` 订**这张牌的主人**头上那份（`owner:on`；**牌不在谁名下就不订**，也不报错——牌堆 / 弃牌堆里的牌照常启用被动）、`globalEvent` 订**局上**那份（`game:on`）；**只做订阅与生命周期**（启用时内核照声明挂上、停用 / 离场 / 换主人自动撤；与 `viewAs` 共用同一套生命周期，挂载顺序 = `'被动'` → viewAs → 「主人那份」→「局那份」），**载荷与返回值都原样转给回调**（第一参补上这张牌 ⇒ `(card, …载荷)`；`fire` 的返回值照旧拿得到，收集式时机也照常工作）。**「要不要发动」仍由回调自己写**（条件写在最前、`card:cast(…)` 起那次发动）⇒ 与手写 `on('被动')` + `host:bindGC(owner:on(…))` **逐字等价**，省的只是那两层壳。**回调里要主人就自己取**（`local zone = assert(card:getZone())` + `assert(zone.owner)` —— 订阅只挂在有主人的牌上，这两个断言都恒真，是**类型窄化**不是防御；取法照 `Card:cast` 内部）。**两条口径**：① 订主人与订局**不可互换**；② **`'被动'` 没有被取代** —— 它承载的是「**启用时做点什么**」（持续性修正：`武器牌` / `坐骑牌` 的 `addAttr`、【诸葛连弩】的 `addLimit`），不是时机订阅。类型面：内核时机的候选在 `env-meta.lua`、**内容侧（伤害 / 治疗 / 判定）时机的候选在 `package/@基础/meta.lua` 的 `CardDef` 块**（配方见 §9.6）。**2026-10-09 装备迁了 7 处订阅**（青釭剑 / 雌雄双股剑 / 方天画戟 / 贯石斧 / 麒麟弓 / 青龙偃月刀 / 仁王盾），保留 3 处持续性修正（`武器牌` / `坐骑牌` / 【诸葛连弩】） |
| 条目字段 | 定义对象是 `CardDef`，字段有 `name`（裸名）/ `package`（包名）/ `fullName`（`标准.杀`）/ `source`（声明它的文件）——字段叫 `package`，注解必须写成 `---@field public package string` |
| `Buff '名字'` | **只在加载过程中可用**（环境函数）：声明一只**状态**（挂在角色身上的东西，写法与 `Card` 同形）；同包重复声明报错。`game:declareBuff` / `game:getBuff` 与牌那套**同形**（按包存、`resetContent` 清、裸名解析同样三条） |
| `Buff:on('获得' / '失去', 回调)` | 链式登记回调（回调收到 `buff` 实例）；事件名固定，清单在 `env-meta.lua`。**资源与订阅一律优先用 `buff:bindGC(...)`**（`Zone:disable()` / `game:on(...)` / `Player:addLimit(...)` 这些撤销函数直接喂给它），**「失去」只留给「真的需要知道」的场合**（用户 2026-09-29 定） |
| `player:addBuff('名字', 载荷?)` | 把一只状态**挂到某人身上**（同名可并存）：挂上 → 发 `'获得'` → 返回 `Buff` 实例；`buff.owner` 读挂在谁身上，`buff.payload` 读**挂上时给的载荷**（内核只存不解释，给内容侧自己约定 —— 如【青釭剑】给「这次使用」，好让状态自己知道该在谁收尾时消掉），`buff:remove()` 失去（幂等，内部就是 `Delete(self)`）；`player:getBuffs()` 给快照、`player:hasBuff(名字)` 给真假。**生命周期归内容**（内核不预设时长）—— 常用两种：状态自己订阅时机删自己，或**让某次结算／某个对象持有它**（`useCard:bindGC(buff)` = 那次结算被删时连带删掉，作业兜底）；失去的顺序是「先发 `'失去'`（此时实例与字段都还在）→ 从宿主摘掉 → 再放掉 `bindGC` 的东西」**「延时类效果」就落在这条上**（2026-10-09，【许褚】裸衣）：效果主体写在一只状态里（`'获得'` 里 `bindGC` 订阅）、**寿命交给持有者**（`turn:bindGC(buff)` / `useCard:bindGC(buff)`）—— **载体不是技能 ⇒ 技能失去 / 无效也照旧执行**（规则集 Ch1/S2 的「触发类效果」） |
| `player:addSkill(名字)` | 让某个角色**拥有一个技能**（2026-09-30，`add-skill-effect`）：没有定义就报错；建 `Skill` 实例（`Skill : GCHost`，字段 `name` / `owner`）并登记进玩家，**挂上即启用**（跑一次 `'被动'` 钩子、给它一个容器 `host` —— 内容侧 `host:bindGC(…)` 订阅 / 建状态，**与装备技能那一套逐字同款**）；`skill:disablePassive()` / `enablePassive()` 停用与恢复（**技能被克制 / 封印**时用，对称、各返回 disposer、层数计数）；`skill:remove()` 摘掉（幂等，内部 `Delete(self)`）、容器跟着放掉；`player:getSkills()` 给快照、`player:hasSkill(名字)` 给真假。**装武将时自动挂技能**（2026-10-01，`mount-hero-skills`）：`Player:setHero` 与 `Player:setIdentity` 都调 **`Player:refreshSkills()`**（住 `@基础/武将.lua`）—— 按「当前武将 + 当前身份」重算（挂上缺的、摘掉不该有的），**主公技只在 `identity == '主公'` 时才挂**（官方口径是「不为主公，其**没有**此技能」） |
| `Hero '名字'` | **只在加载过程中可用**（环境函数）：声明一个**武将**（牌面数据：姓名 / 性别 / 势力 / 体力 / 技能名）；同包重复声明报错。`game:declareHero` / `game:getHero` 与牌那套**同形**（按包存、`resetContent` 清、裸名解析同样三条）。**武将名与牌名是两个命名空间**（同包同名不冲突；预解析的条目校验不管武将 —— 与 `Buff` 同，`Hero = function () end`） |
| `game:getHeroes()` | **这一局装了哪些武将**（2026-10-09，`add-hero-select`）：快照、**按完整名排序**（顺序稳定 ⇒ 同一个随机源可复现）；选将的池子就是它（**没有「公共模板 / 抽象武将」这类东西** ⇒ 列出来的全是能给玩家的真武将） |
| `HeroDef`（链式） | 武将牌面（内核只存不解释）：`: skills { '奸雄', '护驾' }` / `getSkills()`（**技能名列表** —— 技能定义与装配下一批）、`: value(名字, 值)` / `getValue(名字)`（自带数据）。**势力 / 性别 / 体力三样（链式写法与读法）全都住内容侧**（`@基础/武将.lua` 给 `HeroDef` 加字段与方法：`: kingdom '魏'` / `getKingdom()`、`: sex '男'` / `getSex()`、**: `hp(4)` 或 `hp(3, 1)` 写声明值**（底本 Chapter2/Section4：初始体力值可以不等于上限）/ `getHp()` —— 依次取 定义 → `rule.defaultHp` → 5；用户 2026-09-30 定）—— 内核只管「定义本身」、连字段也不占、不知道取值口径。**写**是链式方法、**读**是方法（定义字段私有，与 `CardDef` 同）；单参数的字面量不带括号（与 `: addKind '武器'` 一致） |
| `Player:setHero(hero)`（**内容侧**，`@基础/武将.lua`） | **把一张武将装到这名角色身上**（2026-09-30，`add-hero-setup`）：写 `player.hero` / `player.sex` / `player.kingdom`，并把武将的初始体力上限与初始体力值写进属性（`setAttr` **覆写**）；体力走内容侧的 `hero:getHp()`（依次取 定义 → `默认体力` → 5）。**落点在内容侧**的理由：要写「体力上限」这个属性名，而属性名是内容侧的（内核不预设属性名）—— 照 `Player:distance` / `Player:equipCard` 的先例用 `Class 'Player'`。**装配顺序的口径：先选将、后走开局**（主公 +1 那类加成是 `addAttr` 增量，排在后面才对；`setHero` 用 `setAttr` 覆写基础值）；`@基础/体力.lua` 的默认值已经只给「还没选武将」的角色 ⇒ **两种顺序结果一致**。**技能挂载不在本批**（技能系统落地后接进 `setHero`）。**牌面数据（势力 / 性别 / 体力）的声明与读法都在内容侧**（见上一行）；**体力在角色上的便捷读法**也在同文件：`player:getHp()`（当前）/ `getMaxHp()`（上限）/ `getLostHp()`（缺失 = 上限 − 当前，官方「已损失体力值」） |
| `Skill '名字'` | **只在加载过程中可用**（环境函数）：声明一个**技能**（名字 / 自动同意 / 标签）；同包重复声明报错。`game:declareSkill` / `game:getSkill` 与牌那套**同形**（按包存、`resetContent` 清、裸名解析同样三条）。**技能名与牌名、武将名是三个命名空间**（同包同名不冲突；预解析的条目校验不管技能 —— 与 `Buff` / `Hero` 同，`Skill = function () end`） |
| `SkillDef`（链式） | 技能定义（内核只存不解释）：`: auto(布尔)`（**「自动同意」的默认值** —— 被动触发时要不要问，**不写就是每次问**；`Skill` 实例上的 `auto` 可读可写）、`: tags { '锁定技', '主公技' }`（可多次调、取并集）/ `hasTag(名字)`（**「觉醒技」视为附带锁定技与限定技**，底本 Chapter2/Section5）/ `getTags()`（快照）。**「自动同意」与标签是两个正交维度**（它只是玩家的偏好默认值；「是否必须发动」由技能自己写 —— 强制发动的技能根本不调 `confirm`）。字段私有、写是链式方法、读走方法（与 `HeroDef` 同）；**: `on(钩子, 回调)` / `getHandlers(钩子)`** —— **钩子有两个**：`'被动'`（每次**启用**跑一次、回调收 `(skill, host)`）与 **`'使用'`**（主动发动时跑一次、回调收 `(skill, cast)` —— 2026-10-08，`ask-use-skill`），内容侧在那里 `host:bindGC(owner:on(…))` 订阅 / 建状态（与装备技能的 `'被动'` 同一套；2026-09-30，`add-skill-effect`）；**`Skill:confirm()`**（实例方法，2026-10-01）：自动同意开着直接放行、否则 `askChoice(owner, 技能名, { '发动' })` —— 技能自己决定在哪儿问（强制发动的技能不调它）；**`Skill:tryCast(函数)`**（2026-10-09）：`confirm()` + `cast()` 的**合并写法** —— 问一句、同意才起那次发动，不同意返回空（**用它可以彻底避乱嵌套顺序**：「先 confirm、再 cast」是惯例，写成嵌套就反了）；**`Skill:cast(函数)`**（2026-10-01，`add-cast`）：把那段包成一次「技能发动」⇒ **里面起的结算都挂在它下面**（归因 —— 「这次挪牌是哪个技能做的」沿 `parent` 链查得到），见第 12 节的 `Cast` 行；**: `event(名, 回调)` / `: globalEvent(名, 回调)`**（2026-10-09，`add-skill-event-decl`）—— **声明式订阅时机**（可多次调）：`event` 订**主人头上**那份（`owner:on`）、`globalEvent` 订**局上**那份（`game:on`）；**只做订阅与生命周期** —— 启用时内核照声明挂上、停用 / 离场 / 被克制自动撤（与 `viewAs` 共用同一套生命周期，挂载顺序 = `'被动'` → viewAs → 这两个），**载荷与返回值都原样转给回调**（第一参补上技能自己 ⇒ `(skill, …载荷)`；`fire` 的返回值照旧拿得到，收集式时机也照常工作）。**「要不要发动」仍由回调自己写**（条件写在最前、`skill:tryCast(…)` 起那次发动）⇒ 与手写 `on('被动')` + `host:bindGC(owner:on(…))` **逐字等价**，省的只是那两层壳（**「先 `confirm` 后 `cast`」仍靠 `tryCast`**）。**两条口径**：① 订自己与订局**不可互换**（【鬼才】那种「不分敌我」的必须 `globalEvent`）；② **`'被动'` 没有被取代** —— 它承载的是「**启用时做点什么**」（`addAttr` / `addLimit` 这类持续性修正：【马术】【咆哮】），不是时机订阅。类型面：内核时机的候选在 `env-meta.lua`、**本包（伤害 / 治疗 / 判定）时机的候选在 `package/@基础/meta.lua` 的 `SkillDef` 块**（配方见 §9.6）。**2026-10-09 同一批把武将技能全迁完**（11 处订阅）；装备侧 20 处（`CardDef`）另批 |

**「挂谁」= 「活多久」**（2026-10-09 收口，`add-lubu`；用户问「怎么降心智负担」时定的口径）：可叠加操作一律返回 disposer，而**它挂到哪个对象上就活到那个对象被收掉**（`GCHost` 的 `bindGC`）—— 本回合 `turn:bindGC(...)`（`@基础/回合.lua`）、本阶段 `phase:bindGC(...)`（【裸衣】【英姿】【突袭】）、**这次使用 `useCard:bindGC(...)`**（【青釭剑】的 `防具无效`；【无双】把「响应时多要一张」的订阅挂这儿）、这次发动 `cast:bindGC(...)`（**只到 body 跑完** —— `Cast:settle()` 就是 `return self.body(self)`，想活更久就得换宿主）、一段状态 `buff:bindGC(...)`、被动 / 装备 `host:bindGC(...)`。**两条判据**：① 写「这次使用怎么结算」就挂 `useCard`（与「本阶段怎么结算」挂 `phase` 同形）；② **「失去技能不中断」= 别挂 `host`** —— `skill:disablePassive()` / `remove()` 会把被动容器整个 `Delete`，挂在它上面的订阅随技能一起没（官方规则集 Ch1/S2：已发动的效果不因中途失去技能消失）。**内核不给这类规则开专属字段**（曾考虑 `useCard:setResponseCount` 之类，用户 2026-10-09 否：每条新规则都开一个口子不可持续，而且内核得替内容解释语义）—— 通用解法就是「**订阅挂到正确的宿主上**」。

**裸名的解析顺序：**

1. 查询发生在**包内**（加载过程中、当前上下文有所属包）→ **先取本包**；
2. 本包没有 → 按**包的加载顺序**（清单顺序）取**第一个**定义该名字的包；
3. **包外**（游戏运行期、内核、测试，没有「当前包」）→ 直接从第 2 步开始。
所以：包内写裸名 = 本包版本；**引用他包的同名条目必须写限定名**（军争里想用标准版的「杀」要写 `标准.杀`）。裸名与限定名拿到的是**同一个对象**，不是副本。

### 9.5 依赖 = 执行到那行时同步加载完

`Depends { ... }` 在执行到该行时立刻把依赖加载完，再继续本文件剩余的代码 —— 所以**依赖声明写在文件顶部**（不必预扫描源码文本，避开了字符串/注释里的假匹配）。
去重与防环靠「本轮已加载 / 正在加载」集合：同一文件在本轮只执行一次，互相依赖不会无限递归。

### 9.6 规则集侧的书写环境

- 加载时用 `load(chunk, '@' .. 路径, 't', env)` 把 `game` / `Card` / `Depends`（以及 `Class` / `New` 与共享袋 `rule`）**注入**执行环境，所以规则集文件**不需要 `require` 任何东西**；以 `@路径` 作 chunkname，报错与堆栈里显示真实文件路径（中文路径同样可用）。
- **内核注入的是这七项 + 一份白名单**：`game`（**这一局**，小写对象）+ `Card(name)` / `Depends(items)` / `Class(name)` / `New(name)` / `Extends(类, 基类)` / `Delete(对象)`（**大写环境函数**，只在本轮加载期可用；大写是为了和包里的局部变量区分开）+ 一份**标准库白名单**（`string` / `table` / `math` / `utf8` / `pcall` 等基函数；**`error` 不在里面**，2026-09-28 用户定 —— 内容侧要报告「该有却没有」用 `assert`，且**只在「触发 = 这局打不下去」时用**；写错调用就地退化、不抛）；`moe`（含 `moe.core` 这类写法）、`require`、`io`、`os` 一律不给 —— 规则集是内容，不该具备开文件 / 起进程的能力。
  - **工具集不在这里**：内容侧要什么工具，就在默认包 `@tools` 里**用内容侧写法按需实现**（写下的全局在共享环境里别的包直接就能用）—— 现在是 `table.lua`（`table.filter` / `map` / `contains` / `without` / `mergeArray` / `copy`）与 `util.lua`（`util.defer`）。**不把内核的 `moe.util` 整份注入**（用户 2026-09-28 提了又改口，与 2026-09-19 的结论一致）：它带 `loadFile` / `saveFile` / `expandPath` 这类副作用，等于给内容侧开文件 IO。
  - **包可以给内核类加方法、也可以自定义「一次结算」**（用户 2026-09-28 解锁）：注入的 `Class` / `New` **就是内核那两个全局**（`moe-kill.lua` 里 `Class = class.declare`、`New = class.new`），包照内核的写法用。两种用法：
    - **给已有类加方法**：`---@class Player` + `local M = Class 'Player'` + `function M:distance(to) … end`（首个应用 = `@基础/距离.lua`）。
    - **声明自己的 `Effect` 子类**：`Class('Judge', 'Effect')` —— 第二个参数就是 super，**不需要 `Extends`**；实例化用内核那套**两步**写法 **`New 'Judge' (参数…)`**（先取实例、再调用它跑构造链；`New` 的第二个参数是「实例存储表」，**别往里传东西**）。第一个用户是 `@基础/判定.lua`（判定整个搬出了内核）。
    - 三条口径：① **开 `Class` / `New` / `Extends` / `Delete` 四个口子**（2026-10-09 加后两个：【许褚】要把「本回合伤害 +1」这只延时状态挂到回合对象上，而 `Turn` 是内容侧声明的类 —— 得能 `Extends('Turn', 'GCHost')`（拿到 `bindGC`）、也得能 `Delete(turn)` 才放得掉）；`Type` / `Presize` 仍不注入（用例断言它们够不着）；② **没有护栏**（不走收口函数就没地方挡），靠三条提醒 —— 别用 `__` 开头的名字（框架私有）、别与 `__getter` / `__setter` 同名（会把派生属性读成函数）、别给「实例已有同名字段」的对象装同名方法（类方法会被实例字段遮蔽、永远读不到）；③ **生效范围是 VM 内全局** —— 类表与类注册表一个 VM 里只有一份 ⇒ 对**这个 VM 里的所有局**生效，等「一局一个 VM」落地（`add-worker-mode`）自然变成「这一局」。另有两件要知道的：`Extends` 会把它**复制给子类**（装到 `Zone` 上的会出现在 `OrderedZone` 上）；**类型面基本不用手写注解**（与内核同形即可推断），实测三条 —— `---@class Player` 就够、**不用**写 `: Class.Base`；**派生字段要用 `---@type` 声明**（如内核 `M.acting = nil`），否则读的地方报「未定义的属性/字段」；函数写了 LuaDoc 就要把**每个**返回值都标 `---@return`。
  - **白名单里表值的那几项是「内容侧的副本」**（用户 2026-09-21 定）：`table` / `string` / `math` / `utf8` 在每轮装载时各**浅拷贝**一份（只拷一层，够用 —— 扩充都是往表上挂新函数），所以内容侧改它们**只影响内容侧**，内核的标准库一点不动；**重装换新副本**（上一轮加的函数自然消失）。机制就 `makeEnv` 里那三行 `if type(value) == 'table' then`（拷贝而不是元表代理）。
  - **工具集是对（内容侧）标准库的扩充**（用户 2026-09-21 定，**不是内核注入的** —— 工具集与游戏规则无关）：默认包 `@tools` 往**内容侧那份 `table`** 上加四个纯函数 —— `table.filter(列表, 判定)` / `table.map(列表, 变换)`（回调收 `(值, 下标)`）/ `table.contains(列表, 值)` / `table.without(列表, 值)`（去掉这个值的所有出现、**返回新列表**），**清单与签名以 `package/@tools/table.lua` 为准**。好处：名字自明（不用再纠结工具集该叫什么），也不用为它另开一个全局。代价：**没装 `@tools` 的局仍然有 `table`，只是没有这三个函数**（用 `Depends { '!tools' }` 排斥它、或来源里没有这个包时）；靠默认包顺序（`tools` 按逻辑名排在默认包最前）保证规则包加载时它已经就位。**它和别的内容全局一样不在「每文件刷回」的保护名单里**（只有内核注入的 `game` / `Card` / `Depends` / `Class` / `New` / `rule` 受保护）⇒ 哪个包把它覆盖 / 改写了，由那个包**负全责**（用户 2026-09-21 定，不额外加保护）。要加新函数先过一遍「它用得着沙箱外的东西吗」；将来要加 `string` / `math` 的助手按同一套路再开一个文件（`@tools/string.lua`…）。**旧的「工具集里只有纯函数」那道纪律自然消解了** —— 助手就写在沙箱环境里（`io` / `os` / `moe` 都够不着），想写带副作用的助手也写不出来。
- **整轮装载共用一份环境**（用户 2026-09-21 定）：文件之间**不是**各自一份 env —— `ctx.env` 一次装载只建一份，于是**包 A 里写的全局函数包 B 直接就能用**（这就是「内容侧共享函数」的通道；顺序 = 加载顺序，要定序就用 `Depends`）。三件配套的事：① **注入的 `game` / `Card` / `Depends` 在每个文件加载之前都会刷回** ⇒ 某个包把它们改坏了也不影响后面的文件（别拿它们当全局变量用）；② **重装换新环境** ⇒ 上一轮写的全局自然消失（与规则表 / 规则数值同一生命周期）；③ **试跑那一趟也共用一份**（语义与真跑一致，否则「文件 B 调文件 A 的函数」会在试跑里假报错）；④ **跨包共享的规则数据（含规则数值）挂 `rule` 这个袋**（2026-09-29 起：**装载器每轮装载给一张新的空表**，与 `game` / `Card` / `Depends` / `Class` / `New` 同属注入项 —— 每个文件加载前一起刷回，所以某个包把 `rule` 整个换掉也不影响后面的文件；类型声明在 `env-meta.lua`，字段由内容侧自己加）—— 现在有 **`rule.equipZones`**（装备子区名单）与 **`rule.ownZones`**（「自己的区域」= 手牌 + 装备子区，2026-10-08 加 —— 凡「一张你的牌」都读它：素材 / 弃牌 / 桃，**判定区不在其中**；见第 12 节装备子区那一行；`@基础/装备.lua` 建它俩、别的包在加载期往后追加 `equipZones`）；比一堆裸全局好找、也能给类型（**大写开头还免掉 `lowercase-global`**）；**内核不认识里面的东西**，重装换新袋。
- **沙箱口径不变**：共享的只是「内容自己的全局命名空间」——白名单仍是 `ALLOWED_GLOBALS` 那份清单（除 `_VERSION` 外就是基函数；其中四个表值是**副本**，见上），**没有** `__index = _G`（`moe` 是全局变量，一挂 `_G` 沙箱当场漏），所以 `moe` / `require` / `io` / `os` 仍拿不到。
- **工具集住在内容侧**：`table.*` 那四个是内容侧写法的**扩充**、不是替代（清单以 `package/@tools/table.lua` 为准）；`util.defer` 是**没有标准库可挂**的助手（`package/@tools/util.lua`）；内核那份 `moe.util` 仍不给（见上一条）。
  - **泛型要标在实体函数上**（2026-09-21 实测）：LuaLS **不支持** `---@field f fun<T>(…)` 这种写法（泛型参数会被丢掉），**给标准库补字段也一样** ⇒ 工具集写成 `---@generic T` + `function table.filter(…)`（**实体函数**），于是调用点带 `<T>`，**跳文件也认**（`杀.lua` 里 hover 得到 `fun(list: <T>[], predicate: fun(value: <T>):boolean) -> <T>[]`）。推论：`meta.lua` 只用来放**赋值处表达不出来**的类型（`---@alias`、按名收窄的 `---@field`）；能标在实体函数上就别进 meta，否则反而把泛型压平。
- **规则包需要的内核能力由 `game` 收口**（用户 2026-09-19 定）：`game:getAttributeSystem()` —— 属性系统由**那一局**持有（一局一份；清空重装时置空 ⇒ **重装后是一个全新的系统**：属性定义是规则集内容，属性库也不允许编译后再 `define`）；包在**加载期**往它上面 `define`，装配方再用 `createInstance()` 给玩家建属性实例。
- **一局的资源直接用注入的 `game`**：牌与牌区是运行期的东西，按名字建在局上（`game:createZone(名字, 有序?)` / `game:createCard(名字)`），桌子与随机源是局上的公开字段（`game.desk` / `game.random`）—— **只认字段，没有 getter**（一个概念不要两套 API）。**环境对象就是 `game` 本身，不进时机上下文**（见第 10 节）。
  - 分工：**五个基础牌区由内核建好**（局上 `抽牌` / `弃牌`，玩家身上 `手牌` / `装备` / `判定` —— 建玩家时就有；见 12 节的「基础牌区」）—— 包**不要重建同名区**（撞名当场报错）；要加**自己**的区才用 `game:createZone(名字, 有序?)` / `player:addZone(名字)`。
- **装配方不受限**：测试与将来的房间 / 流程直接用 `moe.*` 组合开局（它们不是包）。
- 规则集文件里**可以用中文标识符**（构建期补丁，见 `infrastructure.md`），但**中文只用于难翻译的内容名**：技能名 / 卡牌名 / 身份名，以及作为数据取值与配置键的名字（`'杀'`、`'体力上限'`、`'游戏-开始'`）；**字段名 / 局部变量 / 函数名一律英文**（详见 `code-style.md` 第 8 节）。
- 规则集里**不要为空值防御**：注入的 `game` 按约定一定拿得到（它就是这一局），直接用；只有**运行期真的会缺**的才 `assert`（如没牌表、人数不在配置表里 —— 内容侧拿不到 `error`，见 9.6）。见 `code-style.md` 第 9 节。
- 这两个环境函数与各时机的上下文类型写在一份**纯类型文件** `server/core/loader/env-meta.lua`（顶部 `---@meta`，不参与运行）：见 9.7 与第 10 节。
- **包自带 `meta.lua`**（用户 2026-09-21 定）：包目录下可以放一份**纯 LuaDoc** 文件（固定叫 `meta`，不跟内容命名走 —— 它是**纯代码功能**、不是规则内容），用来声明**这个包自己的概念**：`---@alias`（如 `身份场.身份`）、以及给内核类**追加按名收窄的签名**（`game:getValue('身份配置')` → 配置表、`game:getValue('默认体力')` → `integer`、`player:getAttr('体力')` → `number`）。**装载器不特殊对待它**（就一个普通文件，里面只有注释 ⇒ 执行是空操作）【约束：它里只放类型声明】。
  - **配方（三处坑）**：① 给某个名字加候选时**必须自带兜底条**（`name: string` / `key: string`）—— **不带兜底时那条声明会把同名的其它候选（含内核那份、别的包那份）一起挤掉** ⇒ 表现是「新老候选都不解析」（实测 2026-09-21：漏写时全仓 27 处 `getTag('顺序')` 报「不能将 `string` 赋给参数 `'身份'`」；反例 2026-09-30：`@基础` 里给 `Player` 加 `'伤害-目标-结束'` 而没带兜底时，同表的 `'伤害-来源-开始'` 也推不出参数，补上就两条都好了）；② 重声明类时**基类要写全**（`---@class Player: Class.Base`）；③ **按名收窄的宿主有几个、回调形状是否相同**（2026-09-30 实测后收敛）：**形状相同**才值得抽一个公共类让各宿主继承（`self` 写 `any` 就能共用），省下同一批候选写两遍；**形状不同就各写一块** —— 形状不同注定要各写一条候选，而**兜底必须跟着候选一起写**（见 ①），合并只是多一层间接。实测：`Player:on` 的回调收纯载荷、`SkillDef:on` 的回调多收一个技能实例 ⇒ 两条候选写在各自的类块里（`---@class Player: Class.Base` / `---@class SkillDef`），参数都推得出来；且**内核那批收窄照常生效**（跨文件是**并存**，不互相挤掉）。
  - 实测的良性质：**多个包各自的候选共存**（`@基础` 的 `'默认体力'` 与 `身份场` 的 `'身份配置'`同时对 `getValue` 生效）、**跨包读也收窄**（`身份场` 读 `@基础` 的值拿到了 `integer`）、重声明**不会弄丢**内核那份类声明里的其他字段。
  - 所以**包作者可见的类型面变成两处**：内核的通用面（注入的 `game` / `Card` / `Depends` / `rule`、各时机上下文）在 `env-meta.lua`；**各包自己的概念**在它自己的 `meta.lua` —— 或者直接标在实体函数 / 赋值处（泛型只能这么标；`@tools` 的 `table` 助手就是直接标在 `package/@tools/table.lua` 上，没进 `meta.lua`）。

### 9.7 规则数值与内容数据（共享袋 `rule`）

规则包里定的默认值（体力上限、身份人数表、牌表…）放**共享袋 `rule`**：装载器**每轮装载建一张新表**、注入给所有内容文件（试跑那趟也给一张空的），**字段名扁平、用英文**（`rule.defaultHp` / `rule.cardTable` / `rule.identityConfig`…）—— 字段名即落点，**这就是后续包（mod）改规则的通道**。

```lua
-- package/@基础/配置.lua
-- 没写武将的角色默认的体力上限（也是初始体力）
rule.defaultHp = 5
```

- **按加载顺序后者覆盖前者**：这是有意提供的**覆盖通道**（例：军争要改血量上限就再写一份配置），与包路由的「同名并存」是两套语义。
- **读的时候才取**，不在文件顶层抄一份 ⇒ 改字段、就地改表内容、整张换掉，都当场生效（阶段清单 `rule.phases` 也是这么读的）。
- 与内容同生命周期：清空重装时换一张新的空袋（`game.rule` —— 与注入的全局 `rule` 是同一张表，局外也读得到）；读不到的默认值写在规则包里，读时 `or 默认`。
- **函数不进共享袋**：行为（如「游戏开始时分身份」）走**时机注册**，不要存回调。
- 类型声明：向 `Loader.Rule` 上补 `---@field`（**写在提供该字段的那个包的 `meta.lua` 里**，一行中文说明；字段一律可空 —— 袋建出来时是空的）。
- **`game:setValue` / `getValue` 保留，但只当临时数据**（2026-10-09 起）：测试探针、将来的房间数据这类「不是规则数值」的东西才用它；规则数值一律写进 `rule`。

### 9.8 定义入口与重装语义

```lua
local slash = Card '杀'
    : on('使用', function () end)
```

- `Card '名字'` = 声明（名字不含 `.`、完整名由装载器拼）；`Card:on(事件, 回调)` 链式登记；查询用 `game:getCard`（未登记得到 `nil`）。
- **环境函数 与 局上的方法**：`Card '杀'` / `Depends { ... }` 是注入环境的**大写函数**，只在**本轮加载期**可用，作用在正在装的那个局上；内容入口（`game:getCard` / `game:getValue` / `game:on` / `game:fire` / `game:getAttributeSystem` / `game:getPackageMeta` …）在加载期与运行期都能用，重装走 `moe.loader.install`。
- **重装 = 清空局上的内容 + 重新加载**：不做增量、不做按名单卸载（用户 2026-09-19 定），重复加载同一份清单会**重新执行**所有文件；包顺序也随清单重新算。桌子 / 随机源 / 牌区**不参与清空** —— 重装只动规则内容。
- 规则表结构是「包名 → 裸名 → 定义」+ 一份包顺序表；**同一轮加载里还能注册时机回调**（见第 10 节），它们与规则表一样随清空重装清空。
- 目前只有「牌」一类，结构按功能点增量长；卡牌的事件名与回调签名**做「杀」时再定**。

## 10. 时机与事件（`moe.event` + `game:on`）

规则集要能**挂到时机上**（`'游戏-开始'` 时分身份、改体力上限，回合各阶段触发技能…）。机制在内核模块组、实例由**局**持有：

| 接口 | 说明 |
| ---- | ---- |
| `Event:on(名字, 回调)` | 按时机名注册，返回 disposer；**注册顺序即执行顺序** |
| `Event:fire(名字, ...)` | 按名触发；未注册 = 空操作；单个回调报错不打断其余（`xpcall(回调, log.error, ...)`） |
| `Event:collect(名字, ...)` | 按名触发并**收齐所有非空返回值**（每个回调只收第一个返回值；没返回 / 报错的不收）；未注册 = 空列表。与 `fire` 的分工见下 |
| `Event:has` / `getNames` / `clear` | 查询与清空 |
| `game:on(名字, 回调)` | 注册时机（**唯一入口**：内容包 / 内核 / 用例都用它），返回 disposer |
| `game:fire(名字, 上下文)` | 触发：给**装配 / 流程代码**与无头测试用；内容包不主动触发 |
| `player:on / fire / collect` | **玩家自己的时机表**（2026-09-29 落地）：与局同形、同一个 `Event` 实现 —— 技能挂在它身上，**只在自己被问到那一方时才醒来**（「装备 / 技能归属」变成了订阅信息的一维）。**第一阶段事件已按当事人发**（2026-09-29）：`'阶段-开始'` / `'阶段-生效'` / `'阶段-结束'` **全局那份照旧**、再对 `phase.player` 发一份（**同名**、全局先）；其余事件（回合 / 摸牌…的定向）将来另做 |

- 实现是「时机名 → `moe.sevent`」的薄封装（`server/core/event.lua`），顺序与错误隔离都沿用 `simple-event`。
- **实例由局持有**（`game.events`）并在**每次装载时重置** —— 于是注册的生命周期天然等于一轮装载，清空重装不会残留旧回调，也不会串到别的局。**玩家还有自己的一张**（`player.events`，随玩家实例生灭）：「只与我有关」的时机挂这里（`player:on` 是技能的自然落点）；resetContent **不清玩家事件表** —— 重装整块即将随 `add-worker-mode` 退役（一局一 VM），不为它写一次性清理。
- **时机名不预设**：内核与加载器不认识任何具体时机名，`'游戏-开始'` / `'回合-开始'` 都是规则集自己约定的字符串。**项目约定用 `分类-动作` 命名**（前一段是分类、后一段是动作，便于按分类聚合事件列表）—— 这只是写法规约、没有任何强校验，但**内核自己发的每个事件都已经符合**（2026-09-24 整理：`'摸牌'` ⇒ `'摸牌-生效'`、`'即将生效'` ⇒ `'效果-能否生效'` —— 后者顺带改成了疑问式，因为阻止生效就是“问一句”）；**新加事件两段都要有**。分类取值跟「谁是主体」走：`游戏` / `回合` / `阶段` / `玩家` / `卡牌` / `效果` / `伤害` / `回复` / `判定` / `濒死` / `决策` / `摸牌`…；**注意与阶段名分属两个命名空间** —— 阶段名（`'准备'` / `'摸牌'` / `'出牌'`…）由内容侧自定、不带连字符，与事件名撞词不影响任何东西
- **对当事人再发一份时，玩家那份的时机名带「来源」/「目标」**（2026-09-30 用户定，记成规则）：全局那份不带方向；玩家对象那份按当事人角色插词 —— 来源侧插 `来源`（`'伤害-开始'` ↔ `'伤害-来源-开始'`、`'卡牌-指定目标后'` ↔ `'卡牌-来源-指定目标后'`、`'卡牌-使用选项'` ↔ `'卡牌-来源-使用选项'`）、承受侧插 `目标`（↔ `'卡牌-目标-指定目标后'`）；`'效果-被响应'` ↔ `'效果-来源-被响应'` 照此。**早期两个同名两份**（`'阶段-开始'` / `'阶段-结束'`、`'效果-收尾'`）是历史口径，未追改；**`'卡牌-结算前'` 原也是同名两份，2026-10-09 把使用者那份改成 `'卡牌-来源-结算前'`**（用户提），从此那个名字只剩全局那份；**`'判定-前'` / `'判定-后'` 是同一类的后来者**（2026-10-09，`add-judge-player-event`）—— 判定没有方向词可用（既不是来源也不是目标）⇒ **同名两份**（全局先、判定者后），「你的判定」类技能订自己那份、【鬼才】那种「一名角色的判定」订全局那份；**`'卡牌-进入区域'` / `'卡牌-离开区域'` 也是同名两份**（2026-10-09，`add-sunshangxiang`）—— 每个区先发**牌自己**那份、再发**区主人**那份（这里同样没有方向词可用）

- **上下文只装事件参数**：回调拿到的载荷 = 这个时机对外声明的参数（`'游戏-开始'` 没有参数 ⇒ 传空表）；环境对象就是注入的 `game`，不进上下文。
  - **开局是两步（2026-10-09，`add-hero-select`）**：`'游戏-准备'`（**更早**）→ `'游戏-开始'`。**两步都由装配侧 fire**（内核不代劳，与 `'游戏-开始'` 的先例一致）；**准备**步里发身份 + 选将（主公先选需要身份已定），**开始**步里才是体力默认值 / 主公加成 / 建牌堆 —— 主公加成留在「开始」是因为它是 `addAttr` 叠加、得排在武将体力写完之后。**准备的载荷**（`Game.Event.游戏准备`）由**内容侧**解释：内核只声明它在、一个字段都不预设；`身份场` 给它补 `{ config = 身份场.准备配置 }`（`identities` 座位号 → 身份 —— **要么不给、要么给全**（给全了就不再校验「身份配置」，全是主公也接受）/ `heroes` 座位号 → 武将名（可逐个点名）/ `skipSelect` 整段跳过），**给了的就不再分配或询问**。**坐次**：`seats`（`Player` 列表）给了 ⇒ 照它排（**必须给全**；**这时主公不必在 1 号位** —— 允许配置成非主公先走第一回合，回合流程照旧从 1 号位起）；没给 ⇒ 用 `Desk:swap`（交换两个座位上的玩家，只换座位、不动牌区）做一次**经典洗牌**（从后往前、每次与随机座位交换），再把主公换到 1 号位。
- **事件参数写进 meta**：`server/core/loader/env-meta.lua`（纯类型文件，不参与运行）为每个时机声明一个上下文类型与 `on` / `fire` 的重载，于是规则集里 `game:on('游戏-开始', function (event) ... end)` 的 `event` 能**按事件名收窄**出字段类型（**参数名按载荷的具体类型起、别叫 `ctx`** —— 见 `code-style.md` 第 8 节）：

```lua
--- 目前没有事件参数：触发时给空表
---@class Game.Event.游戏开始

---@class Game
---@field on fun(self: Game, name: '游戏-开始', callback: fun(event: Game.Event.游戏开始): any): function
---@field fire fun(self: Game, name: '游戏-开始', event: Game.Event.游戏开始): any
---@field on fun(self: Game, name: string, callback: fun(payload: any): any): function
---@field fire fun(self: Game, name: string, ...: any): any
```

  类型名的**最后一段** = 事件名**去掉连字符**（连字符不是合法的 LuaDoc 类型名字符），前面挂在自己类的命名空间下（`Game.Event.游戏开始`）；上下文的类型也可以直接就是内核的某个类（如「伤害-前」与「伤害-后」的上下文就是 `Damage` 实例）。同名多行 `---@field` 会被当成多个签名候选（实测不报 `duplicate-doc-field`）：**字面量事件名走专用那条，动态名字落到 `string` 兜底那条**。
- **两类事件名，兜底策略不同**（用户 2026-09-19 定）：
  - **局的时机**（`game:on` / `game:fire`）是**开放集合**（时机名不预设、不校验）⇒ 专用候选之后**必须补 `string` 兜底**，否则动态时机名会被误报类型不匹配；新增时机时**顺手补一条**，不补也能跑（运行时与注入面都不校验时机名），只是调用点拿不到载荷的字段类型。
  - **牌的钩子**（`CardDef:on`）是**固定集合**：名字由内核约定、与启用的包无关（也没有扩展需求），清单以 `server/core/loader/env-meta.lua` 为准 ⇒ **不留兜底**，拼错在编辑期直接报（实测：把钩子名拼错（如 `: on('获取目标吗', …)`）会在编辑期直接报）。新加钩子**必须同步补进 `env-meta`**，钩子清单只有它一个事实来源。
- **这份 meta 就是包作者（含第三方）可见的类型契约，不额外做“可单独分发的 meta 包”**（用户 2026-09-19 定）：内核的类型（`Game` / `Player` 等）与 `moe` / `bee` 的引用链横跨整个工程，单独导出难以完整 —— 第三方开发者**直接打开本工程**开发自己的包（包放自己目录、再写进来源清单，见 9.2）。因此**改时机名 / 改签名要顺手改这里**，它是对外接口面的一部分。
  - 注意：`.luarc.json` 是**单根工作区**设置 —— 包目录在本工程之外时分析器不会跟着分析（多根工作区也拿不到该配置）；开发外部包时把目录放进工程里，或用单根工作区指向包含它的目录。
- **覆盖靠顺序，不靠改载荷**：上下文约定为**只读**，要覆盖就改**状态**（写标签、改属性、加标记）—— 后注册的回调后执行，它写的状态自然生效（例：身份场写身份，后来者也注册同一时机，则后写者胜）。
- **快速返回（返回值即结论，2026-09-22 定）**：任意触发里，回调**明确返回了返回值（非 nil）就立刻停下、跳过之后的事件，并以它作为 `game:fire` 的结果**。判据只看**没报错**的那一次返回 —— `log.error` 会把错误消息作为返回值交出去，`xpcall(callback, onError, ...)` 下"回调报错"也会产生一个非 nil 值，所以实现必须连 `ok` 标志一起看（落在 `tools/simple-event.lua` 的 `fire`：本项目对上游照搬件的改动点，记在 `infrastructure.md`）。**注册顺序即优先级** ⇒ 谁先说话谁算数；**嵌套触发不串**（返回值靠 `return` 带出、不共享状态）。
- **收集式触发（`collect`，2026-09-29 定）**：`fire` 问「有没有人给结论」（第一个说话的人算数），`collect` 问「**每个来源各贡献多少**」—— 全部收齐、按注册顺序排开。判据：**结果是「一个结论」（能否 / 响应 / 原因）⇒ `fire`；结果是「每个来源各一份」（数量增减这类）⇒ `collect`**。实现落在 `tools/simple-event.lua` 的 `collect`（与 `fire` 同为照搬件改动点，记在 `infrastructure.md`）：`xpcall(callback, onError, ...)` 后**连 `ok` 标志一起看**（报错的不收、其余照收），每个回调只收第一个返回值；`Event:collect` 没订阅时给空表，`game:collect` 是它的转发。首个用户曾是 `'卡牌-目标数修正'`（2026-10-08 已并进 `'卡牌-使用选项'`）；现在按这套写的时机带**全局与使用者两份**（名字按 §10 的方向词规则），如 `'卡牌-使用选项'` ↔ `'卡牌-来源-使用选项'`。
- **命名约定：疑问式名字（能否 / 可否…）= 期望返回值的事件**（2026-09-22 定，2026-09-24 扩到效果层）：如 `'卡牌-能否使用'`（内容侧返回非 nil 值即否决，返回值就是原因）与 `'效果-能否生效'`（**回调返回非 nil 即阻止这一次生效**，返回值就是原因；只给 `false` 归一成一句通用原因）；通知型时机（`'卡牌-结算前'` / `'阶段-开始'`…）照旧不看返回值。名字上就能区分两类，比在参数里约定一个"要不要返回值"的标记清楚。**代价也要记住**：疑问式事件的回调**意外返回一个非 nil 值就会阻住后面注册的回调**（快速返回）—— 写这类回调时别顺手 `return` 别的东西。
- **效果判定的三段式（2026-09-29 落地，`add-player-events`）**：每个效果在结算前**依次**被问「能不能生效」—— ① `game:fire('效果-能否生效')`（全局：【无懈可击】/ 规则）；② `effect.from?:fire('效果-来源-能否生效')`（**来源**：`Effect.from`，如 `CardEffect.from = user`）；③ `effect.to?:fire('效果-目标-能否生效')`（**承受者**：`Effect.to`，如 `CardEffect.to = target`、【仁王盾】挂这里）。**谁先给原因就停在谁那儿**（不再问后面的段）—— 顺序是内容可见的约定（全局 → 来源 → 目标），有实际案例再调；三段对**所有**效果都跑，读得出 `from` / `to` 就进对应段（询问类的 `to` 是「被问者」，也会进目标段）。**`false` 归一的坑**：这个系列的约定是「返回非 nil 即阻止」，而 `or` 链按 **truthy** 短路 —— 归一化必须在**进链之前**做（`Effect:fireVeto`），否则某段只给 `false` 会被当成「没拦」。
- **回调报错被隔离**：单个回调抛错只记录（`log.error`），**触发本身不会失败**；所以“规则包里出错”的可见信号是**状态没写**（不写牌堆、不写身份），装配方要在 `fire` 之后断言必需状态（见第 6 节的无头测试写法）。
- **效果族的收尾时机 `'效果-收尾'`**（2026-09-23 落地，内核自己 `fire`）：**每次结算结完都发一次** —— 这次效果结完（正常结完 / `reject` 不成立 / 取消 / 超时都算，挂在任务的完成点上），上下文 = **效果自己**，时点在**所有子效果结完之后**、且**先于**叫醒 `await` 的人。**触发条件走了两轮**：落地时就是每次都发；2026-09-24（`inherit-temp-zone`）为了配合「临时区沿 `parent` 继承、谁建的谁清」收紧成「**只发给区的归属者**」，2026-09-28 那条继承撤回（`effect-own-temp-zone`）、2026-09-29 把闸门去掉回到每次都发 ⇒ **订阅方要按载荷自己过滤**（`effect.useCard == 这次使用` / `effect.target == 这个目标` 之类）。**发两份（2026-09-30 起）**：先 `game:fire`，再 `effect.to?:fire`（**承受者头上那一份**，「冲我来的效果结完了」—— 与 `'效果-目标-能否生效'` 同一口径，读得出 `to` 才发；想只关心「冲自己来的」就写 `player:on('效果-收尾', …)`，不用再比 `effect.target`）。用途是「结算期间暂存的牌该走了」：内容侧可以在这里先把要留走的牌搬去别处（装备牌进子区、延时锦囊进判定区），**之后内核把剩下的一批同步送进 `弃牌` 区**（默认收尾，2026-09-24 起；**一次批量** `Zone:accept`，2026-09-29 起 —— 内核只认「结算完的牌回弃牌堆」这一条，其余仍由内容侧定；见第 12 节的 `Effect` 行）。
- **`'效果-收尾'` 可重入（2026-09-29 去闸门时实测到）**：处理器里起的**任何结算**（`game:moveCard` / `game:damage` / 一次询问…）结完时**同样会发收尾** ⇒ 没按载荷过滤的处理器会一层套一层自激。**内核兜得住**（见第 12 节的 `MAX_DEPTH`：越限层不结算、也不发收尾 ⇒ 链停在 150 层），但会白造上百层空结算 + 一堆 `warn` ⇒ 约定仍是两条：① 处理器**先按载荷筛掉与自己无关的效果**；② 别在收尾里起新结算（内核自己的默认收尾走 `Zone:accept`、不起结算）。
- **依赖方向**：机制在内核模块组、实例由局持有；内核侧消费者（将来的回合流程、会话）要订阅游戏时机，就用自己那一局（`game:on` / `game:fire`），**不要**自己再造一份。
- **订阅入口只有 `game:on`**（用户 2026-09-21 定，统一了原来的 `game:on` / `game.events:on` 两个写法）：`game.events` 退成**内部字段**（内核自己 `fire` / `clear` 用），外面一律 `game:on` / `game:fire`。早先 `game:on` 限制「只在加载规则集时可用」、把内核 / 用例逼去直接碰 `game.events` —— 2026-09-21 实测**内核侧一个订阅者都没有**（`server/core/` 只有 `event.lua` 的实现与 `game.lua` 的转发；`server/session/` 也不订阅游戏时机），那道限制于是被删掉（`game:on` 现在任何时刻都能注册，不再报「时机注册只能在加载规则集时声明」）。
- **但时机表仍然是「内容」**：每次 `resetContent()`（每次装载）都会 `events:clear()` —— **连同运行期注册的那些一起清** ⇒ 内核 / 装配的**长期簿记**（缓存失效…）千万不要挂在它上面，否则重装一次就静默失效（实测：桌子想靠订阅 `'玩家-死亡'` 清 `alivePlayers` 缓存，加载后订阅就没了 ⇒ 改成「不缓存、每次现算」）。内容包与用例无所谓 —— 它们的订阅本来就随这一轮装载 / 这一个用例生灭。

## 11. 预解析与包元信息

加载一份规则集是「**先试跑、再执行**」：枚举到文件后先用「stub 环境 + `tools/without-check-nil`」跑一遍，只提取它声明的**依赖项 / 互斥项 / 条目清单**（不写规则表、不改状态），汇总成**包元信息**；据此在**执行任何文件之前**校验互斥冲突与同包重复条目，最后才清空规则表并按清单执行。

- 试跑机制在 `server/core/loader/preparse.lua`。`without-check-nil` 给 **`nil` 本身**装元表（nil 上的算术 / 拼接 / 索引 / 调用都不崩），所以文件里 `Card('杀'):on(...)` 这类链式调用落到 `nil` 也不会炸；**它是进程全局改动，必须成对 `enable()` / `disable()`**（用 `<close>` 保证一定恢复）。
- 试跑失败（文件自身报错）**只记警告**并继续：真正的语义仍以执行为准（执行到那一行时的早失败 + 结束前兜底共同保证）。
- 查询：`game:getPackageMeta(包名)` / `game:getMetas()`，返回**只读快照**（包名 / 依赖 / 互斥 / 条目 / 文件与来源 / 试跑是否成功）。

## 12. 使用牌与伤害（内核机制）

规则侧第一个功能点：让一张牌能「用出去并产生后果」。机制在内核、规则全在内容包 —— 契约见 `server/test/core/effect/init.lua`、`server/test/core/effect/play.lua` 与 `server/test/core/effect/damage.lua`。

**效果族的落点**（用户 2026-09-21 定）：`Effect` 与它的**全部子类**都住 `server/core/effect/`（**基类 = `effect.lua`**、模块名 `core.effect.effect`；`effect/init.lua` 只做装载（先基类、再各子文件），`server/core/init.lua` 里只留一行 `include 'core.effect'`；子类顺理成章是 `core.effect.damage` / `core.effect.use-card` …）。**判断标准只有一条 —— 是不是效果**：要进记牌器 / 要 `parent` / 要 `settle()` 的就放这儿，纯机制（`zone` / `desk` / `attribute` / `game`…）留在 `server/core/` 平级。用例对称（`server/test/core/effect/`），套件名跟着模块名走 ⇒ `--test core.effect` 一把跑完整个效果族。**2026-09-28 起：内容侧也能声明 `Effect` 子类**（`Class(name, 'Effect')` + `New`，落点在内核之外，见 §9.6）—— 判定、伤害 / 回复 / 摸牌 / 濒死都是这么搬出去的（它们住 `package/@基础/{判定,伤害,回复,抽牌,濒死}.lua`，**仍是内核的默认规则层，只是落点可被 mod 覆盖**）；下表列的是**内核自己造的那些**（机制类）。

- **效果链与记牌器**：`apply()` 里先取 `parent`（外层效果 —— 从**当前任务的上下文**取，必须在**排队**（`executeSync` / `executeAsync`）**之前**取：一进执行体当前任务就变成自己了）、再按父链累 `deep`、挂进父的 `childs`；根效果记进局上的**只增记牌器**（`game:addEffect`）。
- **两个上限都是安全阀，不是规则**（用户 2026-09-22 定；2026-09-29 补第二条并把判断提到 `bindFinish` 之前）：`Effect.MAX_DEPTH = 150`（**嵌套深度**，`deep = parent.deep + 1`）与 `Effect.MAX_CHILDS = 1000`（**一次结算挂的子结算数**，`#parent.childs`）—— 任一项越限，那一层**不结算也不绑收尾**（`.err` = `canceled`、没有结果、**不算失败、不进错误日志**）+ 记一条 `warn`（“效果嵌套超过 150 层 / 一次结算里挂的子结算超过 1000 个，这次生效没有结算”）；**不再 `error`**（`error` 只该管程序错误；“太深”是引擎撑不住，而规则上确实有能无限用牌的打法，例：技能允许无限使用【无懈可击】）。
  - **实测数字**（2026-09-29，探针 `server/tmp/flat-chain-probe.lua` 与 `server/tmp/deep-awaited-probe.lua`）：`executeSync` 时代 **自激链（收尾里起结算）约 300 层**、**父等子深链约 400 层**把 C 栈耗尽（Windows 上 `STATUS_STACK_OVERFLOW` —— 进程直接没、没有可捕获的错误）；换成 `executeAsync` + 唤醒不内联之后**两条形状都平**（实测 800 / **3000 层**都跑得完，3000 层 0.12 秒）⇒ **`MAX_DEPTH` 现在只当「防自激」（一笔调度一层地无限涨）用，不再兼职「防爆栈」**，余量也从不到一倍变成十几倍。**两根轴不是一回事**：深度是**链式**增长（每个父只有一个孩子），`childs` 是**扇出**（一个结算挂多少子结算）—— 爆栈那根轴是前者，后者防的是账无界。

- **`'卡牌-进入区域'` 与 `'卡牌-离开区域'`：牌区自己发的两个钩子**（进入：2026-09-24 落地，形状由用户定；离开：2026-09-28 用户定，与进入对称）：牌**落进某个牌区之后** / **离开某个牌区时**，由那个区按牌的内容定义各跑一次，载荷都是 `(card, zone, visible?)`（`visible` 2026-10-09 加 = **这次搬动对谁可见**，不给就是空）。**2026-10-09 起每个区发两份**（`add-sunshangxiang`）：先给**牌自己**（`Card:fireHandlers`）、再给**区的主人**（`zone.owner?:fire(...)`，**同名** —— 这里没有方向词可用，同上一条方向词规则；**公共区没有主人 ⇒ 只有牌自己那份**）—— 顺序固定，第二份就是为了【枭姬】那类「你的区里丢了牌」的技能。**唯一的发放点是 `Zone:notifyMoved(moves)`**（`Zone:accept` 的第三步）—— `notifyEnter` 只在它里面被调，`notifyLeave` 由它和 `Zone:clear` 调（`clear` 把牌拿出来时也逐张发「卡牌-离开区域」）—— 于是从手牌用出去、被拆、被抢、死亡弃牌、进弃牌堆、直接 `accept` / `clear` 都算。**发的时候牌已经不在源区里**（虽然归属已经指到新区）—— 「离开」的钩子想读那张牌在哪里就直接读 `card:getZone()`。**批量一起发**（2026-09-28）：一次搬一批时先把每一张的「离开」发完、再发每一张的「进入」（避免「A 已进来、B 还没出去」的中间态被内容侧看见）—— 换装备那两步（旧牌先送弃牌堆、新牌再进子区）现在在内容侧 `equipCard` 里发，因此**旧牌的「离开」自然先发**。三件事让它天然带条件：① **区自己记着局**（`Zone.game`，**必填**字段），所以**公共区（抽牌 / 弃牌 / 临时区）也发**；② 牌名去 `game:getCard` 查定义，**没有对应定义 ⇒ 跳过**（载荷只有 `card` 与 `zone`，**没有槽位名了** —— 2026-09-29 槽位机制删掉）。**装备的修正 2026-09-29 起改由「被动」做**：进子区启用、离子区停用并撤销 —— `withZone` 的撤销发生在 `bindZone`（比『卡牌-离开区域』更早），两者并存会把同一修正撤两次，所以迁移时全撤掉了（**`withZone` 本身已于 2026-09-30 删掉** —— 内容侧零用户、机制与被动容器重复，`passive-bind-gc-host`）。
- **「效果-能否生效」与阻止**（2026-09-24 改；2026-09-29 扩成三段）：每个效果在执行自己的结算**之前**被**依次**问三次「能不能生效」—— 全局（`'效果-能否生效'`）→ 来源（`from` 身上的 `'效果-来源-能否生效'`）→ 目标（`to` 身上的 `'效果-目标-能否生效'`），**回调返回非 nil 值即阻止**（返回值就是原因，`false` 归一成一句通用原因），**谁先给原因就停在谁那儿** —— 这次生效不结算、没有结果、`err` = 原因、不算失败、收尾照跑。阻止**只作用于这一个效果**（不影响外层、不影响同一张牌对其余目标的生效）。**没有 `remove()` 了**（当天删）：内容侧要阻止就返回原因，内核（`apply` 里那两处）要停掉一次结算直接用自己的任务 `task:cancel()`。删它的理由（探针实测）：从别的效果的执行体里取消**停不住对方** —— 任务当场以 `canceled` 收尾、`.err` 立刻读得到、收尾也跑了，但那个执行体照旧跑完；所以「跨效果取消」既没用又危险，而「阻止自己」现在有更直白的返回值。
- **作答通道三类**（2026-09-30 定）：**问句类**（`'效果-能否生效'` 三段）用**返回值**作答 —— 返回非空即阻止；**事实类**（`'效果-被响应'` 两段）用**动作**作答 —— 订阅者在回调里 `ask:cancel(原因)`（调用后不会返回，见 `game:askPlayCard` 行）；**询问类**（`'卡牌-询问'` / `'决策-询问'`）也用**返回值**作答 —— 返回的东西就是答复、返回空 = 不表态，**第一个表态的胜出、后面的订阅者不再调**（旧写法 `ask:answer(...)` 已退休）。判据：内核「先问后办」⇒ 答案；「已成事实、谁有异议就翻案」⇒ 动作；「要人给个东西」⇒ 返回值。
  - **它就是官方的「生效前」**（2026-09-24 定，写进 `sanguosha-rules` §9.10）：内容侧想「在某个效果生效前插一手」就订它；【无懈可击】= 在这个时机里问一圈，有人要抵消就**返回原因**（不是 `remove()`）。被抵消的牌**照常**进弃牌堆（那次使用的去向由既有收尾管）。
- **询问与应答方**：内容侧要一张牌就 `game:askCard(...)`（**要一次「使用」换 `game:askUseCard(...)`**、**要一张「打出」的牌换 `game:askPlayCard(...)`（再加第 4 参数 `responseTo` 就是一次「响应」）**、**要一名角色换 `game:askPlayer(...)`**、**要在若干选项里挑一个换 `game:askChoice(...)`**、**要一次技能发动换 `game:askUseSkill(...)`**）—— 它是一次效果（有父效果、可被取消、`kind` = `askCard` / `askUseCard` / `askPlayCard` / `askPlayer`），**答复就是这次询问的结果**（读 `.card` / `.cards`；`AskUseCard` 还读 `.targets`；**应答一给出就定下** —— 答复时机里就读得到）。**缘由**是不透明字符串（照惯例写**发起这次询问的牌名 / 阶段名**：`'杀'` / `'出牌'` / `'濒死'` 之类，内核只原样带给规则层）；**要的是「使用」还是「打出」还是「随便一张牌」由类表达**（2026-09-23 拆分，不再用缘由传语义）。**条件**（第三个）描述"要什么样的牌"：`name?` / `zone?` / `card?` 三条筛选条件（数组 = 其一，不填 = 无要求），`AskUseCard` 再加 `target?`；候选来源与使用语义见 `AskCard` / `AskUseCard` 行；**业务层不自己拼候选**（"哪些牌可以给、答复在不在里面"得由内核统一做 —— 协议 / AI 给的答复是**外部输入**）。这里**没有"区域候选"这种东西**（2026-09-23 撤）：服务器侧看得见所有牌，暗区的遮蔽归协议层。内核**不写死「谁来答」**：询问通过局上的 **`'卡牌-询问'`** 时机送出去，应答方拿到询问实例后**返回**答复 **`{ card = … }`**（要一次使用时还要 `targets = …`，给单个或一张列表都行 —— 入库前统一成列表，所以 `.targets` 恒为 `Player[]`）；**返回空（`nil`）= 不表态，问下一位**；**第一个给出答复的胜出 —— 后面的订阅者根本不再被调**（2026-09-30 起；`answer` 方法已退休）；应答方可以**让出**（当场拿不到就等会儿再返回，业务侧照旧像写同步代码一样写）；**没答上 = 「取消」**（不表态与空答复是同一件事）：`.err` = 「取消」、`.success` 假、**不进错误处理器**（玩家不表态不是故障）——**但「取消」算不算成立看这次允不允许不给**（用户 2026-10-09 定）：`min` 给 0 ⇒ 取消是合法答复、照常**成立**（`.err` 为空、结果为空）；不允许取消的询问（`condition.cancelable = false`）没答复才记**拒收**（`.err` = 「这次询问必须给出答复」）—— **`cancelable` 只管「协议层给不给取消入口」，逻辑侧无论如何都要处理「玩家不选」**（2026-10-08 用户定：**默认允许**；全库只有四处写 `false` —— 要的牌已经摆出来点名、玩家无权拒收：五谷丰登 / 过河拆桥 / 顺手牵羊 / 【反馈】）；**答复不合法由内核拒收**（`.err` = 原因，与“答不上”对调用方是同一个分支）。这一套只服务「要一张牌 / 要一次使用 / 要一次技能发动」三种问法 —— 要数字（倒计时）的问法将来另开一个类。
- **答复之后**：**有答复才触发**（没人应答不触发 —— "问了没人答"是另一个事件，将来另开）：交互次序是「答复定下 → `self:onAnswered()`（子类处置那张牌）→ **`'卡牌-答复'`** → **`'卡牌-答复后'`**」，后两个时机的上下文都是这次询问实例，把"这次答复意味着什么"交给**规则层**决定。**结果在应答的那一刻就已定下**（询问在 `settle` 里校验并归一化答复之后 `self.task:resolve`），所以这两个时机里 `askCard.card` / `askCard.targets` 就能读到答复里给的东西（【杀】就靠 `askCard.card` 判断"打出了闪"）。**答复的牌去哪**：`AskPlayCard` 在 `onAnswered` 里已经把它放进发起那次结算的临时区（收尾时由**内核的默认收尾**送 `弃牌`）；`askCard` / `askUseCard` 不动那张牌，去向由内容侧自己写。
- **效果即可等待的任务**：效果有完成信号 —— `settle()` 跑完 = 完成（**它的返回值就是这次结算的结果**，读 `.result`；子类也可以在结算中途 `self.task:resolve(结果)` 把结果定下 —— `task` 是 `Effect` 上的公开字段（2026-10-08 起；原先是 `protected`，放开是为了让内容侧能拿几路效果去 `game:effectRace`），`AskCard` 就是这么做的；`Effect` **不提供** `:resolve` 封装（用户 2026-09-20 定））、被取消 = 没有结果、出错 = 失败（读 `.err`）。`:apply()` **驱动**这次结算（**排上队、下一笔调度才开跑**）、`:await()` **等它结完**（都返回效果自己；已驱动 / 已结完就立刻返回，幂等）、`:cancel(原因)` 让这次生效以「不成立 / 被阻止」收尾 —— 它只转手给 `task:cancel(原因)`：**优先级最高**（结果已经定过也强行改成「取消」），**收口与停住执行体都在任务那边**（收口 = `__del`；停住自己 = 先让出一笔调度、由下一笔调度关掉那条协程）。**任务侧的收口只有一个入口**（2026-09-29）：`resolve` / `reject` 只把结果记下来，「叫回调 + 叫醒等待者 + 收掉执行体」全在 `Task:__del` 里 —— 也就是**谁 `Delete` 谁收口**。**入口（`game:useCard` / `game:damage` / `game:ask`）自动「驱动 + 等」并返回效果实例** —— 调用方必须等：效果是一条一条跑的链，同一时刻只有一条在跑。取消以「没有结果」完成、**不抛**；真故障记进 `.err`（`error` 只表示报错，不给「正常结束」当跳出用，见 `code-style.md` 第 10 节）。
- **「打出」是询问的一个类别，不是内核的一个动作**（2026-09-20 定、2026-09-23 改成类型）：没有 `game:respond`、也没有 `'卡牌-打出后'` 时机 —— 一张牌"为响应而用掉"就是**一次 `askPlayCard` 被答复**（2026-10-09 起「响应」也收在它身上：带上 `responseTo` 就会把答复宣布成两段「被响应」时机、并允许订阅者驳回 —— 见上表）：候选按条件筛（不跑 `canUse`、不要目标）、答复只有牌，**牌当场交出去**（进发起那次结算的临时区）。它**不产生"使用时"那套**（不跑 `'卡牌-能否使用'`、**不进使用账**；2026-10-08 起自己记一本**打出账**）—— 「打出 vs 使用」的区别就体现在**用哪个类**上。

- **前提：整个游戏都在协程里跑**（用户 2026-09-21 确认）：装配方在协程里开局、触发 `'游戏-开始'`、`game:runFlow()`，所以**内容侧的时机钩子可以放心 `await`**（放置走 `game:moveCard`、`game:ask` / `askCard`、`useCard`、`damage` 都是 await 点）；内核不为「在同步上下文里触发时机」兜底（那会表现为「当前协程无法让出」）。
- **游戏结束（2026-09-21 落地）**：**信号在内核、判据在内容** —— 内核只给 `game:endGame(result)` / `game:getResult()` 与 **`'游戏-结束'`** 时机（结果类型 `Game.Result` = `{ side, reason }`：`side` 用官方术语「主公方 / 反贼 / 内奸」，`reason` 是给人看的中文短句），判据写在 `package/身份场/胜负.lua`（订阅 `'玩家-死亡'`）。**结束后内核不再起新的结算**：`Effect:apply()` 开头查一次结果，已结束 ⇒ 这次生效以「取消」收尾（多目标【杀】打死主公后不会再打下一个目标，游戏结束后也不会再起新的濒死）；**已经跑着的结算不打断**（记牌器是**只增的历史**、不是结算栈，没法猜「谁还在跑」）。

## 13. 座位控制者（User）与询问的分派

- **`User` 是「谁在控制这个座位」**：真实玩家（`ClientUser`，将来走协议）、电脑（将来的 `AIUser`）、测试夹具都是它的子类。落点 `server/user/` —— `init.lua` **只做装载**（`user.user` 先、`user.client-user` 后），`user.lua` 是基类、`client-user.lua` 是真实玩家；走 `require`（**不参与热重载**，与 `server/session/` 同一层）；**没有工厂 ⇒ 不挂门面**，类按 `Class` 名全局可用（`New 'ClientUser' (…)`）。
- **绑定在玩家身上**：`player.user`（**可空** —— 没有就是没人应答、直接走全局时机）+ `player:setUser(user?)`（绑定 / **中途更换** / 解绑都走它；不发事件）。内核只依赖**类型**（`Player.user` 上的注解），不 `require` 实现。
- **每类询问一个方法**（11 个，名字与询问类同名）：`ask` / `askChoice` / `askPlayer` / `askCard` / `askCardWithTarget` / `askUseCard` / `askUseCardToCard` / `askPlayCard` / `askUseSkill` / `askHero` / `askPanel`；参数是那次询问的实例，返回值就是**与内核同一形状的答复**，**返回空 = 不表态**（回落全局时机；最终按既有口径判「取消 / 必须给出答复」）。基类那 11 个方法都是空的 ⇒「没有 User」「User 不关心这一类」「User 认为该问全局」三者同一个结果。
- **分派的顺序：先问本人的 User，返回空才走全局时机**（`'卡牌-询问'` / `'决策-询问'` / `'技能-询问'` / `'武将-询问'` / `'面板-询问'`）—— **同一个询问**只走一遍这两步，User 的答复优先于任何全局订阅者。典型写法（`AskChoice` / `AskPlayer` / `AskHero` / `AskUseSkill` / `AskPanel` 各自在自己的取值处写）：

  ```lua
  local answer = self.to.user?:askPlayer(self)
              or self.game:fire('决策-询问', self)
  ```

  **`Ask` 是例外**：它的答复是「任意值」、可能是 `false`（合法答复）⇒ 写成 `or` 串会把 `false` 吞掉，所以它用显式判空。
- **`AskCard` 一族共用一个取值处**（`AskCard:collectAnswer`）⇒ 具体方法名交给子类给：基类 `AskCard:askUser(user)` 转发 `user:askCard(self)`，四个子类各覆写一行（`askUseCard` / `askUseCardToCard` / `askPlayCard` / `askCardWithTarget`）。
- **全局时机没有被取代**：它是**兜底与调试**通道 —— 现有 300 余处用例的应答脚本照旧工作（`Player` 上没有 User 就直接走它）。
- **本批只做骨架**：`ClientUser` 只留接口（协议接线是后续批次）；`AIUser`（真 AI）另开变更；`AskPanel` 的多轮接口形状、删除 `server/session/` 都留后（用户 2026-10-09 定：session 是「还没有 User 概念时为了跑测试临时加的外壳」，之后去掉）。

## 14. 传输层与 Client（`server/transport/`）

- **三层切分**（都不参与热重载，走 `require`）：

  | 文件 | 职责 | 认识的边界 |
  | --- | --- | --- |
  | `jsonrpc.lua` | 编解码**纯函数**（`decode` / `encodeCall` / `encodeResult` / `encodeError` + 标准错误码）；**线上消息的形状声明在 `server/proto.d.lua`（`JSONRPC.*`）**，`Jsonrpc.Message` 只是那四类的联合别名 | 只认识「表 ↔ 字符串」 |
  | `link.lua` | 传输：`read` / `write`（+ 可选 `close`） | 只认识「一条消息 = 一个字符串」 |
  | `client.lua` | 端点：`create(link)` / `start()` / `onMessage` / `notify` / `request` / `awaitRequest`；`register` 走**模块级** | 只认识 `Link` 的那几个方法 |

- **`Link` 是纯字节通道**（用户 2026-10-09 定）：`read(n)` 读 `n` 个字节（不够就挂起）、`read()` 不给 `n` 就把**能读的全读走**（完全没有数据才挂起）—— 两者都是 `---@async`，断开或出错给 `nil, 原因`；`write(text)` 给 `boolean, 原因?`；`close(reason?)` 可选。**帧不归它管**（它只会拼字符串 / 切字节）。本批带一个**内存实现** `moe.link.pair()`（一对互通 —— 本地回环 / 测试用；**不是测试后门**）。
- **帧格式：4 字节长度头 + 正文**（用户 2026-10-09 给）—— 头是 `'>I4'`（大端 32 位无符号）、**长度不含头本身**，正文就是 JSON-RPC 那串。三个原语（`HEADER_SIZE` = 4 / `decodeFrameLength` / `encodeFrame`）就住 `client.lua` 的局部 —— **帧不是 JSON-RPC 的一部分**（用户 2026-10-09 定：长度头是传输约定，`jsonrpc.lua` 只管「表 ↔ 字符串」）；**`Client` 不维护字节缓冲**：`send` 先套头再写，读循环写成「`read(4)` 取头 → `decodeFrameLength` → `read(长度)` 取正文 → `onMessage`」—— 凑够一帧这件事**由 `Link` 挂着等**（半包 / 粘包都在 `link:read(n)` 里消化）。
- **`register` 是模块级的**（`moe.client.register(method, fun(client, params): any)`，返回 disposer）：方法表**所有连接共用**，与具体连接无关（重连不用重注册）；同一个 method 重复注册报错。**带 id 的调用当请求**（回调返回值 = `result`；抛错 ⇒ `-32603`）、**不带 id 的当通知**（返回值忽略，抛错只记日志 —— 通知没地方回错）。回调**可以 `await`**（经网络层的东西本来就不可能同步）。
- **入站请求各自起一个协程** —— 读循环不被处理器挡住。这条是硬的：处理器里可能要 `client:awaitRequest(...)`（后端反向请求），那个响应要靠读循环读进来，串行处理会当场死锁。
- **`request` 返回 `Task`**（`callback` 可选，参数同 `Task:await` 的两个返回值）；`awaitRequest` = `request(...):await()`（失败给 `nil, 原因`、**不抛**）；`notify` 透传 `write` 的成败。**写失败** ⇒ 该请求立刻以那个原因收尾。
- **断开**：`start()` 起的读循环拿到的 `read` 给空 ⇒ `Client:close(原因)` 收摊（标记关闭 + 把还在等的请求全部以「连接断开」收尾）；不认识的结果记一条 `warn` 丢掉。
- **`start()` 用 `executeSync` 内联跑到第一个挂起点** ⇒ 返回时读循环已经挂在「等消息」上（调用方不必再让出一次）。⚠️ 用 `executeAsync` 的话它要等一个调度才跑，用例里就得先 `sleep(0)`。
- **本批不做**（用户 2026-10-09 定）：TCP 与帧格式、请求超时（**不做**）、`server/proto/` 的方法名常量、`ClientUser` 的接线、删除 `server/session/`。

## 16. 卡牌下行同步（`server/transport/card-sync.lua`）

**要解决的问题**：客户端要「看到盘面」—— 每个牌区里有哪些牌、牌面是什么、牌从哪到哪；而询问（候选 / 答复 / 目标）全建立在这份视图上。

**形状：不可变实例 + 三类通知 + 一类动画预通知**（用户 2026-10-10 定）

| 通知 | 什么时候发 |
| --- | --- |
| `Card.Create` | 牌出现（含开局的全量灌入） |
| `Card.Update` | 牌**没换区**但内容变了（转化 / 翻明）—— 实例 id 不变 |
| `Card.Remove` | 牌消失（按 id 列表） |
| `Card.Move` | 搬牌那一刻**当场**发（带 `from` / `to`），只为播动画；保证早于 `Card.Remove` |

- **视图与 id 住在连接侧，内核不认识协议**：`moe.cardSync` 按**每个连接**维护一份「这个客户端看见的牌」的账（`id → Proto.Card`，背面牌也在里面），id 由这个连接自己的号源发。内核那条 `Card.id` 与协议无关（留着当调试号）。
- **反过来，内核只多一条「旁观者」通道**：`Game:watch { enter?, leave?, change? }`（**内核级**，**不随 `resetContent` 清空** —— 内容时机表每次装载都会清，内核机制不能挂在它上面，见 §8.4 的老教训）。`Zone` 的进 / 离区与 `Card:addModifier` 都会通知它。
- **牌面分两层**（2026-10-10 用户定）：`template` = **牌自己那份**面（`card.ownFace`，永不变）、`modifier` = **所有「转化」叠出来的那一份**（`card.modifier`，没挂转化就不带这个字段）。**合并只在内核做一份**（`card.face` 是最终值，`card.name` / `suit` / `point` 都指向它），客户端把两层叠起来即可。`Card.Move` 只带 `template`（客户端本地已有 `modifier`）。
- **判定口径**（用户 2026-10-10 定）：牌变化后**置脏**；flush 时把「新算的一份」与「这个连接视图里已有的那份」逐字段比 ——
  - 完全一致 ⇒ 不发（所以「加了转化又撤销」等于没发生）；
  - 有变化、**协议区域相同** ⇒ `Card.Update`；
  - 有变化、**协议区域不同** ⇒ 换新 id + `Card.Remove` + `Card.Create`。
- **协议区域 = 玩家 + 区名**：临时区（既没名字也没归属）一律是同一个空区域 ⇒ **临时区之间互移不算换区**（不换 id、也不发 `Move`）。
- **背面牌的 id 是匿名代号**：看不见内容的区里每张牌只有 id（客户端只知道「这个区里有几张」）。**从这种区移除时，从「该连接看到的、这个区里没有牌面的那些牌」里随机挑一个 id** —— 否则「移除 + 创建」是对称的，客户端能把刚消失的匿名牌与刚出现的明牌配起来。
- **按收件人裁剪**：区级可见性（`zone:isVisibleTo`）叠加这一次搬动的可见性，任一不可见就省掉 `template`（客户端渲染成背面）；可叠加的可见性由后端消费，不下发。
- **批量**：`Create` / `Update` / `Remove` 攒到一次调度末尾合并发（与 `player.custom` 的置脏 + flush 同一套），`Move` 例外。
- **出口**：`User` 上四条（`cardCreate` / `cardUpdate` / `cardRemove` / `cardMove`，基类空），`ClientUser` 覆写成对应的 `notify`。
- **开局 / 重连**：`moe.cardSync.syncAll(game)` 把这一局全部牌区里的牌灌一遍 —— **由外壳在开局后调用**（本批只提供入口，会话那批接）。

**已知件**：`Proto.CardTemplate.modifier` 本批没发（`template` 只带叠加后的最终值）—— 要区分「原始牌面 / 转化」，得先定下「牌自己那份牌面」的读法再定发什么。

## 15. 玩家的自定义数据与增量下发（`player.custom` + `Player.Update`）

**要解决的问题**：武将牌、身份、将来的装备 / 技能 / 状态……都得让客户端看见，但**谁看得见**各不相同（武将公开、身份只有主公与自己）。于是把「内容侧往玩家身上挂的自由数据」收进一个容器，**可见性由容器记账**，下发时**按视角裁剪**。

- **容器 `player.custom`**（`server/core/custom.lua`，`Custom` 类；建玩家时就建好）：
  - `custom.proxy` —— 内容侧**读写**的那张表（`player.custom.proxy.heroName = '刘备'`）；**写走元表**：进 `raw` → 调 `hook(key, value)`（可选）→ `player:markDirty('custom')`。
  - `custom.raw` —— 真实数据（内核遍历用）；`visibles` —— 逐键可见性（私有）。
  - `custom:setVisible(key, options)` / `isVisible(key, viewer)` / `allVisibles(viewer)`；`options` 就是通用的 `Visibility`（`true` / `false` / 一名角色 / 角色表 / 谓词，见 `moe.visibility`）。
  - **默认只有自己看得见**（fail-closed）：没设过可见性的键，别人一律看不见；自己没有值也照样「看得见自己那份」（读出来是空）。
- **内容的落点**：身份写在 `package/身份场/身份.lua`（`setIdentity` 写 `proxy.identity`，主公 `setVisible('identity', true)`）；武将牌面写在 `package/@基础/武将.lua`（`heroName` / `heroSex` 公开）。**协议类型由内容包自己补** —— 各包在自己的 `meta.lua` 里给 `---@class Proto.Custom` 加字段（class 声明是合并语义）。
- **`player.identity` 是只读的便捷读法**（`M.__getter.identity`，真相在容器里）—— 读的地方保持「像字段」（`code-style.md` §11 的口径），写入只有 `setIdentity` 一处。
- **置脏与批量下发**（`game` 上）：`player:markDirty(种类)` → `game:markDirty(player, kind)`；**第一次标脏时登记一次** `moe.await.wake(flush)`（不是计时器、也不是「每帧」），`kind` 现在两种：`'base'`（id / 用户名 / 座位）与 `'custom'`。**一笔调度里改多少字段都只发一次**，flush 完就清（不会重复发）。
- **按视角组装**（`moe.player.sendUpdates(game, dirty)`）：基础信息一份（`Proto.Player.Base` = `id` / `userName` / `seat`，人人相同）合成**一条** `Player.Update`；custom **每个收件人各组装一份**（`custom:allVisibles(viewer)`），**一个玩家一条** `Player.UpdateCustom`（载荷 `Proto.Player.Custom` = `{ id, custom }`），**看得见的键一个都没有就跳过**。**没有 `user` 的玩家（或视角）不下发**。
- **`User:update(data)`** 是唯一出口：`data.base?` / `data.custom?` 各是「要发的载荷」，基类空实现（不表态），`ClientUser` 覆写成两条 `notify`。**内核不认识协议** —— 它只把组装好的表交出去（与 `player.user` 同一路：只依赖类型注解，不 `require` 实现）。
- **连接集合**（`server/transport/clients.lua`，`moe.clients`）：`add(client)`（**返回撤销函数**）/ `remove` / `broadcast(method, build)`（`build(client)` 各造一份，返回 `nil` 即跳过）。**内核不碰它** —— 谁持有集合、谁往里放连接由外壳决定。
- **一类数据一条协议**（用户 2026-10-10 定）：`Update` 只带基础信息、`UpdateCustom` 只带 custom；将来 `Zone` / `Skill` / `Buff` 各自一条，**不做「一个大快照」**。
- **增量由客户端比对**（用户 2026-10-10 定）：本批**不做差分**，每次发的是该类数据的**全量**（custom 会按视角裁键，但发出去的都是当前值）。
